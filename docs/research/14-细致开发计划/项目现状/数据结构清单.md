## 存储架构：PostgreSQL vs Qdrant 职责划分

### 核心原则

**PostgreSQL 管"存什么"，Qdrant 管"怎么找"。**

PostgreSQL 是系统的事实源（source of truth），存储全部结构化业务数据。Qdrant 是检索加速器，只存储需要被向量搜索的文本子集及其向量。

### 存储内容对比

| 维度 | PostgreSQL（22 张表） | Qdrant（5 个集合） |
|------|----------------------|-------------------|
| papers | 完整记录：title/abstract/authors/year/venue/doi/identifiers/classify/status/source_platform 等 30+ 字段 | paper_profiles 仅存 title+abstract 文本 + 向量，metadata 仅 paper_id/project_id/title |
| paper_chunks | 解析结果、chunk 元数据（完整字段见 2.1） | chunk 文本 + 向量，metadata 仅 7 字段（paper_id/section_type/chunk_type/parent_id/page_start/page_end/token_count） |
| paper_sections | 章节级全文 + 结构化提取（claims/entities/methods_used/key_results/limitations 等 27 字段） | section 全文向量，metadata: paper_id/section_type/section_title/project_id/token_count |
| paper_cards | 完整卡片：research_question/method/findings/limitations/future_work/source_spans/quality_score | 不存储 |
| evidence_records | 完整证据：topic/finding/limitation/method/evidence_strength/source_chunk_id/source_quote | 不存储 |
| citation_contexts | 引用上下文：citation_context/surrounding_text/citation_type/section/source_chunk_id | 引用上下文向量，metadata: citing_paper_id/cited_paper_id/citation_type/section/project_id |
| graphs | 节点/边/关系/GAP | 不存储 |
| reports | 综述/创新点报告全文 + 版本历史 | 不存储 |
| search_sessions | 搜索会话工作空间（session_id/project_id/name/status） + session_papers 纯关联表 | 不存储 |
| 其他 | projects/papers_pool/qa_history/tasks/report_versions/topic_scores/queries/paper_queries/paper_references/kg_nodes/kg_edges/parse_results/search_cache 等 | 不存储 |

### Qdrant 集合详情

#### paper_chunks（chunk 级向量）

```text
向量：dense（sentence-transformers/all-MiniLM-L6-v2）+ sparse（Qdrant/bm25）
用途：ScopeQA 精细检索，按 chunk 返回最相关文本片段（L2 层）
写入时机：parse_paper() 解析后双写
过滤维度：paper_id / section_id / section_type / chunk_type
```

#### paper_profiles（论文级向量）

```text
向量：dense（sentence-transformers/all-MiniLM-L6-v2）+ sparse（Qdrant/bm25）
用途：search_for_review 快速论文级检索，按论文粒度返回最相关论文
写入时机：embed_paper() 解析后双写（title + abstract 拼接）
过滤维度：paper_id / project_id
```

#### search_queries（查询向量）

```text
向量：dense + sparse
用途：历史查询相似度匹配，供 SearchCache 查询相似度检索
写入时机：search_candidates / search_for_review 保存查询记录时
payload：search_id / project_id / search_type
过滤维度：project_id / search_type
```

#### paper_sections（章节级向量）

```text
向量：dense + sparse
用途：章节级语义检索，按 section 返回最相关章节文本
写入时机：parse_paper() 解析后双写
payload：paper_id / section_type / section_title / project_id / token_count
过滤维度：paper_id / section_type / project_id
```

#### citation_contexts（引用上下文向量）

```text
向量：dense + sparse
用途：引用上下文语义检索，支持立场分析和引用溯源
写入时机：提取引用上下文后写入
payload：citing_paper_id / cited_paper_id / citation_type / section / project_id
过滤维度：citing_paper_id / cited_paper_id / citation_type / section / project_id
```

     ▼                                    ▼

### 章节提取数据流

```text
PDF 解析 → PaperChunk[] → 按 section_type 聚合 → PaperSection[]
                                                         │
                                                    SectionExtractor (LLM)
                                                         │
                                                         ▼
                              PaperSection（填充 summary/claims/entities/key_results/limitations 等）
                                                         │
                                                  ┌──────┴──────┐
                                                  ▼              ▼
                                          PostgreSQL         Qdrant
                                         (结构化查询)     (语义检索)
                                                    向量：summary（~200 token）
```

Qdrant 的数据是 PostgreSQL 的子集的向量化投影。没有 PostgreSQL 就没有完整的论文库、卡片、证据、图谱和报告；没有 Qdrant 只是失去向量检索能力，退化为关键词搜索。

### 分层检索架构（L0→L1→L2）

**问题**：flat chunk 检索在论文量大时性能差——每篇论文可能有 50-100 个 chunk，100 篇论文就有 5000-10000 个候选向量，检索噪声大、速度慢。

**方案**：三层递进检索，每层缩小范围后再深入下一层。

```text
L0  PaperProfile（论文级）
    集合：paper_profiles
    向量：title + abstract 拼接
    粒度：1 向量/论文
    作用：快速定位相关论文（100 篇 → Top-K 篇）
         │
         ▼ 过滤条件：paper_id ∈ L0 结果
L1  PaperSection（章节级）
    集合：paper_sections
    向量：章节摘要（summary，~200 token，由 SectionExtractor 生成）
    粒度：1 向量/章节（约 5-8 章节/论文）
    作用：定位相关章节（Top-K 篇 × 5-8 章节 → Top-K 章节）
    备注：使用 summary 而非全文（3000-8000 token），提升检索精度和效率
         │
         ▼ 过滤条件：section_id ∈ L1 结果
L2  PaperChunk（chunk 级）
    集合：paper_chunks
    向量：chunk 文本
    粒度：1 向量/chunk（约 5-15 chunk/章节）
    作用：精确检索相关片段（Top-K 章节 × 5-15 chunk → Top-K chunk）
```

**性能对比**：

| 维度 | Flat 检索 | 分层检索 |
|------|----------|---------|
| 100 篇论文候选向量数 | ~5000-10000 | L0: 100 → L1: ~500 → L2: ~1500 |
| 检索精度 | 低（噪声多） | 高（逐层聚焦） |
| 检索速度 | 慢 | 快（每层向量少） |
| 上下文连贯性 | 差（chunk 零散） | 好（section 级聚合） |

**服务**：`HierarchicalRetriever`（`hierarchical_retriever.py`）

```text
输入：query_text, project_id, top_k_papers=10, top_k_sections=20, top_k_chunks=30
输出：list[RetrievalResult]（包含 chunk 文本 + 所属 paper/section 信息 + 相关度分数）

流程：
1. L0：paper_profiles 检索 → 返回 top_k_papers 篇论文
2. L1：paper_sections 检索（filter: paper_id ∈ L0）→ 返回 top_k_sections 个章节
3. L2：paper_chunks 检索（filter: section_id ∈ L1）→ 返回 top_k_chunks 个 chunk
4. 合并结果，附带 paper/section 上下文信息
```

### PaperProfile 设计（只读聚合）

PaperProfile 不是独立提取模型，而是从 PaperSection 只读聚合的论文级视图：

```text
PaperProfile = f(Paper, PaperSection[])
  - title: Paper.title
  - abstract: Paper.abstract
  - tldr: 由 SectionExtractor 从 abstract section 生成
  - methods_summary: 聚合所有 section.methods_used，去重
  - key_findings_summary: 聚合 result/discussion section.key_results
  - limitations_summary: 聚合所有 section.limitations
  - topics: 聚合所有 section.entities（type=topic）
```

写入 Qdrant paper_profiles 时，embedding 文本 = title + abstract + tldr（如有）。

### 按需提取层（On-Demand Extraction）[待设计]

**背景**：上线产品（Elicit / Paperguide / Consensus）的文献综述流程中，提取阶段是**用户驱动**的——根据具体研究问题定义要提取什么字段，然后从 Top 论文的 PDF 全文按需提取。我们的 SectionExtractor 是**预定义**的——不管研究问题是什么，都提取同样的 8 个字段（methods_used/key_results/limitations 等）。

**两种模式对比**：

| 维度 | 预提取（当前 SectionExtractor） | 按需提取（Elicit/Paperguide 模式） |
|------|-------------------------------|----------------------------------|
| 提取时机 | PDF 解析时 | 生成综述/QA 时 |
| 字段来源 | 固定 schema（8 个字段） | 用户定义 + AI 建议（24 种可选列） |
| 提取范围 | 全部论文的全部 section | 仅 Top-K 论文 |
| 灵活性 | 低（字段固定） | 高（用户可增删改列） |
| 速度 | 快（预计算） | 慢（每次读 PDF） |
| 适用场景 | 论文卡片、通用 QA | 定制化综述、系统综述 |

**上线产品的提取字段参考（Elicit 24 种列 + PICO 框架）**：

```text
研究识别：Author/Year/Country/Journal
研究设计：Study Design/Duration/Sample Size/Randomization
人群：Population Characteristics/Age/Gender/Inclusion Criteria
干预：Intervention Type/Dosage/Frequency/Duration
对照：Comparator/Control Condition
结局：Primary Outcome/Outcome Value/Confidence Interval/Secondary Outcomes
质量：Risk of Bias/Quality Score
发现：Key Findings/Limitations/Conclusions/Research Gaps
```

每条提取结果附带 **supporting quote**（原文引用 + 页码 + 段落位置）和 **reasoning**（AI 推理过程）。

**设计方向**：

```text
用户研究问题
     │
     ▼
QueryAnalyzer（LLM）
     │ 分析问题，建议提取字段
     ▼
ExtractionPlan（提取计划）
  - target_papers: Top-K 论文（从 L0 检索）
  - extraction_columns: [字段列表]（用户确认/编辑）
     │
     ▼
OnDemandExtractor（LLM）
  - 输入：PDF 全文 + extraction_columns
  - 输出：每篇论文的结构化提取结果
  - 每条结果附带 supporting_quote + page_number
     │
     ▼
ExtractionResult[]
  - paper_id
  - columns: {field_name: {value, quote, page, confidence}}
     │
     ▼
LLM 合成综述（从 ExtractionResult[] 生成）
```

**与现有系统的关系**：
- 预提取（SectionExtractor）→ 用于论文卡片、通用 Scope QA、快速浏览
- 按需提取（OnDemandExtractor）→ 用于定制化文献综述、系统综述、特定研究问题
- 两者共存，预提取提供基础数据，按需提取提供定制化深度

### embed_paper() 双写逻辑

```text
① paper_chunks：每个 child chunk 一个向量点（跳过 parent 块）
② paper_profiles：每篇论文一个向量点（title + abstract 拼接）

云端推理（cloud_inference=true）：Qdrant 自动生成 dense + sparse 向量，传文本即可
本地模式：EmbeddingService 预计算 dense（bge-small-zh）+ TF-IDF sparse
```
