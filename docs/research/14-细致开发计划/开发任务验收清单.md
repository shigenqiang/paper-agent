# 开发任务验收清单

更新时间：2026-05-28

本文档用于把 `docs/research/14-细致开发计划` 和 `模块级开发计划/00-15` 拆成可执行、可测试、可验收的开发任务。它可以直接作为 issue、迭代看板、PR 自检和阶段验收依据。

当前主线目录：

```text
src/agents_v3/research_workspace/
tests/agents_v3/research_workspace/
docs/research/14-细致开发计划/
```

验收目标：

```text
1. 每个模块都有明确输入、输出、失败路径和测试证明。
2. 从项目创建到报告导出形成稳定 MVP 闭环。
3. QA、综述、创新点必须基于 RetrievalScope 和 Evidence，可追溯、可拒答、可评估。
4. 搜索、解析、LLM、导出等失败不会让项目数据进入不可恢复状态。
5. 日志和评估能发现 Scope 越界、无来源报告、空泛创新点和敏感信息泄露。
```

## 1. 使用方式

### 1.1 状态定义

| 状态 | 含义 |
| --- | --- |
| `[ ]` | 未开始或未完成 |
| `[x]` | 已完成并有测试或人工验收证明 |
| `阻塞` | 不满足会阻塞 P0 MVP 或合入 |
| `可延后` | 不影响 P0，但应进入 P1/P2 |

### 1.2 验收证据

每个任务完成时至少给出一种证据：

```text
单元测试文件和用例名
端到端 smoke test 结果
本地 CLI 输出
API contract 示例
导出的 Markdown/JSON 文件
日志或 evaluation report 摘要
```

### 1.3 PR 合入底线

任何涉及代码的 PR 合入前至少满足：

```text
1. 新增或修改的 service 有失败路径测试。
2. 新增 Pydantic 模型有 model_validate/model_dump 测试。
3. 不把 API key、完整 prompt、完整 PDF 文本、完整 LLM response 写入日志。
4. QA、综述、创新点不引用 Scope 外论文或证据。
5. 报告保存时记录 scope、paper_ids、evidence_ids。
6. LLM JSON 输出经过 schema 校验、repair 或 fallback。
7. 批处理任务中单篇论文失败不导致整个项目失败。
```

## 2. 阶段总览

| 阶段 | 目标 | 完成后能力 |
| --- | --- | --- |
| P0-A 工程基线 | 存储、模型、测试隔离、E2E smoke | 可以稳定开发和回归 |
| P0-B 搜索 MVP | 多源搜索、缓存、限流、去重、入库 | 用户能找到并导入论文 |
| P0-C 解析与证据 | PDF chunk、PaperCard、EvidenceTable | 论文变成可追溯证据 |
| P0-D 图谱与 Scope | KnowledgeGraph、RetrievalScope、ScopeGuard | 用户选择范围后有边界 |
| P0-E QA 与报告 | ScopeQA、综述、创新点、导出 | 生成可追溯成果 |
| P0-F API 与评估 | API/task、日志、quality gates | 可前端联调，可验收 |
| P1 增强 | 检索质量、RAG 质量、成本、版本差异 | 产品体验和质量提升 |
| P2 扩展 | 数据库、向量库、图数据库、多用户、外部监控 | 面向规模化部署 |

## 3. P0-A：工程基线

### 3.1 Models 与 Storage

目标：所有模块共享稳定数据契约，测试与真实数据隔离。

- [ ] `Project`、`Paper`、`PaperChunk`、`PaperCard`、`EvidenceRecord`、`KnowledgeGraph`、`RetrievalScope`、`QAResponse`、`Report` 模型字段稳定。
- [ ] 模型支持 `model_validate` 和 `model_dump` 往返。
- [ ] 旧格式数据能兼容读取，缺失字段有合理默认值。
- [ ] `JSONStorage` 支持注入 `data_dir`，测试使用 `tmp_path`。
- [ ] `JSONStorage` 写入具备原子性或最小损坏恢复策略。
- [ ] collection 命名统一，不同项目数据不会串库。
- [ ] 损坏 JSON 文件有可读错误或安全回退。
- [ ] `__init__.py` 只导出稳定模型和服务，不导出实验内部对象。

验收证明：

```text

tests/agents_v3/research_workspace/test_storage.py
tests/agents_v3/research_workspace/conftest.py
```

阻塞条件：

```text
模型字段变更导致已有 fixture 无法读取。
跨项目查询返回其他项目数据。
```

### 3.2 ProjectService

目标：项目是所有工作流入口，能管理状态、统计和清理。

- [ ] 支持创建、查询、更新、删除项目。
- [ ] 项目包含 name、description、status、created_at、updated_at、metadata。
- [ ] 删除项目时有明确策略：级联删除或软删除。
- [ ] 项目统计包含 paper_count、card_count、evidence_count、report_count。
- [ ] 项目健康检查能指出缺失阶段：无论文、未解析、无证据、无图谱、无报告。
- [ ] 支持演示项目或最小 fixture 项目。

## 4. P0-B：论文搜索与入库

### 4.1 Search Models

目标：搜索请求、结果、session 和错误结构可序列化。

- [ ] `SearchQuery` 支持 query、year range、source filters、limit、sort。
- [ ] `SearchResult` 包含 title、authors、year、venue、doi、arxiv_id、abstract、pdf_url、source、source_url、score。
- [ ] `SearchResponse` 包含 results、source_stats、errors、cached、latency_ms。
- [ ] `SearchSession` 保存 query、results、selected ids、committed ids、created_at。
- [ ] `SearchErrorInfo` 记录 provider、category、message、retryable。

```text

```

### 4.2 Search Adapters

目标：至少支持稳定 mock 和真实 provider adapter 的统一接口。

- [ ] `BaseSearchAdapter` 定义 `search(query) -> SearchResponse`。
- [ ] OpenAlex adapter 支持关键词、年份、limit。
- [ ] arXiv adapter 支持关键词、分类或年份近似过滤。
- [ ] CrossRef adapter 支持 DOI 或关键词元数据补全。
- [ ] provider 失败不会导致整个搜索失败。
- [ ] adapter timeout、rate limit、bad response 有统一错误类型。

### 4.3 缓存、限流、去重、排序

目标：搜索结果稳定、可控、可重复。

- [ ] 搜索缓存 key 由 query、filters、sources、limit 稳定生成。
- [ ] 缓存支持 TTL，DOI 精确查询和普通关键词可使用不同 TTL。
- [ ] rate limit 支持 provider 维度最小间隔和失败退避。
- [ ] 去重优先级：DOI > arXiv ID > 标准化标题 + 年份 + 第一作者 > 标题相似度。
- [ ] merge 同一论文时保留更完整字段和来源列表。
- [ ] ranking 综合相关性、新近性、引用量、来源可信度。
- [ ] 返回结果包含 duplicate flags 或 merge provenance。

- [ ] 上传 PDF 校验文件存在、类型和大小。

## 5. P0-C：PDF 解析、论文卡片、证据表

### 5.1 PDF 解析与分块

目标：把论文 PDF 或文本变成可追溯 chunks。

- [ ] `ParserService` 支持单篇解析和项目批量解析。
- [ ] 解析前检查 paper 是否存在、是否有 pdf_path、文件是否存在。
- [ ] 成功解析后更新 paper parsing_status。
- [ ] 失败解析后更新 `PaperStatus.FAILED` 或 parsing error 字段。
- [ ] 单篇失败不影响项目中其他论文继续解析。
- [ ] chunk 包含 chunk_id、paper_id、section_title、section_type、text、start_char、end_char、token_count。
- [ ] 支持 abstract、introduction、method、result、discussion、limitation、conclusion、references 的基础识别。
- [ ] references chunks 可标记并在卡片生成时默认排除。
- [ ] token 估算支持英文、中文和混合文本。
- [ ] 不生成伪造 stub chunk 作为成功结果。

验收证明：

```text
tests/agents_v3/research_workspace/test_parser_service.py
tests/agents_v3/research_workspace/test_parser_sections.py
```

阻塞条件：

```text
解析失败被标记为成功。
空 PDF 或错误文件产生伪造研究内容。
chunk 缺少 paper_id 或 text。
```

### 5.2 PaperCard 生成

目标：把单篇论文变成结构化卡片，并保留来源。

- [ ] `PaperCardGenerator` 支持注入 storage 和 LLM。
- [ ] 生成前选择上下文，优先 abstract、method、result、discussion、limitation，排除 references。
- [ ] 上下文选择尊重 token budget。
- [ ] LLM 输出经过 Pydantic schema 校验。
- [ ] 解析失败时使用 fallback，但明确低 confidence 和 extraction_method。
- [ ] 卡片包含 research_question、method、data_or_sample、key_findings、limitations、future_work、topics、possible_gaps。
- [ ] 关键字段有 source_spans 或明确 unknown。
- [ ] source_spans 指向真实 chunk_id 和 quote。
- [ ] 卡片支持 active version，重复生成默认幂等，regenerate 创建新版本。
- [ ] confidence 根据字段完整度、source span 覆盖率、LLM/规则来源计算。
- [ ] 生成失败不写入伪造高置信内容。

验收证明：

```text
tests/agents_v3/research_workspace/test_paper_card_generator.py
```

阻塞条件：

```text
PaperCard 无来源却被标记高置信。
source_spans 指向不存在 chunk。
重复生成产生多个 active card。
```

### 5.3 EvidenceTable

目标：把卡片中的发现、不足、未来工作转成项目级事实层。

- [ ] `EvidenceTableService` 能从单篇卡片生成多条 evidence。
- [ ] 支持按项目聚合所有 included papers 的 evidence。
- [ ] 每条 evidence 包含 evidence_id、project_id、paper_id、topic、method、finding、limitation、future_work。
- [ ] evidence 尽量绑定 source_chunk_id 或 source_quote。
- [ ] 支持 evidence_type 或 claim_type：finding、limitation、future_work、gap、method。
- [ ] 支持 evidence_strength、confidence、review_status。
- [ ] 支持按 project_id、paper_id、topic、method、review_status 查询。
- [ ] 支持按 RetrievalScope 过滤 evidence。
- [ ] unknown 或无来源强结论不能进入 accepted 状态。

验收证明：

```text

```

阻塞条件：

```text
excluded paper 的 evidence 进入项目正式证据表。
accepted evidence 无 source_quote/source_chunk_id 且无解释。
```

## 6. P0-D：知识图谱与 RetrievalScope

### 6.1 KnowledgeGraph

目标：把论文、主题、方法、发现、不足、gap 组织成可追溯关系图。

- [ ] 图谱包含 Paper、Topic、Method、Finding、Limitation、Gap 节点。
- [ ] 图谱包含 BELONGS_TO_TOPIC、USES_METHOD、REPORTS_FINDING、HAS_LIMITATION、SUGGESTS_GAP 等关系。
- [ ] 节点 ID 稳定，同一项目重复构建结果稳定。
- [ ] 非 Paper 节点记录 source paper_ids、evidence_ids 或 card_ids。
- [ ] 边记录 provenance 和 confidence。
- [ ] 支持获取节点、邻居、子图、路径解释。
- [ ] 支持 node_ids + hops 获取子图，hops 有上限。
- [ ] 支持基础 gap 检测：共同 limitation、future_work、topic-method 空白。
- [ ] 图谱统计包含节点类型、边类型、孤立节点、gap_count。
- [ ] excluded paper 不进入图谱。

验收证明：

```text
tests/agents_v3/research_workspace/test_graph_service.py
```

阻塞条件：

```text
图谱节点无法回溯到 paper/evidence。
重复构建生成不稳定 ID，导致报告引用失效。
Graph path 被当成 evidence citation 使用。
```

### 6.2 RetrievalScope

目标：所有 QA、综述、创新点都必须先解析范围。

- [ ] 支持 all_project。
- [ ] 支持 selected_papers。
- [ ] 支持 topic_group。
- [ ] 支持 method_group。
- [ ] 支持 year_range。
- [ ] 支持 graph_subgraph。
- [ ] 支持组合过滤：topic + year、selected + method 等。
- [ ] resolve 返回 paper_ids、evidence_ids、graph_node_ids、graph_edge_ids、summary、metadata。
- [ ] 空 Scope 返回 empty_reason、summary 和 suggested_actions。
- [ ] Scope 只包含当前 project 且 included 的论文。
- [ ] `build_scope_guard` 可校验 paper/evidence/graph ids 是否越界。
- [ ] `to_paper_cards`、`to_evidence_records` 不返回范围外数据。

验收证明：

```text
tests/agents_v3/research_workspace/test_retrieval_scope.py
```

阻塞条件：

```text
selected_papers 返回未选中论文。
其他项目论文进入 scope。
空 scope 被当成全项目 scope 使用。
```

## 7. P0-E：ScopeQA、综述、创新点、报告

### 7.1 ScopeQA 与 RAG

目标：在范围内基于证据回答，证据不足时拒答或说明不确定。

- [ ] QA 入口必须先调用 RetrievalScopeService.resolve。
- [ ] QA 只能使用 scope 内 papers、evidence、graph context。
- [ ] 返回 QAResponse：answer、intent、scope_summary、supporting_papers、evidence_records、graph_paths、uncertainty、suggested_actions、validation_warnings、confidence。
- [ ] 支持 summary、method_compare、limitation_analysis、gap_analysis、innovation_generation、review_generation。
- [ ] 证据不足、空 scope、低质量 evidence 时拒答或降级说明。
- [ ] LLM 输出的 citations 必须经过 ScopeGuard 和存在性校验。
- [ ] 引用不存在 evidence_id 时清理并记录 warning。
- [ ] 检索结果带 retrieval_diagnostics。
- [ ] QA 历史或素材保存可延后，但 response 必须可复盘。

验收证明：

```text
tests/agents_v3/research_workspace/test_scope_qa.py
```

阻塞条件：

```text
QA 引用 scope 外 paper/evidence。
证据为空仍生成确定性结论。
LLM 输出 citation 未校验直接返回。
```

### 7.2 文献综述

目标：生成有结构、有来源、有质量校验的综述报告。

- [ ] 综述生成入口必须接收或解析 RetrievalScope。
- [ ] 收集材料时按 evidence、paper cards、graph summaries 构建 Evidence Matrix。
- [ ] 综述章节至少包含研究背景、主题划分、方法比较、主要发现、局限、不足与趋势、参考文献。
- [ ] Report 保存 scope、paper_ids、evidence_ids、graph_node_ids。
- [ ] 主体章节有 section_sources 或可解析来源标记。
- [ ] 大 scope 支持分批综合或材料压缩，避免简单截断重要证据。
- [ ] 低证据情况下生成“不足说明型报告”，而不是编造综述。
- [ ] 质量校验包含 source_coverage、section_source_coverage、traceability warnings。
- [ ] Markdown 导出包含报告元数据和来源索引。

验收证明：

```text
tests/agents_v3/research_workspace/test_review_generator.py
tests/agents_v3/research_workspace/test_report_service.py
```

阻塞条件：

```text
综述主体章节无来源。
报告引用 scope 外论文。
报告保存后无法追溯 evidence_ids。
```

### 7.3 创新点报告

目标：基于 gap 和限制证据生成具体、可执行、可追溯的创新方向。

- [ ] 创新点来自 gap、共同 limitation、future_work、方法迁移、数据/场景空白。
- [ ] 每个 InnovationPoint 包含 name、description、gap、supporting_papers、limiting_evidence、feasibility、risk、possible_topic、scores。
- [ ] 创新点必须引用 scope 内 supporting_papers。
- [ ] gap 必须能回溯到 limiting_evidence 或 graph gap。
- [ ] 过滤空泛表达，如“进一步研究”“优化模型”“提升性能”。
- [ ] 至少生成 3 个候选；证据不足时允许少于 3 个但必须说明不足。
- [ ] 评分包含 novelty、evidence_support、feasibility、risk、topic_fit。
- [ ] 可行性和风险不能为空。
- [ ] 创新点报告保存为 Report，并可导出。

验收证明：

```text
tests/agents_v3/research_workspace/test_innovation_generator.py
```

阻塞条件：

```text
创新点无 supporting_papers。
创新点只有空泛描述但通过质量检查。
引用 scope 外 evidence 或 paper。
```

### 7.4 报告版本与导出

目标：成果可保存、可版本化、可导出、可追溯。

- [ ] `ReportService.save_report` 保存 report_id、project_id、report_type、scope、content、paper_ids、evidence_ids、status。
- [ ] 支持 list/get/update/archive/delete。
- [ ] 支持 create_version、list_versions、restore_version。
- [ ] version 记录 scope_snapshot、content、created_at、change_summary。
- [ ] build_source_index 汇总 paper、evidence、section usage。
- [ ] validate_report_traceability 检查 paper/evidence 存在性和 scope 越界。
- [ ] validate_section_coverage 检查主体章节来源覆盖。
- [ ] export_markdown 包含标题、元数据、正文、来源索引、质量校验摘要。
- [ ] export_json 输出机器可读 report payload。
- [ ] 导出失败返回可读错误或空结果，不破坏 report 数据。

验收证明：

```text

```

阻塞条件：

```text

```

## 8. P0-F：LLM、API、任务、评估日志

### 8.1 LLM 提示词与结构化输出

目标：所有 LLM 调用可控、可修复、可观测。

## 14. 阶段验收定义

### P0 完成定义

P0 完成时必须满足：

```text
1. 用户能创建项目并搜索或导入论文。
2. 系统能解析论文并生成 PaperCard、EvidenceRecord、KnowledgeGraph。
3. 用户能选择 RetrievalScope 并进行 QA。
4. QA 返回范围声明、证据、论文来源和不确定性。
5. 系统能基于 Scope 生成文献综述。
6. 系统能基于 gap 和 evidence 生成创新点报告。
7. 报告能保存版本并导出 Markdown/JSON。
8. 前端或 API 能跑通核心演示链路。
9. 日志能定位搜索、解析、LLM、导出失败原因。
10. 质量门禁能发现 Scope 越界、报告无来源、创新点空泛和日志泄露。
```

### P1 完成定义

```text
1. 检索质量有 golden cases 和指标。
2. 报告质量有来源覆盖、traceability 和版本差异摘要。
3. token 成本和 LLM 失败率可汇总。
4. API/task/front-end 联调体验完整。
```

### P2 完成定义

```text
1. 数据层支持更大规模项目。
2. 检索层支持向量库和更复杂 GraphRAG。
3. 多用户、权限、审计和外部监控具备设计和初步实现。
```
