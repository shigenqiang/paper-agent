# 10-综述生成模块专项开发计划

更新时间：2026-05-28

本文档基于 `docs/research` 下的产品方案、当前开发计划、证据表计划、知识图谱计划、RetrievalScope 计划、Scope QA/RAG 计划、报告版本与导出计划、Token 成本分析和当前代码实现，重新细化综述生成模块的开发方案。

综述生成模块负责把 Scope 内的论文卡片、证据表和图谱上下文组织成可交付的文献综述。它不是“让 LLM 直接写一篇综述”，而是一个有材料收集、证据矩阵、章节生成、引用渲染、来源校验和报告保存的成果生成管线。它必须遵守证据边界：不直接拿全文拼接，不引用 Scope 外论文，不写无来源的泛化结论。

对应代码：

```text
src/agents_v3/research_workspace/review_generator.py
src/agents_v3/research_workspace/report_service.py
src/agents_v3/research_workspace/models.py
tests/agents_v3/research_workspace/test_review_generator.py
```

上游依赖：

```text
papers
paper_cards
evidence_records
KnowledgeGraph
RetrievalScope
Scope QA saved materials
```

下游依赖：

```text
ReportService
ReportVersion
Markdown / JSON export
成果报告页面
```

## 1. 模块定位

### 1.1 在产品链路中的位置

产品主线：

```text
研究项目
  -> 论文库
  -> PDF 解析与分块
  -> 论文卡片
  -> 证据表
  -> 知识图谱
  -> Retrieval Scope
  -> Scope-based QA
  -> 文献综述
  -> 创新点报告
```

综述生成位于 QA 探索之后、正式报告输出阶段。用户可以直接基于 Scope 生成综述，也可以先通过 QA 保存若干综述素材，再生成或补充综述。但最终报告必须重新绑定 Scope、paper_ids、evidence_ids 和 section_sources，不能只保存一段自然语言。

### 1.2 一句话目标

基于 Scope 内的结构化证据生成有章节、有引用、有来源索引、有质量校验、可版本化的文献综述报告。

### 1.3 核心原则

```text
1. Scope 是硬边界。
2. EvidenceRecord 是事实层。
3. PaperCard 是结构化摘要层。
4. KnowledgeGraph 是组织和解释关系的辅助层。
5. 每个主要章节必须尽量绑定 evidence_ids。
6. 证据不足时写限制，不扩写。
7. 长 Scope 必须分组、分批或摘要，不能一股脑塞入 prompt。
8. Report 必须保存 scope、paper_ids、evidence_ids、section_sources 和 validation_result。
```

## 2. 本地调研结论落地

### 2.1 产品方案落地

`当前产品方案.md` 要求文献综述基于选定 Scope、论文卡片、证据表和图谱上下文生成，默认结构包括：

```text
研究背景
主题划分
代表性文献和研究脉络
主要研究方法
主要研究结论
现有研究不足
未来研究趋势
参考文献
```

因此综述生成模块必须输出：

```text
1. 正文 Markdown。
2. 使用范围说明。
3. 使用论文列表。
4. 使用证据列表。
5. 章节级来源索引。
6. 参考文献。
7. 质量校验结果。
```

### 2.2 RetrievalScope 计划落地

08 模块要求 Scope 解析为：

```text
paper_ids
evidence_ids
graph_node_ids
graph_edge_ids
summary
empty_reason
explain
ScopeGuard
```

综述生成入口必须固定为：

```text
scope_payload
  -> RetrievalScopeService.resolve()
  -> ScopeGuard
  -> collect_materials()
  -> build_evidence_matrix()
  -> generate section drafts
  -> validate section sources
  -> render report
  -> save report/version
```

### 2.3 证据表计划落地

06 证据表模块强调：

```text
EvidenceRecord 是 QA、知识图谱、综述生成、创新点生成的事实层。
unknown、空字符串、模板占位文本不应进入 evidence_records。
QA 和报告生成应优先使用 accepted 或 traceable 的 evidence。
```

当前 `EvidenceRecord` 仍是旧字段：

```text
topic
research_question
method
data_or_sample
finding
limitation
future_work
evidence_strength
citation_context
source_chunk_id
source_quote
```

综述生成必须兼容旧字段，同时为未来字段预留：

```text
evidence_type
claim
review_status
evidence_relation
certainty
```

### 2.4 知识图谱计划落地

07 知识图谱模块要求 Topic、Method、Dataset、Finding、Limitation、Gap 等节点可追溯到 evidence。综述生成可以使用图谱做：

```text
1. 主题分组。
2. 方法分组。
3. Gap/局限聚合。
4. 图谱路径说明研究脉络。
5. 大范围下的 Topic/Gap summary。
```

但规则是：

```text
图谱用于组织和解释。
综述事实仍必须引用 EvidenceRecord 或 PaperCard。
```

### 2.5 Scope QA/RAG 计划落地

09 模块要求 QA 回答可保存为：

```text
review_material
innovation_material
evidence_note
```

综述生成可以读取已保存 QA 素材，但只能作为草稿材料：

```text
1. QA 素材必须有 scope、paper_ids、evidence_ids。
2. 生成正式综述时仍要回查 EvidenceRecord。
3. QA 素材不能绕过 ScopeGuard。
```

### 2.6 Token 成本调研落地

Token 调研给出关键结论：

```text
论文卡片比全文省约 10 倍 Token。
50-80 篇硕士文献综述需要分批处理。
博士 100-200 篇必须用 RAG 或分批摘要。
超过 20 篇论文要注意 Lost in the Middle。
```

综述生成的默认材料层级：

| 层级 | 内容 | 用途 |
| --- | --- | --- |
| L0 | 元数据 | 参考文献、年份趋势 |
| L1 | 摘要 | 大范围背景概览 |
| L2 | PaperCard | 主题、方法、发现、局限 |
| L3 | EvidenceRecord | 段落级证据和引用 |
| L4 | source_quote / chunk | 精确引用和细节补充 |
| L5 | 全文 | 默认不进入多篇综述生成 |

### 2.7 报告版本与导出计划落地

12 模块要求报告支持：

```text
Report
ReportVersion
ReportSourceIndex
ReportValidationResult
ExportPackage
```

综述生成模块必须给 ReportService 提供：

```text
section_sources
validation_result
references
source_index
export-ready markdown
```

## 3. 当前实现分析

### 3.1 已有能力

当前 `LiteratureReviewGenerator` 已有方法：

```text
generate(project_id, scope_payload, options=None)
collect_materials(scope)
_generate_with_llm(materials, options)
_build_evidence_text(evidence)
_build_cards_text(cards)
_render_review(result, materials)
_generate_fallback(materials)
validate_review(report)
```

当前优点：

| 能力 | 状态 |
| --- | --- |
| Scope 驱动 | 已通过 `RetrievalScopeService.resolve()` 收集材料 |
| 输入材料 | 已使用 evidence 和 paper_cards，不直接使用完整 PDF |
| LLM JSON | prompt 要求输出 background/topic/methods/findings/limitations/future_trends |
| Report 输出 | 已保存 report，包含 scope、paper_ids、evidence_ids |
| fallback | LLM 失败时能生成基础综述 |
| validate_review | 已有基础检查 |

### 3.2 当前关键问题

| 问题 | 当前表现 | 影响 | 优先级 |
| --- | --- | --- | --- |
| 测试可能触发真实 LLM | `LiteratureReviewGenerator()` 默认创建真实 LLM | 测试不稳定，依赖 API 环境 | P0 |
| 空 Scope 未强拒绝 | `generate()` 不检查 empty_reason | 可能生成空泛综述 | P0 |
| 材料组织粗糙 | evidence/cards 简单列表 | 无法形成高质量主题脉络 | P0 |
| 无 Evidence Matrix | 没有按 paper/topic/method/year 结构化 | prompt 噪声高，校验困难 | P0 |
| 章节来源缺失 | 只有报告级 evidence_ids | 无法段落级/章节级追溯 | P0 |
| LLM 输出 schema 弱 | 输出不含 section evidence_ids | 无法校验每节来源 | P0 |
| 引用格式弱 | 参考文献从 card title 简单拼接 | 缺 authors/year/venue/doi/url | P0 |
| ScopeGuard 缺失 | 报告引用不校验 scope | 可能引用范围外来源 | P0 |
| 长 Scope 无策略 | 固定截断 evidence 30、cards 20 | 大范围质量差，重要材料丢失 | P1 |
| validate_review 太弱 | 只检查 scope/paper/evidence 是否存在 | 不能发现空泛、越界、缺来源 | P0 |
| ReportService 未联动 | 直接 storage upsert | 缺版本、校验、导出索引一致性 | P1 |
| GraphContext 未使用 | collect_materials 不收图谱 | 主题/gap/路径组织能力弱 | P1 |

## 4. 主流综述做法与本项目选择

### 4.1 可借鉴做法

| 来源 | 可借鉴做法 | 本项目落地 |
| --- | --- | --- |
| PRISMA 2020 | 系统综述要透明说明检索、筛选、纳入和结果 | MVP 记录 scope、paper_count、evidence_count，P2 输出 PRISMA 风格范围说明 |
| Cochrane Handbook | 按研究问题、研究特征、风险/局限、结果综合组织 | Evidence Matrix + topic/method/finding/limitation 分组 |
| GRADE / Summary of Findings | 关键结论要有证据数量、确定性和限制 | P1/P2 展示 evidence_strength/certainty 和证据不足说明 |
| Covidence | 数据抽取先于综合写作 | 综述只从 EvidenceRecord/PaperCard 生成 |
| GraphRAG | 大范围先按主题/社区摘要再全局综合 | P1 长 Scope 按 topic/gap 分批生成 section drafts |
| 学术写作实践 | 围绕主题脉络、方法比较、研究不足组织 | 默认结构避免逐篇罗列 |

### 4.2 本项目不做什么

MVP 不做：

```text
完整系统综述平台。
完整元分析。
自动风险偏倚评估。
复杂 GRADE 自动判定。
Word/PDF 精排。
多人 reviewer/consensus 工作流。
```

MVP 必须做：

```text
Scope 边界。
证据矩阵。
章节级来源。
参考文献。
质量校验。
Markdown 报告。
```

## 5. 目标架构

### 5.1 服务职责拆分

当前可以继续放在 `review_generator.py`，但职责上应拆成：

```text
LiteratureReviewGenerator
  编排入口：resolve scope、收集材料、生成、校验、保存。

ReviewMaterialCollector
  收集 evidence、paper_cards、papers、graph_context、QA saved materials。

EvidenceMatrixBuilder
  构建按 paper/topic/method/year/type 组织的矩阵。

ReviewPlanner
  根据 review_type 和 scope 生成章节计划。

ReviewSectionGenerator
  逐章节生成，要求输出 section_sources。

ReviewRenderer
  渲染 Markdown、来源标记和参考文献。

ReviewValidator
  检查结构、来源、Scope 越界、空泛表达、参考文献覆盖。

ReviewBatcher
  长 Scope 分主题/分批生成 section drafts。
```

### 7.4 方法对比综述结构


### 7.5 Gap Review 结构

```text
1. 当前研究覆盖范围

```

## 8. 材料收集

### 8.1 collect_materials 规则

必须收集：

```text
scope summary
resolved paper_ids
resolved evidence_ids
Paper 元数据
PaperCard
EvidenceRecord
GraphContext
QA saved review materials
```

过滤规则：

```text
1. 只收 scope 内 paper/evidence。
2. excluded paper 不进入材料。
3. rejected evidence 默认不进入正文材料，可进入“排除证据/限制”诊断。
4. unknown、空文本、伪证据不进入 Evidence Matrix。
5. source_quote 缺失时可以使用，但要标记 needs_review_source。
```

### 8.2 兼容旧字段

当前 EvidenceRecord 没有 `claim/evidence_type/review_status`，综述生成需推断：

```text
finding 非空 -> finding evidence
limitation 非空 -> limitation evidence
future_work 非空 -> future_work evidence
method 非空 -> method evidence
data_or_sample 非空 -> dataset/sample evidence
review_status 缺失 -> pending
claim 缺失 -> 拼接 finding/limitation/future_work 等字段
```

### 8.3 参考文献材料

优先从 `papers` collection 获取：

```text
title
authors
year
venue
doi
url
source
```

fallback：

```text
paper_cards.title
paper_id
```

## 9. Evidence Matrix 与分组

### 9.1 分组维度

```text
topic
method
year
evidence_type
paper
gap / limitation
```

### 9.2 默认分组策略

```text
1. 先按 topic 分组。
2. topic 内按 method 分组。
3. method 内按 year 排序。
4. finding、limitation、future_work 单独拉出用于综合段落。
5. Gap 相关 evidence 用于研究不足和未来趋势。
```

### 9.3 去重规则

```text
同一 paper_id + normalized claim + evidence_type 只保留一条。
同一 source_quote 只保留一条。
同一章节引用同一 evidence 不重复显示。
```

### 9.4 Evidence Matrix 输出到 prompt

不要把完整 JSON 大对象塞给 LLM。应渲染为紧凑表格：

```text
paper_id | year | topic | method | finding | limitation | future_work | evidence_ids
p1 | 2024 | llm feedback | experiment | ... | ... | ... | ev1, ev2
```

## 10. 长 Scope 策略

### 10.1 阈值

```text
paper_count <= 20:
  single_pass，直接基于 Evidence Matrix 生成。

20 < paper_count <= 50:
  section_by_section，按章节生成，避免上下文拥挤。

50 < paper_count <= 100:
  topic_batch，按 topic 生成 section drafts，再合并。

paper_count > 100:
  graph/topic summaries + RAG top evidence，不直接生成全量综述。
```

### 10.2 Token 策略

```text
小范围：cards + evidence matrix + source quotes。
中范围：evidence matrix + cards 摘要 + top quotes。
大范围：topic summaries + method summaries + representative evidence。
超大范围：先生成分主题摘要，再请求用户确认或分批生成。
```

### 10.3 Lost in the Middle 处理

```text
1. 重要证据和输出 schema 放在 prompt 开头和结尾。
2. 每章只放相关 evidence。
3. 不把 50+ 篇卡片线性堆叠给单次 LLM。
4. 分主题生成后再全局合并。
```

## 11. Prompt 与结构化输出

### 11.1 System prompt 规则

必须强调：

```text
只能使用输入材料。
不得引用 Scope 外论文。
不得编造论文、作者、年份、结论。
每个主要章节必须返回 evidence_ids 和 paper_ids。
证据不足必须写入“本综述限制”。
冲突或不一致证据必须保留。
输出必须是 JSON。
```

### 11.2 LLM 输出 schema

```json
{
  "sections": [
    {
      "section_id": "methods",
      "title": "主要研究方法",
      "content": "段落正文",
      "paper_ids": ["p1", "p2"],
      "evidence_ids": ["ev1", "ev2"],
      "graph_node_ids": [],
      "uncertainty": ""
    }
  ],
  "overall_limitations": "本综述限制",
  "suggested_next_actions": ["expand_scope"],
  "missing_evidence": []
}
```

### 11.3 JSON 解析失败

如果 LLM 输出无法解析：

```text
1. 使用 fallback 生成结构化 Markdown。
2. section_sources 使用材料分组自动生成。
3. validation_result 写 json_parse_failed。
4. 不信任 LLM 自带引用。
```

### 11.4 fallback 规则

fallback 必须可追溯：

```text
主要发现：从 finding evidence 列表生成。
主要方法：从 method/data_or_sample 证据生成。
研究不足：从 limitation/future_work 证据生成。
未来趋势：从 future_work/gap 证据生成。
每个 bullet 后附 evidence_id。
```

## 12. 渲染与引用

### 12.1 Markdown 渲染

每个章节保留来源标记：

```markdown
## 主要研究方法

段落内容。[证据: ev1, ev2；论文: p1, p2]
```

正文引用策略：

```text
P0：章节末尾统一列 evidence_ids。
P1：段落级 evidence_ids。
P2：句子级引用和标准引用格式。
```

### 12.2 参考文献

P0 简化格式：

```text
- [p1] Authors (Year). Title. Venue. DOI/URL
```

P1 支持：

```text
APA
GB/T 7714
BibTeX
```

### 12.3 来源索引

报告末尾可追加：

```text
## 来源索引

### 使用论文
- [p1] ...

### 使用证据
- [ev1] p1 | finding | source_chunk_id | quote...

### 使用图谱节点
- [topic:abc] Topic: ...
```

来源索引可由 ReportService 导出时追加，综述生成至少要提供数据。

## 13. 质量校验

### 13.1 validate_review 增强

检查：

```text
结构完整性：必需章节是否存在。
来源覆盖率：主要章节是否有 evidence_ids。
Scope 校验：paper_ids/evidence_ids 是否都属于 scope。
引用存在性：正文或 section_sources 中的 id 是否存在。
空泛表达：检测“许多研究”“大量文献”“普遍认为”等无来源表达。
证据不足：少于阈值时是否写 limitation。
参考文献覆盖：使用论文是否在参考文献中出现。
重复内容：章节是否高度重复。
长度合理性：是否明显过短或过长。
```

### 13.2 Validation result

```json
{
  "valid": false,
  "score": 0.72,
  "issues": [
    {"type": "missing_section_sources", "section_id": "methods"}
  ],
  "warnings": [],
  "source_coverage": 0.85,
  "scope_violations": [],
  "generic_text_hits": ["大量研究表明"],
  "reference_coverage": 0.9
}
```

### 13.3 质量门槛

MVP：

```text
source_coverage >= 0.8
scope_violations == 0
required_sections_present == true
reference_coverage >= 0.8
generic_text_hits <= 3
```

## 18. 开发阶段

### R0：测试稳定与依赖注入

目标：让综述生成可测试，不依赖真实 LLM。

任务：

```text

```

验收：

```text
无 OPENAI_API_KEY 环境下测试稳定。
fallback 报告包含 evidence_ids 或限制说明。
```

### R1：Scope 安全与材料收集

目标：先保证不越界、不空写。

任务：

```text
R1.1 generate 检查 scope.empty_reason。
R1.2 collect_materials 只收 scope 内 paper/evidence。

```

验收：

```text
空 scope 不生成虚假综述。
Scope 外 evidence 不进入 materials。
references 来自 papers 元数据。
```

### R2：Evidence Matrix 与 ReviewPlan

目标：把材料从简单拼接升级为结构化组织。

任务：

```text

R2.3 去除 unknown/空/伪证据。

```

验收：

```text

```

### R3：章节级生成与来源索引

目标：让每个章节可追溯。

任务：


验收：

```text
Markdown 章节后有来源标记。
```

### R4：质量校验与引用格式


不要优先做：

## 22. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 综述幻觉 | 写出无证据结论 | section_sources + validate_review |
| Scope 越界 | 引用范围外论文 | ScopeGuard |
| 空泛表达 | “大量研究表明”无来源 | generic phrase 检测 |
| 长上下文失效 | 50 篇以上材料被忽略 | topic_batch / section_by_section |
| 参考文献不完整 | 只列 paper_id | 从 papers 元数据格式化 |
| 测试不稳定 | 真实 LLM 调用 | FakeLLM 注入 |
| 报告不可复现 | 没有 scope/material snapshot | Report metadata 保存 scope 和 source_index |
| 图谱误用 | 把路径当事实 | 图谱只组织，事实引用 evidence |
