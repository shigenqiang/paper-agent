# 10-综述生成模块专项开发计划

更新时间：2026-06-05

本文档基于 `docs/research` 下的产品方案、当前开发计划、证据表计划、知识图谱计划、RetrievalScope 计划、Scope QA/RAG 计划、报告版本与导出计划、Token 成本分析和当前代码实现，重新细化综述生成模块的开发方案。

综述生成模块负责把 Scope 内的论文卡片、证据表和图谱上下文组织成可交付的文献综述。它不是"让 LLM 直接写一篇综述"，而是一个有材料收集、证据矩阵、章节生成、引用渲染、来源校验和报告保存的成果生成管线。它必须遵守证据边界：不直接拿全文拼接，不引用 Scope 外论文，不写无来源的泛化结论。

对应代码：

```text

src/agents_v3/research_workspace/models.py

```



## 1. 模块定位

### 1.1 在产品链路中的位置

产品主线：

```text
研究项目
  -> 论文库
  -> PDF 解析与分块
  -> 论文卡片
  -> 证据表
  -> 知识图谱
  -> Retrieval Scope
  -> Scope-based QA
  -> 文献综述
  -> 创新点报告
```

综述生成位于 QA 探索之后、正式报告输出阶段。用户可以直接基于 Scope 生成综述，也可以先通过 QA 保存若干综述素材，再生成或补充综述。但最终报告必须重新绑定 Scope、paper_ids、evidence_ids 和 section_sources，不能只保存一段自然语言。

### 1.2 一句话目标

基于 Scope 内的结构化证据生成有章节、有引用、有来源索引、有质量校验、可版本化的文献综述报告。

### 1.3 核心原则

```text
1. Scope 是硬边界。
2. EvidenceRecord 是事实层。
3. PaperCard 是结构化摘要层。
4. KnowledgeGraph 是组织和解释关系的辅助层。
5. 每个主要章节必须尽量绑定 evidence_ids。
6. 证据不足时写限制，不扩写。
7. 长 Scope 必须分组、分批或摘要，不能一股脑塞入 prompt。
8. Report 必须保存 scope、paper_ids、evidence_ids、section_sources 和 validation_result。
```

## 2. 本地调研结论落地

### 2.1 产品方案落地

`当前产品方案.md` 要求文献综述基于选定 Scope、论文卡片、证据表和图谱上下文生成，默认结构包括：

```text
研究背景
主题划分
代表性文献和研究脉络
主要研究方法
主要研究结论
现有研究不足
未来研究趋势
参考文献
```

因此综述生成模块必须输出：

```text
1. 正文 Markdown。
2. 使用范围说明。
3. 使用论文列表。
4. 使用证据列表。
5. 章节级来源索引。
6. 参考文献。
7. 质量校验结果。
```

### 2.2 RetrievalScope 计划落地

08 模块要求 Scope 解析为：

```text
paper_ids
evidence_ids
graph_node_ids
graph_edge_ids
summary
empty_reason
explain
ScopeGuard
```

综述生成入口必须固定为：

```text
scope_payload
  -> RetrievalScopeService.resolve()
  -> ScopeGuard
  -> collect_materials()
  -> build_evidence_matrix()
  -> generate section drafts
  -> validate section sources
  -> render report
  -> save report/version
```

### 2.3 证据表计划落地

06 证据表模块强调：

```text
EvidenceRecord 是 QA、知识图谱、综述生成、创新点生成的事实层。
unknown、空字符串、模板占位文本不应进入 evidence_records。
QA 和报告生成应优先使用 accepted 或 traceable 的 evidence。
```

当前 `EvidenceRecord` 仍是旧字段：

```text
topic
research_question
method
data_or_sample
finding
limitation
future_work
evidence_strength
citation_context
source_chunk_id
source_quote
```

综述生成必须兼容旧字段，同时为未来字段预留：

```text
evidence_type
claim
review_status
evidence_relation
certainty
```

### 2.4 知识图谱计划落地

07 知识图谱模块要求 Topic、Method、Dataset、Finding、Limitation、Gap 等节点可追溯到 evidence。综述生成可以使用图谱做：

```text
1. 主题分组。
2. 方法分组。
3. Gap/局限聚合。
4. 图谱路径说明研究脉络。
5. 大范围下的 Topic/Gap summary。
```

但规则是：

```text
图谱用于组织和解释。
综述事实仍必须引用 EvidenceRecord 或 PaperCard。
```

### 2.5 Scope QA/RAG 计划落地

09 模块要求 QA 回答可保存为：

```text
review_material
innovation_material
evidence_note
```

综述生成可以读取已保存 QA 素材，但只能作为草稿材料：

```text
1. QA 素材必须有 scope、paper_ids、evidence_ids。
2. 生成正式综述时仍要回查 EvidenceRecord。
3. QA 素材不能绕过 ScopeGuard。
```

### 2.6 Token 成本调研落地

Token 调研给出关键结论：

```text
论文卡片比全文省约 10 倍 Token。
50-80 篇硕士文献综述需要分批处理。
博士 100-200 篇必须用 RAG 或分批摘要。
超过 20 篇论文要注意 Lost in the Middle。
```

综述生成的默认材料层级：

| 层级 | 内容 | 用途 |
| --- | --- | --- |
| L0 | 元数据 | 参考文献、年份趋势 |
| L1 | 摘要 | 大范围背景概览 |
| L2 | PaperCard | 主题、方法、发现、局限 |
| L3 | EvidenceRecord | 段落级证据和引用 |
| L4 | source_quote / chunk | 精确引用和细节补充 |
| L5 | 全文 | 默认不进入多篇综述生成 |

### 2.7 报告版本与导出计划落地

12 模块要求报告支持：

```text
Report
ReportVersion
ReportSourceIndex
ReportValidationResult
ExportPackage
```

综述生成模块必须给 ReportService 提供：

```text
section_sources
validation_result
references
source_index
export-ready markdown
```

## 3. 主流综述做法与本项目选择

### 3.1 可借鉴做法

| 来源 | 可借鉴做法 | 本项目落地 |
| --- | --- | --- |
| PRISMA 2020 | 系统综述要透明说明检索、筛选、纳入和结果 | MVP 记录 scope、paper_count、evidence_count，P2 输出 PRISMA 风格范围说明 |
| Cochrane Handbook | 按研究问题、研究特征、风险/局限、结果综合组织 | Evidence Matrix + topic/method/finding/limitation 分组 |
| GRADE / Summary of Findings | 关键结论要有证据数量、确定性和限制 | P1/P2 展示 evidence_strength/certainty 和证据不足说明 |
| Covidence | 数据抽取先于综合写作 | 综述只从 EvidenceRecord/PaperCard 生成 |
| GraphRAG | 大范围先按主题/社区摘要再全局综合 | P1 长 Scope 按 topic/gap 分批生成 section drafts |
| GPT-Researcher | Review-Revise 审核修订循环、上下文压缩 | P1 增加 Reviewer→Revisor 流程，长 Scope 按 topic 分组压缩 |
| 学术写作实践 | 围绕主题脉络、方法比较、研究不足组织 | 默认结构避免逐篇罗列 |

### 3.2 本项目不做什么

MVP 不做：

```text
完整系统综述平台。
完整元分析。
自动风险偏倚评估。
复杂 GRADE 自动判定。
Word/PDF 精排。
多人 reviewer/consensus 工作流。
```

MVP 必须做：

```text
Scope 边界。
证据矩阵。
章节级来源。
参考文献。
质量校验。
Markdown 报告。
```

## 4. 目标架构

### 4.1 服务职责拆分

当前可以继续放在 `review_generator.py`，但职责上应拆成：

```text
LiteratureReviewGenerator
  编排入口：resolve scope、收集材料、生成、校验、保存。

ReviewMaterialCollector
  收集 evidence、paper_cards、papers、graph_context、QA saved materials。

EvidenceMatrixBuilder
  构建按 paper/topic/method/year/type 组织的矩阵。

ReviewPlanner
  根据 review_type 和 scope 生成章节计划。

ReviewSectionGenerator
  逐章节生成，要求输出 section_sources。

ReviewRenderer
  渲染 Markdown、来源标记和参考文献。

ReviewValidator
  检查结构、来源、Scope 越界、空泛表达、参考文献覆盖。

ReviewBatcher
  长 Scope 分主题/分批生成 section drafts。

ReviewReviewerAgent
  审核综述初稿，检查逻辑连贯性、证据覆盖、空泛表达、章节重复。

ReviewReviserAgent
  根据审核意见修订综述。
```

## 7. 材料收集

### 7.1 collect_materials 规则

必须收集：

```text
scope summary
resolved paper_ids
resolved evidence_ids
Paper 元数据
PaperCard
EvidenceRecord
GraphContext
QA saved review materials
```

过滤规则：

```text
1. 只收 scope 内 paper/evidence。
2. excluded paper 不进入材料。
3. rejected evidence 默认不进入正文材料，可进入"排除证据/限制"诊断。
4. unknown、空文本、伪证据不进入 Evidence Matrix。
5. source_quote 缺失时可以使用，但要标记 needs_review_source。
```

### 7.2 兼容旧字段

当前 EvidenceRecord 没有 `claim/evidence_type/review_status`，综述生成需推断：

```text
finding 非空 -> finding evidence
limitation 非空 -> limitation evidence
future_work 非空 -> future_work evidence
method 非空 -> method evidence
data_or_sample 非空 -> dataset/sample evidence
review_status 缺失 -> pending
claim 缺失 -> 拼接 finding/limitation/future_work 等字段
```

### 7.3 参考文献材料

优先从 `papers` collection 获取：

```text
title
authors
year
venue
doi
url
source
```

fallback：

```text
paper_cards.title
paper_id
```

## 8. Evidence Matrix 与分组

### 8.1 分组维度

```text
topic
method
year
evidence_type
paper
gap / limitation
```

### 8.2 默认分组策略

```text
1. 先按 topic 分组。
2. topic 内按 method 分组。
3. method 内按 year 排序。
4. finding、limitation、future_work 单独拉出用于综合段落。
5. Gap 相关 evidence 用于研究不足和未来趋势。
```

### 8.3 去重规则

```text
同一 paper_id + normalized claim + evidence_type 只保留一条。
同一 source_quote 只保留一条。
同一章节引用同一 evidence 不重复显示。
```

### 8.4 Evidence Matrix 输出到 prompt

不要把完整 JSON 大对象塞给 LLM。应渲染为紧凑表格：

```text
paper_id | year | topic | method | finding | limitation | future_work | evidence_ids
p1 | 2024 | llm feedback | experiment | ... | ... | ... | ev1, ev2
```

## 9. 长 Scope 策略

### 9.1 阈值

```text
paper_count <= 20:
  single_pass，直接基于 Evidence Matrix 生成。

20 < paper_count <= 50:
  section_by_section，按章节生成，避免上下文拥挤。

50 < paper_count <= 100:
  topic_batch，按 topic 生成 section drafts，再合并。

paper_count > 100:
  graph/topic summaries + RAG top evidence，不直接生成全量综述。
```

### 9.2 Token 策略

```text
小范围：cards + evidence matrix + source quotes。
中范围：evidence matrix + cards 摘要 + top quotes。
大范围：topic summaries + method summaries + representative evidence。
超大范围：先生成分主题摘要，再请求用户确认或分批生成。
```

### 9.3 Lost in the Middle 处理

```text
1. 重要证据和输出 schema 放在 prompt 开头和结尾。
2. 每章只放相关 evidence。
3. 不把 50+ 篇卡片线性堆叠给单次 LLM。
4. 分主题生成后再全局合并。
```

### 9.4 上下文压缩（GPT-Researcher 借鉴）

```text
当前：50 篇论文 → 截断到 30 条 evidence → 一次生成（丢失信息）
改进：50 篇论文 → 按 topic 分 5 组 → 每组生成摘要 → 基于 5 个摘要生成综述（不丢失）
```

实现方式：

```python
def _compress_by_topic(self, evidence: list, cards: list, max_per_topic: int = 5) -> str:
    """按 topic 分组压缩，每组生成摘要"""
    by_topic = defaultdict(list)
    for ev in evidence:
        by_topic[ev.topic].append(ev)

    summaries = []
    for topic, ev_list in by_topic.items():
        top_ev = ev_list[:max_per_topic]
        summary = f"主题:{topic} | 论文:{len(set(e.paper_id for e in top_ev))}篇 | "
        summary += f"发现:{'; '.join(e.finding[:50] for e in top_ev if e.finding)}"
        summaries.append(summary)

    return "\n".join(summaries)
```

触发条件：

```text
paper_count <= 20: single_pass
paper_count > 20: topic_compress（按 topic 压缩后生成）
paper_count > 50: section_by_section（按章节分批生成）
```

## 12. Review-Revise 审核修订循环

### 12.1 设计（GPT-Researcher 借鉴）

当前问题：综述生成是单次 LLM 调用，缺少质量把关环节。

GPT-Researcher 做法：

```text
Writer 写初稿 → Reviewer 审核 → Revisor 修订 → 最终输出
```

本项目适配方案：

```text
Evidence Matrix
  -> LLM 生成初稿 sections
  -> Reviewer Agent 审核（检查逻辑连贯性、证据覆盖、空泛表达、章节重复）
  -> LLM 修订（根据审核意见修改）
  -> validate_review
  -> 输出
```

### 12.2 Reviewer Agent 审核维度

```text
1. 逻辑连贯性：章节之间是否有逻辑衔接，是否存在矛盾
2. 证据覆盖：每个论断是否有 evidence_id 支撑
3. 空泛表达：是否使用"大量研究表明"等无来源套话
4. 章节重复：不同章节是否重复相同内容
5. 研究脉络：是否展示了研究演进和方法对比
6. 限制说明：证据不足时是否写了限制
```

### 12.3 实现方式

```python
class ReviewReviewerAgent:
    """审核综述初稿，输出审核意见"""

    def review(self, sections: list[dict], materials: dict) -> ReviewCritique:
        # 检查逻辑、证据、空泛、重复
        # 返回 issues + suggestions
        pass

class ReviewReviserAgent:
    """根据审核意见修订综述"""

    def revise(self, sections: list[dict], critique: ReviewCritique) -> list[dict]:
        # 根据 critique 修改 sections
        pass
```

集成到生成流程：

```python
def _generate_sections(self, materials, matrix, options):
    # 1. 初稿生成
    sections = self._generate_draft(materials, matrix)

    # 2. 审核（新增）
    if options.get("enable_review_revise", True):
        critique = self.reviewer.review(sections, materials)
        if critique.has_issues:
            sections = self.reviser.revise(sections, critique)

    return sections
```

### 12.4 审核意见写入 Report metadata

```json
{
  "review_critique": {
    "issues": [
      {"section_id": "methods", "type": "missing_evidence", "detail": "..."}
    ],
    "suggestions": ["增加方法对比段落"],
    "revision_rounds": 1
  }
}
```

## 21. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 综述幻觉 | 写出无证据结论 | section_sources + validate_review |
| Scope 越界 | 引用范围外论文 | ScopeGuard |
| 空泛表达 | "大量研究表明"无来源 | generic phrase 检测 |
| 长上下文失效 | 50 篇以上材料被忽略 | topic_batch / section_by_section |
| 参考文献不完整 | 只列 paper_id | 从 papers 元数据格式化 |
| 测试不稳定 | 真实 LLM 调用 | FakeLLM 注入 |
| 报告不可复现 | 没有 scope/material snapshot | Report metadata 保存 scope 和 source_index |
| 图谱误用 | 把路径当事实 | 图谱只组织，事实引用 evidence |
| graph_context 浪费 | 收集但不使用 | 传入 prompt 用于主题组织 |
| prompt 版本不可追踪 | 内联 prompt | 接入 PromptRegistry |
