# 模块总览与依赖关系

更新时间：2026-05-29

本目录是 `src/agents_v3/research_workspace` 的模块级专项开发计划集合。目标是把论文知识库分析 Agent 从“已有 service 雏形”推进到“可运行、可追溯、可测试、可前端联调”的产品级 MVP。

## 1. 总体主链路

```text
Project
  -> Paper Library / Search / Import / Upload
  -> PDF Parser / Chunk
  -> Paper Card
  -> Evidence Table
  -> Knowledge Graph
  -> Retrieval Scope
  -> Scope QA / RAG
  -> Literature Review
  -> Innovation Report
  -> Report Version / Export
```

支撑链路：

```text
Models / Storage
StorageBackend / PostgreSQL / VectorStorage
LLM Service / Prompt Schema
API / Task Progress
Evaluation / Logging / Monitoring
Frontend Integration
```

```text

12. ReportService

15. Evaluation + Logging + Monitoring
```

关键依赖：

```text
PaperCard 依赖 PaperChunk。
EvidenceRecord 依赖 PaperCard 和 SourceSpan。
KnowledgeGraph 依赖 EvidenceRecord。
RetrievalScope 依赖 Paper、EvidenceRecord 和 KnowledgeGraph。
ScopeQA、Review、Innovation 都依赖 resolved scope。
Report 必须记录 scope、paper_ids、evidence_ids、graph_node_ids。
Evaluation 必须覆盖 QA、Review、Innovation 和日志脱敏。
```

## 5. 主流做法落地映射

| 主流做法 | 本项目落地 |
| --- | --- |
| 系统综述工具的 extraction form | EvidenceTableSchema、EvidenceColumn、review_status |

| GraphRAG 的实体图谱和 local/global search | GraphService + related_evidence_ids + graph summaries |
| RAG 的 hybrid retrieval 和 faithfulness 评估 | EvidenceRetriever + ScopeGuard + golden QA |
| PRISMA/Cochrane/GRADE 的可追溯综述 | Evidence Matrix + section_sources + certainty 字段 |
| FastAPI/OpenAPI 的契约化 API | `/api/rw` router + Pydantic request/response |
| OpenTelemetry/LangSmith/Ragas 的评估监控 | structured logs + LLM metrics + evaluation.py |

## 6. 全局质量门禁

模块实现完成后，必须能证明：

```text
1. 从创建项目到报告导出全链路可运行。
2. 所有正式回答和报告都能追溯到 paper、evidence 或 graph node。
3. Scope 外内容不会进入 QA、综述或创新点报告。
4. unknown、伪证据、无来源强结论不会污染 evidence table。
5. PDF 解析失败、LLM 失败、搜索失败都有状态和日志。
6. 每个核心模块都有单元测试。
7. 端到端 smoke test 能稳定复现演示项目。
8. 日志不泄露 API key、完整 prompt、完整 PDF 文本。
9. 报告导出包含范围、论文、证据和版本信息。
10. 创新点必须有 gap、证据链、风险和可行性评分。
```

## 当前代码对齐深化（2026-05-29）

### 当前实现确认

```text
src/agents_v3/research_workspace 已从单层服务文件演进为“核心服务 + search/api/llm/evaluation 子包”的结构。
搜索链路已具备 SearchField、SearchOrchestrator、缓存、限流、去重、融合排序和多来源 adapter。
API 层已存在 FastAPI app、统一响应模型、错误处理、TaskService 和依赖注入。

Evaluation 层已拆分为 evaluator、gates、golden、metrics、logging_utils。
存储层已新增 StorageBackend、PostgresStorage、VectorStorage，但各业务 service 对 JSON/PostgreSQL 的语义尚未完全收敛。
```

### 下一步深化任务

```text
1. 先统一存储后端契约，避免 API、ProjectService、PaperLibraryService 在 JSON/PostgreSQL 下行为分叉。
2. 再把搜索、解析、卡片、证据、图谱、Scope、QA、报告链路接成可观测的端到端工作流。
3. 对所有 LLM 生成产物统一接入 invoke_structured、PromptRegistry、traceability validation 和 evaluation gates。
4. API 与前端联调以 /api/rw 为主边界，补齐搜索诊断、任务进度、错误码和报告导出契约。
5. 评估日志模块成为验收闭环：每个核心流程都能产出结构化指标、质量门禁结果和可复现 fixture。
```

### 当前最高优先级

```text
P0-1 StorageBackend 语义收敛：ProjectService update/delete/stats、PaperLibraryService、TaskService 在两类后端下结果一致。
P0-2 Search productization：API 返回 SearchResponse 的 source diagnostics、ranking score、dedup/merge 信息。
P0-3 Evidence trust chain：SourceSpan、EvidenceRecord、Graph edge、Report source_index 之间可追踪、可校验。
P0-4 Evaluation gate 接入主流程：QA、综述、创新点报告默认生成 validation_result。
```


### 风险与阻塞

```text
1. config.yaml 默认存储后端与本地服务状态不一致时，API smoke 和前端联调容易被 PostgreSQL/ChromaDB 环境阻塞。
2. 若 StorageBackend 契约不先收敛，后续模块会继续在 JSONStorage 与 PostgresStorage 之间产生行为差异。
3. ScopeGuard、EvidenceRecord、Graph edge、Report source_index 若字段口径不统一，QA/综述/创新点报告会出现越界引用或不可追踪来源。
4. 批量下载、解析、卡片、报告生成若不任务化，前端只能同步等待，失败也难以重试和定位。
5. LLM prompt/schema/version 若分散在业务模块内，质量评估和 golden regression 无法稳定判断退化来源。
```
