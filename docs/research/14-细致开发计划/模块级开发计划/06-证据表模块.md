## 0. 与产品方案的关联

证据表模块是产品主线的核心中间层：

```text
论文入库 -> 论文解析 -> 论文卡片
  -> 证据表 ← 本模块
  -> 知识图谱
  -> Scope QA
  -> 文献综述
  -> 创新点报告
```

证据表是 QA、综述和创新点的”事实底座”。借鉴产品方案中的以下技术：

| 借鉴来源 | 在证据表模块的应用 |
| --- | --- |
| Elicit Columns | 以”论文表格 + 自定义列”组织抽取，99.4% 提取准确率 |
| Consensus Claims & Evidence Table | 每个 AI 总结绑定真实论文，Consensus Meter 汇总立场 |
| Scite | 证据关系区分 supporting/contradicting/mentioning |
| Covidence Extraction | AI suggestion + accept/reject，双人审核与 consensus |
| Cochrane/GRADE | Summary of Findings 表按 outcome 展示 certainty |
| PRISMA-trAIce | 透明报告检查清单，记录 AI 辅助决策 |
| PapersFlow | Critic Agent 反证检测，Chain of Verification |
| LettuceDetect | 幻觉检测：证据表质量直接影响 QA 幻觉率 |

### 1.1 当前已有能力

### 1.2 当前主要缺口

| 领域 | 当前状态 | 问题 | 产品方案要求 |
| --- | --- | --- | --- |
| 证据类型 | finding/limitation/future_work 依赖空字段区分 | 不利于筛选、排序、图谱建边和导出 | evidence_type 枚举 |
| 主张表达 | finding/limitation 分散在不同字段 | 缺少统一 `claim` 字段，QA 很难统一引用 | claim 统一字段 |
| 证据方向 | 无 | 不能表达 supporting/contradicting/mentioning | evidence_direction（借鉴 Scite） |
| 共识水平 | 无 | 不能表达多论文结论的共识程度 | consensus_level（借鉴 Consensus） |
| 来源追溯 | finding 只按 index 粗略绑定 `source_spans` | limitation/future_work/gap 基本无 source span | source_spans 多片段 |
| 引文校验 | 未验证 `source_quote` 是否真实存在于 chunk | 后续 QA 可能引用不可靠文本 | quote 校验 |
| 证据强度 | 默认为 medium | 没有基于来源、章节、quote 匹配、card confidence 的评分 | 规则评分 |
| 审核状态 | 无 | 无法区分 AI 建议、人工确认、拒绝、待复核 | review_status |
| 去重合并 | ⚠️ build_for_project 重复运行产生重复记录 | 同一论文重复 finding 会产生重复记录 | 幂等 upsert |
| 伪证据 | ⚠️ 无证据时生成 "No specific findings extracted" | 污染 QA、图谱和综述 | 不生成伪证据 |
| 冲突证据 | 无 | 不能表达支持、反驳、限定、混合结论 | contradicting_evidence_ids |
| 结构化列 | 无 | 不能像主流工具一样按项目配置抽取字段 | EvidenceTableSchema |
| 导出 | 无 | 难以输出给 CSV、Markdown、综述表格或人工复核 | CSV/Markdown/JSON |
| 覆盖率 | 无 | 不知道哪些论文、主题、问题缺证据 | coverage report |

### 1.3 当前实现中需要立即修正的行为

当前 `_card_to_evidence()` 在没有生成任何证据时会创建：

```text
finding = "No specific findings extracted"
evidence_strength = "low"
```

生产逻辑中不应生成这种伪证据。它会污染 QA、图谱和综述。后续应改为：

```text
没有可用 evidence -> 不生成 EvidenceRecord
同时写入 coverage/validation 报告：
  paper_id
  missing_fields
  reason
  suggested_action
```

## 2. 主流产品和系统做法

### 2.1 调研参考

本计划参考了以下主流产品/方法的公开资料：

| 来源 | 可借鉴做法 |
| --- | --- |
| Elicit Columns | 以“论文表格 + 自定义列”组织抽取；每个列有名称、说明、答案格式；支持预设列、选择题、Yes/No/Maybe、导出 |
| Covidence Extraction 1/2 | 系统综述的数据抽取模板；支持 PICO(T)、自定义表单、PDF 左侧阅读 + 右侧抽取、AI suggestion 需要接受/拒绝、双人审核与 consensus |
| Rayyan | 用标签、排除理由、PICO 高亮/过滤、Include/Maybe/Exclude 决策管理筛选与复核 |
| DistillerSR | 强调可配置表单、标准化答案集、AI-assisted extraction、human-in-the-loop、审计追踪、版本控制和证据复用 |
| scite | 将证据关系区分为 supporting、contrasting、mentioning，并保留 citation context、章节和分类置信度 |
| Consensus | 每个 AI 总结要绑定真实论文；Study Snapshot 抽取 population、sample size、method、outcome、results；Consensus Meter 汇总 yes/no/possibly/mixed 立场 |
| Cochrane/GRADE | Summary of Findings 表按 outcome 展示 effect、样本/研究数量、certainty；GRADE 区分 high/moderate/low/very low，并给出降级原因 |

### 2.2 主流产品共性

主流工具不是把证据当成“自然语言摘要列表”，而是当成“可追踪的数据抽取表”：

```text
论文/全文 -> 项目级抽取模板 -> 每篇论文的字段值 -> 来源片段/引用 -> 审核状态 -> 汇总表/报告/导出
```

共性设计：

| 设计点 | 主流做法 | 本项目落地 |
| --- | --- | --- |
| 抽取列可配置 | Elicit/Covidence/DistillerSR 都支持按项目定义字段 | 增加 `EvidenceTableSchema` 和 `EvidenceColumn` |
| 来源必须可追溯 | Elicit/Covidence/scite/Consensus 都强调来源文本或引用 | 每条 evidence 必须尽量绑定 `source_spans` 和 quote 校验结果 |
| AI 只是建议 | Covidence/DistillerSR 采用 suggestion + accept/reject | 默认 `review_status=pending`，人工确认后才进入高信任输出 |
| 审核状态显式化 | Covidence/Rayyan 有 reviewer/consensus/decision | 增加 pending/accepted/rejected/needs_review/conflict |
| 冲突和立场可表达 | scite/Consensus 表达 supporting/contrasting/mixed | 增加 `evidence_relation` 与 `contradicting_evidence_ids` |
| 结构化评估 | Cochrane/GRADE 按 outcome 评估 certainty | 区分单条 `evidence_strength` 和证据组 `certainty` |
| 筛选和分面 | Rayyan 支持 PICO、标签、理由、排序 | query 支持 topic/method/outcome/type/status/strength 等分面 |
| 审计和导出 | DistillerSR/Covidence 支持审计、CSV/RevMan 等导出 | 增加 audit events、CSV/Markdown/JSON 导出 |

### 2.3 对本项目最重要的结论

第一阶段不要追求完整的系统综述平台，但必须先打好证据层：

```text
1. 每条证据要有统一 claim 字段。
2. 每条证据要有 evidence_type。
3. 每条证据要尽量有 source_span，并能校验 quote。
4. AI 生成的证据默认 pending，不能默认当作事实。
5. 查询必须支持 Scope，不能越过用户指定范围。
6. 证据强度和 GRADE certainty 是两个概念，不能混用。
7. 伪证据和 unknown 字段不能进入 evidence_records。
```

## 3. 模块目标

### 3.1 一句话目标

把论文卡片、PDF 分块和人工审核结果统一转成可追溯、可筛选、可复用的项目级证据表。

### 3.2 MVP 成功标准

第一阶段完成后，必须满足：

```text
1. 每条 EvidenceRecord 都有 project_id、paper_id、evidence_type、claim。
2. finding、limitation、future_work、gap、method、dataset/sample 可生成不同 evidence_type。
3. unknown、空字符串、模板占位文本不生成证据。
4. 每条 evidence 尽量绑定 source_span；无法绑定则标记 needs_review。
5. source_quote 能通过 chunk 文本校验，校验失败要出现在 validation report。
6. 支持按 Scope 查询，不能返回 scope 外的 paper/topic/method evidence。
7. 支持 evidence_type、review_status、strength、topic、method、year、keyword 过滤。
8. 支持去重：同一 paper/type/normalized claim 不重复入库。
9. 支持人工审核状态：pending、accepted、rejected、needs_review。
10. 支持 CSV、Markdown、JSON 导出。
11. QA 和报告生成只能优先使用 accepted 或 traceable 的 evidence。
```

### 3.3 暂不做

第一阶段不做以下内容：

```text
1. 完整元分析和统计合并。
2. 完整 GRADE 自动判定。
3. 多 reviewer 复杂权限系统。
4. 图形化 Evidence Table 前端编辑器。
5. 商业系统综述工具级别的 RevMan 双向同步。
6. 自动判定论文质量的复杂 risk-of-bias 工具。
```

但数据模型要为这些能力预留字段。

### 4.3 模块边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |

### 5.2 SourceSpan 扩展

当前 `SourceSpan` 只有：

```text
field
chunk_id
quote
```

建议扩展为：

```python
class EvidenceSourceSpan(BaseModel):
    field: str = ""
    chunk_id: str = ""
    quote: str = ""
    section_title: str = ""
    page_start: int | None = None
    page_end: int | None = None
    start_char: int | None = None
    end_char: int | None = None
    quote_match_score: float = 0.0
    quote_match_status: str = "unchecked"  # unchecked / matched / fuzzy_matched / missing / failed
```

处理原则：

```text
1. 兼容旧的 SourceSpan，读旧数据时转成 EvidenceSourceSpan。
2. 如果只有 chunk_id 没有 quote，允许生成 evidence，但 review_status=needs_review。
3. 如果 quote 不在 chunk text 中，evidence_strength 不能是 high。
```

## 6. 证据生成规则

### 6.1 从 PaperCard 生成 EvidenceRecord

基础规则：

| PaperCard 字段 | EvidenceType | claim 来源 | 兼容字段 |
| --- | --- | --- | --- |
| `key_findings[]` | finding | 每个 finding 单独一条 | `finding` |
| `limitations[]` | limitation | 每个 limitation 单独一条 | `limitation` |
| `future_work[]` | future_work | 每个 future_work 单独一条 | `future_work` |
| `possible_gaps[]` | gap | 每个 gap 单独一条 | metadata 或 gap 字段 |
| `method` | method | 非 unknown 时一条 | `method` |
| `data_or_sample` | sample | 非 unknown 时一条 | `data_or_sample` |

不生成 evidence 的值：

```text
""
"unknown"
"N/A"
"not mentioned"
"No specific findings extracted"
长度小于 4 且无语义的碎片
模板占位文本
```

### 6.2 source_span 绑定规则

绑定优先级：

```text
1. 精确 field 匹配：source_spans[].field == 当前字段名
2. quote 与 claim 文本重叠最高的 span
3. 同一字段多个 span 时保留全部，并把最高分 span 写入 source_chunk_id/source_quote
4. 没有字段匹配时，尝试在 PaperChunk 中用 claim 关键词检索
5. 仍找不到时生成 evidence，但 review_status=needs_review，evidence_strength=low
```

字段映射：

| 证据类型 | 优先匹配 source_spans.field |
| --- | --- |
| finding | `key_findings`, `finding`, `results`, `discussion`, `conclusion` |
| limitation | `limitations`, `limitation`, `discussion`, `threats_to_validity` |
| future_work | `future_work`, `conclusion`, `discussion` |
| gap | `possible_gaps`, `future_work`, `limitations`, `discussion` |
| method | `method`, `methods`, `experiment`, `study_design` |
| sample | `data_or_sample`, `dataset`, `participants`, `sample`, `data` |

### 6.3 quote 校验规则

新增 `validate_evidence_traceability(project_id)`：

```text
输入：project_id
读取：evidence_records + paper_chunks
输出：EvidenceValidationReport
```

校验项：

| 校验项 | 通过标准 | 失败处理 |
| --- | --- | --- |
| paper 存在 | `paper_id` 可查到 | 标记 invalid_paper |
| chunk 存在 | `source_chunk_id` 可查到 | 标记 missing_chunk |
| quote 存在 | quote 在 chunk.text 中精确匹配 | matched |
| quote 模糊匹配 | 相似度达到阈值 | fuzzy_matched |
| quote 缺失 | 无 quote 但有 chunk | needs_review |
| source 必需 | finding/limitation/gap 应有 source | 降低 strength |

建议阈值：

```text
exact match: 1.0
fuzzy match: >= 0.82
weak match: 0.65 - 0.82
failed: < 0.65
```

### 6.4 去重和合并规则

去重 key：

```text
project_id + paper_id + evidence_type + normalized_claim
```

`normalized_claim` 规则：

```text
1. lowercase
2. 去除首尾空白
3. 压缩连续空白
4. 去除末尾句号、分号
5. 统一百分号、数字空格、常见连字符
6. 可选：中英文全角半角归一
```

重复处理：

| 情况 | 处理 |
| --- | --- |
| 完全重复 | 不新增，更新 `updated_at` 和 metadata |
| claim 相同但 source 不同 | 合并 `source_spans` |
| claim 相近但不完全相同 | 标记 `possible_duplicate`，不自动合并 |
| 不同 evidence_type | 不合并 |

## 7. 证据强度和确定性

### 7.1 区分两个概念

| 概念 | 作用 | 粒度 |
| --- | --- | --- |
| `evidence_strength` | 这条证据本身是否可追溯、是否可靠抽取 | 单条 EvidenceRecord |
| `certainty` | 一组证据对某个 outcome/claim 的总体确定性 | evidence group / outcome |

第一阶段只实现 `evidence_strength` 自动规则，`certainty` 先保留字段，默认为 `not_assessed`。

### 7.2 evidence_strength 评分规则

建议先采用规则评分，不引入模型打分：

```text
base = 0
+2 有 source_chunk_id
+2 有 source_quote
+2 quote exact/fuzzy matched
+1 来自 Results/Findings/Discussion/Conclusion/Methods 等可信章节
+1 card.confidence >= 0.7
+1 review_status == accepted
-2 quote 校验失败
-2 source 缺失但 source_required
-1 extraction_method == fallback
-1 claim 太短或过泛
```

映射：

```text
score >= 6 -> high
score 3-5 -> medium
score <= 2 -> low
```

强制降级：

```text
quote_match_status == failed -> 最高 medium
source_chunk_id 为空 -> 最高 low
review_status == rejected -> 不参与查询默认结果
claim 包含 unknown/template placeholder -> 不入库
```

### 7.3 certainty 预留规则

后续借鉴 GRADE：

| 维度 | 字段建议 |
| --- | --- |
| risk of bias | `certainty_reasons` 中记录研究设计/偏倚 |
| inconsistency | 多篇论文结论是否冲突 |
| indirectness | 样本/场景是否偏离项目研究问题 |
| imprecision | 样本量、置信区间、效果大小是否不足 |
| publication bias | 是否只来自少数同源论文 |

第一阶段不自动给出 high/moderate/low，只允许人工或后续聚合服务写入。

## 8. 查询、筛选和排序

### 8.1 EvidenceQuery

新增查询对象，替代任意 dict 拼接：

```python
class EvidenceQuery(BaseModel):
    project_id: str
    paper_ids: list[str] = Field(default_factory=list)
    evidence_ids: list[str] = Field(default_factory=list)
    evidence_types: list[EvidenceType] = Field(default_factory=list)
    topics: list[str] = Field(default_factory=list)
    methods: list[str] = Field(default_factory=list)
    outcomes: list[str] = Field(default_factory=list)
    review_statuses: list[EvidenceReviewStatus] = Field(default_factory=list)
    strengths: list[EvidenceStrength] = Field(default_factory=list)
    keyword: str = ""
    year_from: int | None = None
    year_to: int | None = None
    source_required: bool | None = None
    scope: dict[str, Any] = Field(default_factory=dict)
    sort_by: str = "relevance"
    limit: int = 100
    offset: int = 0
```

### 8.2 必须支持的过滤项

| 过滤项 | 用途 |
| --- | --- |
| project_id | 项目隔离 |
| paper_ids | 选定论文范围 |
| evidence_type | finding/limitation/gap/method 等 |
| topic | 主题综述 |
| method | 方法对比 |
| outcome | 结果/指标对比 |
| review_status | 人工审核队列 |
| evidence_strength | QA 优先使用高质量证据 |
| source_section | 只看 Results/Discussion/Methods |
| keyword | claim/source_quote/citation_context 检索 |
| year_range | 时间趋势 |
| relation | supports/contradicts/mixed |

### 8.3 排序规则

第一阶段排序：

```text
1. accepted > pending > needs_review > rejected
2. high > medium > low
3. quote matched > fuzzy matched > missing > failed
4. 与 keyword/topic 的文本匹配分
5. 新论文优先或年份倒序
```

后续排序：

```text
1. 论文质量分
2. citation_count
3. 来源章节权重
4. 多篇论文共同支持程度
5. 与当前 RetrievalScope 的图谱距离
```

### 8.4 Scope 查询约束

`query_by_scope(scope)` 必须遵守：

```text
1. scope.project_id 是硬边界。
2. scope.paper_ids 非空时，只返回这些 paper。
3. scope.evidence_ids 非空时，只返回这些 evidence。
4. scope.topic_ids 非空时，只返回 topic 命中的 evidence。
5. scope.method_ids 非空时，只返回 method 命中的 evidence。
6. scope.time_range 非空时，需要结合 Paper.year 过滤。
7. graph_node_ids/graph_edge_ids 后续通过 supports_graph_node_ids / supports_graph_edge_ids 过滤。
```

不得出现：

```text
scope 外的 evidence 被 QA 或报告引用。
rejected evidence 被默认结果返回。
低强度 evidence 在没有说明的情况下被当作核心结论。
```

## 11. 与其他模块集成

### 11.1 与 PDF 解析/分块模块

需要上游提供：

```text
chunk_id
paper_id
section_title
text
start_char
end_char
page_start/page_end（后续）
```

证据表依赖这些字段做 quote 校验和章节权重。

### 11.2 与论文卡片生成模块

PaperCard 生成时必须遵守：

```text
1. source_spans.field 要能映射到 key_findings/limitations/future_work/method/data_or_sample。
2. 每个 key_findings 尽量有对应 quote。
3. 不确定字段写 unknown，但 EvidenceTable 不会为 unknown 生成证据。
4. confidence 需要写入，供 evidence_strength 使用。
```

### 11.3 与 QA 模块

QA 检索规则：

```text
1. 优先 accepted + high/medium evidence。
2. pending evidence 可用于补充，但答案必须说明“未人工确认”。
3. rejected evidence 不参与默认回答。
4. needs_review evidence 只在证据不足时作为弱证据，并进入 uncertainty。
5. 回答必须返回 evidence_ids 和 supporting_papers。
```

QA 的拒答/不确定性：

```text
如果 scope 内没有足够 accepted/traceable evidence：
  不要编造答案
  返回 uncertainty
  建议用户补充 PDF、扩大 scope 或审核 pending evidence
```

### 11.4 与知识图谱模块

映射关系：

| EvidenceType | GraphNode | EdgeType |
| --- | --- | --- |
| finding | Finding | REPORTS_FINDING |
| limitation | Limitation | HAS_LIMITATION |
| gap | Gap | SUGGESTS_GAP |
| method | Method | USES_METHOD |
| dataset/sample | Dataset | USES_DATASET |

每个图谱节点/边应能回链：

```text
evidence_id -> paper_id -> source_chunk_id/source_quote
```

### 11.5 与综述生成模块

综述生成不应直接读取 PaperCard 拼段落，而应读取：

```text
accepted evidence
high/medium strength evidence
grouped by topic/method/outcome/year
with contradictory evidence and limitations
```

生成综述时必须保留：

```text
evidence_ids
paper_ids
source_quote/citation context
uncertainty notes
```

### 11.6 与创新点模块

创新点模块重点使用：

```text
gap evidence
limitation evidence
future_work evidence
contradictory evidence
low-coverage topic report
```

创新点输出必须能说明：

```text
这个 gap 来自哪些论文？
它是作者明确提出的 future work，还是系统从 limitation 推断的？
有没有相反证据？
证据强度如何？
```

## 15. 质量门禁

### 15.1 数据质量门禁

```text

3. 100% 非 rejected EvidenceRecord 必须有 claim。
```

### 15.2 来源质量门禁


## 22. 研究借鉴增强

### 22.1 Evidence Direction（借鉴 Scite）

**来源**：Scite 引用意图分类（supporting/contradicting/mentioning）

产品方案要求每条证据有 `evidence_direction` 字段，表达该证据对研究问题的立场：

```text
supporting   — 该证据支持某个结论或假设
contradicting — 该证据反驳或限制某个结论
mentioning   — 该证据只是提及，不表达立场
```

**与知识图谱的关系**：
- supporting evidence → Finding SUPPORTS Finding 关系
- contradicting evidence → Finding CONTRADICTS Finding 关系
- 多篇论文的 contradicting evidence → 识别研究争议点 → 创新点来源

**实现位置**：
- E2 抽取阶段：从 PaperCard 的 finding/limitation 语义推断 direction
- E5 下游集成：QA 回答中展示 supporting/contradicting 证据

### 22.2 Consensus Level（借鉴 Consensus）

**来源**：Consensus Claims & Evidence Table + Consensus Meter

产品方案要求每条证据有 `consensus_level` 字段，表达多论文结论的共识程度：

```text
strong_agreement — 多篇论文一致支持
agreement        — 多数论文支持
mixed            — 论文结论混合
disagreement     — 论文结论矛盾
insufficient     — 证据不足，无法判断
```

**实现位置**：
- E5 下游集成：按 topic/method 聚合 evidence，计算 consensus_level
- 创新点报告：disagreement 和 insufficient 是创新点来源

### 22.3 反证检测（借鉴 PapersFlow）

**来源**：PapersFlow Critic Agent + Chain of Verification

产品方案要求创新点报告必须列出"限制或反对证据"。证据表需要支持：

```text
1. 每条 finding evidence 可以关联 contradicting_evidence_ids
2. 生成创新点时，自动搜索反对证据
3. 验证状态：supported / contradicted / unverified
```

**与现有设计的关系**：
- §5.3 已有 `contradicting_evidence_ids` 字段
- §9.1 已有 conflict 状态设计
- 需要在 E2 抽取阶段实现自动关联

### 22.4 幻觉检测与证据表质量

**来源**：LettuceDetect + Vectara Hallucination Leaderboard

证据表质量直接影响 QA 幻觉率：

```text
高质量证据表 → QA 基于真实证据回答 → 低幻觉率
低质量证据表 → QA 基于噪声/伪证据回答 → 高幻觉率
```

**质量指标**（借鉴 Atlas H/V ratio）：
- `evidence_coverage` = 有来源支撑的 evidence 数 / 总 evidence 数
- `source_match_rate` = quote 校验通过的 evidence 数 / 有 quote 的 evidence 数
- `review_rate` = 已审核的 evidence 数 / 总 evidence 数

### 22.5 PRISMA-trAIce 透明报告

**来源**：PRISMA-trAIce AI 辅助 SR 透明报告检查清单（12 项）

证据表的审计日志应支持 PRISMA-trAIce 风格的透明报告：

```text
1. 使用了哪些 AI 工具（LLM 版本）
2. 哪些证据是 AI 生成的（extraction_method=llm）
3. 哪些证据经过人工确认（review_status=accepted）
4. 哪些证据被拒绝（review_status=rejected）
5. 排除的论文及排除理由
```

当前 `EvidenceAuditEvent` 设计已覆盖大部分需求。
