## 1. 模块定位

### 1.1 一句话定位

评估日志监控模块负责回答三个问题：

```text
系统发生了什么？
结果是否可信？
重构后有没有退化？
```

### 1.2 在产品链路中的位置

```text
Search
  -> Parser
  -> PaperCard
  -> EvidenceTable
  -> KnowledgeGraph
  -> RetrievalScope
  -> ScopeQA/RAG
  -> ReviewReport
  -> InnovationReport
  -> ReportVersion/Export
  -> API/Task/Frontend
  -> Evaluation/Logs/Monitoring
```

评估日志监控模块横向接入所有模块，但不替代业务模块的核心逻辑。它只做四类事情：

| 类型 | 职责 | 产物 |
| --- | --- | --- |
| Observability | 记录结构化日志和运行指标 | JSON 日志、metric records |
| Evaluation | 对 QA、RAG、报告、创新点进行质量评估 | evaluation results |
| Quality Gate | 把指标转成可通过/失败的门禁 | quality gate summary |
| Regression | 用固定 fixtures 发现重构退化 | golden test reports |

### 1.3 与其它模块的关系

| 上游模块 | 本模块接收 | 本模块输出 |
| --- | --- | --- |
| 01 搜索模块 | search session、query、source results、dedup result | search latency、provider success rate、dedup precision |
| 04 PDF 解析与分块 | parse result、chunks、section map | parse success rate、chunk coverage、parse warnings |
| 05 论文卡片 | cards、source spans | card completeness、source span coverage |
| 06 证据表 | evidence records、review_status | evidence traceability、accepted evidence ratio |
| 07 知识图谱 | graph nodes、edges、path query result | graph build stats、graph path validity |
| 08 RetrievalScope | scope object、scope guard | scope size、scope violation count |
| 09 ScopeQA/RAG | QAResponse、retrieved context | scope_guard_pass_rate、citation_coverage、context metrics |
| 10 综述生成 | Report、sections、citations | report_traceability、section_source_coverage |
| 11 创新点报告 | InnovationPoint、scores、supporting evidence | specificity、gap support、feasibility completeness |
| 12 报告版本导出 | report versions、export result | export success rate、format validation |
| 13 LLM 提示词 | llm call、prompt name、schema parse result | token、latency、retry、parse failure rate |
| 14 API 与前端联调 | request、task、frontend action | request/task trace、error taxonomy、demo smoke result |

## 2. 本地调研结论

### 2.1 现有文档给出的硬性要求

结合 `09-ScopeQA与RAG模块.md` 至 `14-API任务与前端联调模块.md`，评估日志监控模块必须承接以下要求：

| 来源 | 关键要求 | 对本模块的要求 |
| --- | --- | --- |
| ScopeQA/RAG | 不能越界引用，答案必须有证据，可拒答 | `scope_guard_check`、`citation_coverage_check`、QA golden cases |
| 综述生成 | 报告要有来源覆盖和章节质量校验 | `report_traceability_check`、`section_source_coverage_check` |
| 创新点报告 | 避免空泛创新点，gap 和 evidence 必须可追溯 | `innovation_specificity_check`、`gap_support_check` |
| 报告版本导出 | 导出结果要可验证、可回滚、可追踪 | `export_validation_check`、report version metrics |
| LLM 提示词 | 结构化输出、JSON 解析失败、token 成本要可见 | `llm.call` metric、schema parse metrics |
| API 任务联调 | request/task/project 三层 trace 要打通 | `request_id`、`task_id`、`project_id` 统一上下文 |

### 2.2 可借鉴的主流做法

本项目第一阶段只借鉴思想，不强依赖外部 SaaS：

| 方向 | 可借鉴点 | 本项目落地方式 |
| --- | --- | --- |
| OpenTelemetry | trace、logs、metrics 使用统一上下文 | P2 提供 adapter，P0 先统一字段 |
| LangSmith 类 LLM Trace | 记录 prompt version、model、latency、token、error | `LLMCallMetric` 和 `llm.call` event |
| RAGAS 类 RAG 评估 | faithfulness、answer relevance、context precision/recall | P0 先做轻量规则评估，P1 可接第三方评估器 |
| Evidently 类质量报告 | 指标快照、漂移、评估报告 | `--write-report` 输出 Markdown/JSON |
| Loguru | 本地日志轮转、结构化记录、异步写入 | 复用现有 Loguru，封装 `logging_utils.py` |
| pytest golden tests | 固定输入输出防回归 | `tests/fixtures/research_workspace` |

| 无报告质量门禁 | 报告保存前缺少统一检查 | 低来源覆盖、空泛段落进入版本库 | P0 |
| 无创新点质量门禁 | 只靠生成逻辑自约束 | 创新点可能泛泛、无 gap 支撑 | P0 |
| 无 golden fixtures | 测试多为代码级 | 难以比较业务输出质量是否退化 | P0 |
| 无评估 CLI | 无一键质量报告 | 重构、联调、发布前无法快速验收 | P0 |
| 无 API/task trace | 任务执行日志与请求缺少关联 | 前端看不到失败阶段和原因 | P1 |
| 无成本统计 | token 和调用次数没有汇总 | 无法控制 LLM 成本 | P1 |
| 无外部监控适配 | 未接 OpenTelemetry 等 | 后续部署后观测能力不足 | P2 |

## 4. 开发目标与边界

### 4.1 P0 目标

P0 目标是建立“本地可运行、测试可覆盖、失败可解释”的质量闭环：

```text
1. 所有关键 service 操作有结构化日志。
2. request_id、task_id、project_id 可以贯穿 API、任务和 service。
3. LLM 调用记录 provider、model、latency、token、retry、status、error_type。
4. 日志默认脱敏，不记录完整 prompt、完整 PDF、完整 response、API key。
5. evaluation.py 能评估 ScopeQA、报告、创新点、日志脱敏和 E2E smoke。
6. tests/fixtures/research_workspace 提供稳定 golden cases。
7. scripts/evaluate_research_workspace.py 可输出 JSON 和 Markdown 质量报告。
8. 质量门禁失败时明确列出失败 case、失败指标和建议定位模块。
```

### 4.2 P1 目标

```text
1. 增加搜索、解析、分块、证据、图谱、导出的模块级指标。
2. 增加 RAG context precision/recall 的 golden 评估。
```

| --- | --- | --- |

| `operation` | str | 操作名，如 `answer` |
| `status` | str | started/succeeded/failed/skipped |

### 6.3 上下文字段传播

建议使用 `contextvars` 保存当前执行上下文：

```python
from contextlib import contextmanager
from dataclasses import dataclass, field
from typing import Any

@dataclass
class LogContext:
    request_id: str | None = None
    task_id: str | None = None
    project_id: str | None = None
    paper_id: str | None = None
    report_id: str | None = None
    metadata: dict[str, Any] = field(default_factory=dict)
```

核心接口：

```python
def bind_context(**kwargs: Any) -> None:
    """把 request_id/task_id/project_id 等写入当前上下文。"""


def get_context() -> dict[str, Any]:
    """返回当前上下文，用于日志和指标自动带上关联 ID。"""


def log_event(event_type: str, level: str = "info", **fields: Any) -> None:
    """输出结构化事件，内部自动脱敏和合并上下文。"""


@contextmanager
def log_operation(service: str, operation: str, **fields: Any):
    """自动记录 started/succeeded/failed 和 latency_ms。"""
```

使用方式：

```python
with log_operation(
    service="ScopeQAService",
    operation="answer",
    project_id=project_id,
    question_hash=hash_text(question),
):
    response = qa_service.answer(project_id, question, scope_payload)
```

### 6.4 start/success/fail 规范

每个关键操作应至少记录两条事件：

```text
operation.started
operation.succeeded
```

失败时记录：

```text

```

失败事件要求：

```text
必须有 error_type。
error_message 必须脱敏和截断。
不记录完整 traceback 到普通业务日志。
debug 模式可记录 traceback_hash 或单独安全文件。
```

### 6.5 日志输出位置

P0 建议：

```text

logs/research_workspace/evaluation/latest.json
```

如果现有全局日志配置已有轮转和保留策略，则只需要把 research workspace 的事件作为结构化字段写入同一 Loguru sink。不要重复实现复杂日志轮转。

## 7. 日志脱敏设计

### 7.1 脱敏原则

```text
默认不记录完整用户输入。
默认不记录完整 PDF 文本。
默认不记录完整 prompt。
默认不记录完整 LLM response。
默认不记录 API key、Bearer token、Cookie、Authorization。
用户文件绝对路径默认 hash 或相对化。
source_quote 默认截断。
```

### 7.2 敏感模式

`redact_text` 至少覆盖：

| 类型 | 示例模式 | 输出 |
| --- | --- | --- |
| OpenAI key | `sk-...` | `[REDACTED_API_KEY]` |
| Bearer token | `Bearer abc...` | `Bearer [REDACTED_TOKEN]` |
| 环境变量 | `OPENAI_API_KEY=...` | `OPENAI_API_KEY=[REDACTED]` |
| Authorization | `Authorization: ...` | `Authorization: [REDACTED]` |
| Cookie | `Cookie: ...` | `Cookie: [REDACTED]` |
| 长 prompt | 超过阈值文本 | 截断 + hash |
| PDF 大段文本 | 超过阈值文本 | 摘要长度 + hash |
| Windows 绝对路径 | `C:\Users\...` | `[REDACTED_PATH]` 或相对路径 |

### 7.3 推荐函数

```python
def hash_text(text: str | None) -> str | None:

    """脱敏 token/key/path 后再截断。"""
```

## 9. 评估指标体系

### 9.1 总体指标分层

| 层级 | 目标 | 示例指标 |
| --- | --- | --- |
| 运行稳定性 | 系统是否能跑完 | success rate、latency、failure rate |
| 结构正确性 | 输出格式是否符合契约 | schema parse success、required field completeness |
| 可追溯性 | 结论是否有来源 | citation coverage、traceability rate |
| Scope 安全 | 是否越界引用 | scope_guard_pass_rate、out_of_scope_count |
| RAG 质量 | 检索上下文是否支撑答案 | context precision、context recall、faithfulness |
| 报告质量 | 报告是否完整且有来源 | section source coverage、generic text rate |
| 创新点质量 | 是否具体、可执行、有 gap | specificity、gap support、feasibility completeness |
| 安全合规 | 日志是否泄露敏感数据 | redaction pass、forbidden field count |

### 9.2 ScopeQA 指标

| 指标 | 公式 | P0 阈值 |
| --- | --- | --- |
| `scope_guard_pass_rate` | 通过 scope 检查的 QA cases / QA cases | `1.0` |
| `out_of_scope_citation_count` | 引用 scope 外 paper/evidence 的次数 | `0` |
| `answer_citation_coverage` | 有 evidence 支撑的回答要点 / 回答要点总数 | `>= 0.80` |
| `refusal_correctness` | 证据不足 case 中正确拒答比例 | `>= 0.80` |
| `intent_accuracy` | intent 命中 golden intent 的比例 | `>= 0.75` |
| `uncertainty_when_needed` | 低证据场景有 uncertainty 的比例 | `>= 0.80` |

### 9.3 RAG 检索指标

| 指标 | 公式 | P0/P1 |
| --- | --- | --- |
| `context_precision` | retrieved evidence 中与 golden 相关的比例 | P1 |
| `context_recall` | golden required evidence 被检出的比例 | P1 |
| `faithfulness_light` | 答案中声明可被 evidence 文本关键词支持的比例 | P0 轻量 |
| `answer_relevance_light` | 答案覆盖问题关键词或 expected topics 的比例 | P0 轻量 |
| `retrieval_empty_rate` | 非空 scope 下检索为空的比例 | P0 |

P0 的 faithfulness 不要求复杂 LLM judge，先用规则：

```text
1. 每个结论必须有 evidence_id。
2. evidence_id 必须存在。
3. evidence.paper_id 必须在 scope.paper_ids 内。
4. evidence.source_quote 或 finding/limitation 中至少命中部分问题主题关键词。
```

### 10.2 scope_guard_check

输入：

```text
QAResponse
RetrievalScope
```

检查：

```text
supporting_papers 必须是 scope.paper_ids 子集。
evidence_records[*].evidence_id 必须在 scope.evidence_ids 内，scope.evidence_ids 为空时至少 paper_id 在 scope.paper_ids 内。
graph_paths 引用的 node/edge 必须在 scope graph ids 内。
validation_warnings 中如果已有 scope violation，需要合并到失败原因。
```

输出示例：

```json
{
  "name": "scope_guard_check",
  "passed": false,
  "score": 0.0,
  "threshold": 1.0,
  "failures": [
    "supporting_papers contains paper_3 outside scope"
  ],
  "suggested_actions": [
    "Run citation validation after LLM output and remove out-of-scope ids"
  ]
}
```

### 10.3 citation_coverage_check

P0 不做复杂自然语言切句，只做保守近似：

```text
如果 answer 非空但 evidence_records 为空，则失败。
如果 answer 中出现明显引用标记但 evidence_records 不匹配，则失败。
如果 answer 超过 500 字但 evidence_records 少于 2 条，则 warning。
如果 response.uncertainty 表示证据不足，则允许 citation coverage 降低，但必须有 suggested_actions。
```

### 10.4 report_traceability_check

检查：

```text
report.paper_ids 是否存在。
report.evidence_ids 是否存在。
report.paper_ids 是否在 scope.paper_ids 内。
report.evidence_ids 对应 evidence.paper_id 是否在 report.paper_ids 或 scope.paper_ids 内。
report.content 中出现的 citation id 是否能解析。
report.content 非空且长度达到最小阈值。
```

重要：报告 traceability 不能只检查 `Report.evidence_ids` 字段，还要检查正文中是否有来源标记。否则报告可能保存了 evidence_ids，但正文没有任何可读来源。

### 10.5 section_source_coverage_check

P0 先基于 Markdown 标题和引用模式：

```text
解析二级/三级标题。
跳过 摘要/结论/参考文献 等可低引用章节。
对 背景/方法/主题/发现/不足/未来方向 等章节要求至少一个来源标记。
来源标记可以是 [paper_id]、[evidence_id]、论文标题片段或统一 citation marker。
```

输出字段：

```text
section_count
source_required_section_count
covered_section_count
missing_sections
coverage
```

### 10.6 innovation_specificity_check

每个创新点至少满足：

```text
name 不是泛泛词。
description 包含具体对象、方法、数据、场景或机制中的至少两个。
gap 非空，且不是“研究不足”“需要进一步研究”等泛泛表达。
supporting_papers 非空。
limiting_evidence 或 scores 中能看到 gap/evidence 支撑。
feasibility 非空。
risk 非空或有明确限制条件。
```

空泛表达词表初始建议：

```text
进一步研究
深入探讨
提高效果
优化模型
结合多种方法
构建系统
提升性能
拓展应用
加强分析
探索机制
```

注意：词表只用于发现明显问题，不能作为唯一判断。P1 可以结合结构化字段完整性和 evidence 支撑提升准确率。

### 10.7 redaction_check

检查日志中是否出现：

```text
sk-
OPENAI_API_KEY=
Authorization:
Bearer 后跟长 token
Cookie:
api_key
完整 prompt 字段名
raw_response
超过阈值的大段 PDF 文本
C:\Users\ 绝对路径
```

P0 策略：

```text
只要发现 API key/token 立即失败。
发现 raw_response/full_prompt 立即失败。
发现绝对路径 warning，P1 改为 failure。
发现长 source_quote warning 或 failure，取决于字段名。
```

## 17. 实施细节建议

### 17.1 error_type 归一化

建议统一错误类型：

```text

RateLimitError

```

### 17.2 latency 记录

使用 `time.perf_counter()`，不要用 wall clock 计算耗时：

```python
start = time.perf_counter()
try:
    ...
finally:
    latency_ms = int((time.perf_counter() - start) * 1000)
```

### 17.3 JSONL 写入

P0 可以先通过 Loguru sink 或简单 append 写 JSONL。若写入 metrics 文件：

```text
每行一个 JSON。
所有 payload 必须先 sanitize。
写入失败不能影响主业务流程，但应记录 warning。
```

### 17.4 评估函数设计原则

```text
优先纯函数，便于测试。
不在评估函数中调用真实 LLM。
不要让评估函数修改业务对象。
输出必须机器可读。

```

### 17.5 阈值配置

阈值放在 `quality_gates.py` 中，并支持 CLI profile 覆盖：

```text

```

## 18. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 指标过多导致落地慢 | 文档很好但代码推进慢 | P0 只实现 required gates |
| 日志接入污染业务代码 | service 中到处是日志字段 | 用 `log_operation` 降低侵入 |
| 脱敏误删有效调试信息 | 日志看不到问题 | 记录 hash、长度、prompt_name、error_type |
| 规则评估误判 | 好答案被判失败 | P0 对主观质量用 warning，硬门禁只管可追溯和越界 |
| fixture 过时 | 业务模型更新后测试失效 | golden_loader 做 schema 校验，fixture 随模型迁移 |
| 外部平台依赖不稳定 | CI 受网络和账号影响 | P0/P1 不依赖外部服务 |
| token usage 取不到 | 不同 provider 返回格式不同 | 允许为空，至少记录 chars 和 latency |

## 23. 研究借鉴增强

### 23.1 LettuceDetect 幻觉检测指标（借鉴 LettuceDetect）

产品方案要求使用 LettuceDetect 进行 token-level 幻觉检测，并将 H/V ratio 作为质量指标。

评估指标新增：

```text
指标名: hallucination_ratio
含义: 幻觉 token 占比（LettuceDetect 检测）
计算: NOT_SUPPORTED tokens / total response tokens
数据源: LettuceDetect 模型输出
阈值: <= 0.20（warning）、<= 0.10（good）

指标名: h_v_ratio
含义: 幻觉断言数 / 总断言数（Atlas 定义）
计算: unverified_claims / total_claims
数据源: Chain of Verification 输出
阈值: < 0.10（优秀）、< 0.20（可接受）、>= 0.30（需要 Review-Revise）

MVP 降级:
  如果 LettuceDetect 未部署，使用规则检查：
  - citation_coverage < 0.5 视为等效 hallucination_ratio > 0.3
  - 未被 evidence_id 引用的关键断言视为幻觉
```

### 23.2 Chain of Verification 评估（借鉴 PapersFlow）

产品方案要求 QA 和创新点使用 Chain of Verification。评估模块需要验证 CoVe 的执行质量：

```text
指标名: verification_coverage
含义: 已验证声明占比
计算: verified_claims / total_claims
数据源: QAResponse.verification_results 或 InnovationPoint.verification_status
阈值: >= 0.80

指标名: unverified_claim_count
含义: 未验证的声明数量
数据源: verification_results 中 status == "unverified" 的条目
阈值: 0（warning if > 0）

指标名: contradicted_claim_count
含义: 被证据矛盾的声明数量
数据源: verification_results 中 status == "contradicted" 的条目
阈值: 0（阻塞 if > 0）
```

### 23.3 反证检测评估（借鉴 PapersFlow Critic Agent）

产品方案要求创新点报告必须列出反证。评估模块需要验证反证检测的执行：

```text
指标名: counter_evidence_ratio
含义: 有反证的创新点数 / 总创新点数
计算: innovations_with_counter_evidence / total_innovations
数据源: InnovationPoint.limiting_evidence_ids 非空
阈值: 不设硬阈值，但记录用于质量分析

指标名: counter_evidence_search_rate
含义: 执行了反证搜索的创新点比例
数据源: InnovationPoint.metadata.counter_evidence_searched
阈值: >= 0.80（P1）
```

### 23.4 证据覆盖指标（借鉴 Atlas）

Atlas 将 evidence_coverage 作为核心质量指标：

```text
指标名: evidence_coverage
含义: 有来源支撑的要点数 / 总要点数
计算: key_points_with_evidence / total_key_points
数据源: QAResponse.key_points 或 Report sections
阈值: >= 0.80

指标名: source_quote_rate
含义: 有原文引用的证据数 / 总证据数
计算: evidence_with_source_quote / total_evidence
数据源: EvidenceRecord.source_quote 非空
阈值: >= 0.50（P1）
```

### 23.5 PRISMA-trAIce 透明报告检查（借鉴 PRISMA-trAIce）

PRISMA-trAIce 定义了 12 项 AI 辅助系统综述的透明报告检查清单。本产品可借鉴其中适用的项目：

```text
适用检查项：
  1. 工具识别：记录使用的 LLM 模型和版本
  2. 目的/阶段：记录 AI 在哪个阶段辅助（检索/筛选/提取/综合）
  3. 输入数据：记录输入的论文数量、Scope、evidence 数量
  4. 输出数据：记录生成的报告版本、章节数、引用数
  5. Prompt 记录：记录 prompt name/version（L1）、prompt hash（L2）、完整 prompt（L3 debug）
  6. 人工确认：记录用户确认/修改的操作

评估函数新增：
  def prisma_transparency_check(report: Report) -> dict:
      """检查报告是否包含 PRISMA-trAIce 要求的透明元数据"""
      checks = {
          "model_info": bool(report.metadata.get("model_info")),
          "scope_snapshot": bool(report.metadata.get("scope_snapshot")),
          "prompt_version": bool(report.metadata.get("prompt_version")),
          "generation_time": bool(report.metadata.get("generated_at")),
          "quality_metrics": bool(report.metadata.get("quality_metrics")),
          "used_papers_count": len(report.paper_ids) > 0,
          "used_evidence_count": len(report.evidence_ids) > 0,
      }
      return {"pass": all(checks.values()), "checks": checks}
```

### 23.6 RAG 评估指标增强（借鉴 RAGAS）

RAGAS 定义了 RAG 系统的标准评估指标。本产品已有轻量版，可增强：

```text
已有轻量版（P0）：
  - faithfulness_light: 规则检查声明是否有 evidence_id
  - answer_relevance_light: 答案覆盖问题关键词比例
  - context_precision_light: 检索证据与 golden 相关比例

增强方向（P1）：
  - context_recall: golden required evidence 被检出比例
  - context_relevancy: 检索上下文与问题的语义相关度
  - answer_correctness: 答案与 golden answer 的匹配度

P1 实现方式：
  1. 使用 LLM-as-Judge 评估 faithfulness 和 answer_relevance
  2. 使用 embedding 相似度评估 context_relevancy
  3. 使用 token overlap 评估 answer_correctness
```

### 23.7 Vectara 幻觉基准参考（借鉴 Vectara）

Vectara Hallucination Leaderboard 基准测试了 80+ 模型的幻觉率：

```text
关键发现（2026 年 2 月更新）：
  - 推理模型幻觉率比基础模型高 3-4 倍（o3-pro 23.3% vs GPT-4.1 5.6%）
  - RAG grounding 可减少 75-90% 幻觉（最强单一手段）
  - 最佳模型幻觉率约 1.8-3%

对本产品的启示：
  1. 优先使用 RAG grounding（本产品已有 evidence-based 回答）
  2. 记录模型幻觉率基准，作为 quality_metrics 的参考
  3. 如果 h_v_ratio > 模型基准 + 0.1，说明 prompt 或检索有问题
```
