## 1. 模块定位

### 1.1 在产品链路中的位置

产品主线：

```text
研究项目
  -> 论文库
  -> PDF 解析与分块
  -> 论文卡片
  -> 证据表
  -> 知识图谱
  -> Retrieval Scope
  -> Scope-based QA
  -> 文献综述
  -> 创新点报告
```

知识图谱处在证据表之后、Scope 和生成模块之前。它的核心价值是把分散的 EvidenceRecord 组织成图结构，使系统能够回答：

```text
哪些论文属于同一主题？
哪些论文使用相似方法？
哪些发现支持同一结论？
哪些局限共同指向同一个研究空白？
某个 gap 背后有哪些论文和证据？
两个主题、方法或论文之间通过什么路径相关？
当前选择的图谱子图能限定哪些 paper_ids 和 evidence_ids？
```

### 1.2 模块边界

本模块要做：

```text
1. 从 EvidenceRecord、PaperCard 和 Paper 元数据构建轻量 property graph。
2. 生成稳定的 GraphNode 和 GraphEdge ID。
3. 为节点和边保留 paper_ids、evidence_ids、source_chunk_ids、source_quotes。
4. 支持节点、邻居、子图、路径、统计和质量校验查询。
5. 支持 Gap 候选聚合，并为创新点模块提供输入。
6. 支持 RetrievalScope 基于 graph_node_ids / graph_edge_ids 解析范围。
7. 为 QA 提供紧凑、可追溯、Token 可控的 GraphRAG 上下文。
8. 为前端知识图谱页面提供可过滤、可选择、可查看来源的数据。
```

本模块暂不做：

```text
1. MVP 阶段不上 Neo4j、NebulaGraph、JanusGraph 等重型图数据库。
2. MVP 阶段不做 TransE、RotatE、R-GCN、Node2Vec 等图嵌入训练。
3. MVP 阶段不直接从 PDF 全文自由抽取任意三元组，优先使用 PaperCard 和 EvidenceRecord。
4. MVP 阶段不做完整 citation network 和作者消歧。
5. MVP 阶段不把每个可视化布局结果写成权威事实。
```

## 2. 本地调研结论落地

### 2.1 知识图谱调研落地

`docs/research/10-知识图谱/学术论文知识图谱构建调研报告.md` 给出的知识图谱通用流程是：

```text
数据采集
  -> 信息抽取
  -> 知识融合
  -> 知识表示
  -> 知识存储
  -> 应用服务
```

本项目的对应实现：

| 通用步骤 | 本项目落地 |
| --- | --- |
| 数据采集 | PaperLibrary、PDF Parser、Search 模块 |
| 信息抽取 | PaperCardGenerator、EvidenceTableService |
| 知识融合 | EntityNormalizer、EvidenceMerger、GapDetector |
| 知识表示 | GraphNode、GraphEdge、KnowledgeGraph |
| 知识存储 | MVP 使用 JSON collection，后续可迁移 SQLite/Neo4j |
| 应用服务 | Scope QA、综述、创新点、知识图谱页面 |

开发策略采用“自顶向下 Schema + 自底向上证据填充”：

```text
自顶向下：
  先固定 Paper、Topic、Method、Dataset、Finding、Limitation、Gap 等节点类型和边类型。

自底向上：
  从 EvidenceRecord 中抽取真实项目证据，逐步填充节点和边。

LLM 辅助：
  只用于 PaperCard、EvidenceRecord、Gap 聚合摘要等明确任务，不允许绕过证据表凭空构图。
```

### 2.2 产品方案落地

`当前产品方案.md` 明确要求：

```text
所有 QA、综述、创新点都能追溯到论文、证据记录和图谱节点。
知识图谱页面可以查看节点和关系、筛选节点类型、查看节点证据来源、选择节点或子图。
Retrieval Scope 可以选择论文、主题、方法、年份、知识图谱节点、知识图谱子图。
```

因此知识图谱模块必须优先保证：

```text
1. traceability：任何非结构性节点和边都必须有来源。
2. scopeability：图谱查询结果必须能导出 paper_ids 和 evidence_ids。
3. explainability：路径查询必须能解释“为什么相关”，而不是只返回 node_id。
4. compactness：GraphRAG 上下文必须用卡片、证据和图谱摘要，不直接塞全文。
```

### 2.3 RAG/QA 调研落地

QA 调研中建议复杂学术问题使用 Query Decomposition、Self-RAG、CRAG 和拒答策略。知识图谱模块对应提供三类能力：

```text
1. 多跳路径：为“论文 A 和论文 B 为什么相关”提供结构化路径。
2. 局部子图：为“这个主题下常见方法和局限是什么”提供 1-hop/2-hop 证据范围。
3. 全局摘要：为“这个项目主要研究脉络是什么”提供 Topic/Gap 层面的汇总。
```

QA 的拒答和防幻觉依赖图谱来源属性：

```text
如果子图无 evidence_ids，QA 不应基于该子图生成确定结论。
如果 graph scope 解析出的论文少于阈值，答案应标记不确定或建议扩大范围。
如果用户问题超出当前 graph scope，QA 不允许引用 scope 外论文。
```

### 2.4 Token 调研落地

Token 成本调研建议使用分层内容：

| 层级 | 内容 | 用途 |
| --- | --- | --- |
| L0 | 元数据 | 列表和筛选 |
| L1 | 摘要 | 快速概览 |
| L2 | PaperCard | QA 和综述 |
| L3 | EvidenceTable | 证据型回答和创新点 |
| L4 | 相关 chunks | 深度 QA 和引用定位 |
| L5 | 全文 | 单篇深度分析 |

知识图谱上下文只输出 L0-L3，必要时附带 L4 的 `source_quote` 或 `source_chunk_id`。默认不把全文放进 GraphRAG。

### 2.5 评估调研落地

`RAG与知识图谱检索评估标准调研报告.md` 给出的关键指标包括：

```text
Context Precision >= 0.75
Context Recall >= 0.80
Faithfulness >= 0.80
Answer Relevance >= 0.80
KG accuracy / completeness / consistency / freshness
```

知识图谱模块自身的质量门槛：

```text
traceability_coverage >= 0.95
orphan_node_rate <= 0.05
duplicate_entity_rate <= 0.05
invalid_edge_count == 0
scope_leak_count == 0
stable_id_rebuild_match_rate == 1.0
```

### 3.2 当前关键问题

| 问题 | 当前表现 | 影响 | 优先级 |
| --- | --- | --- | --- |
| ID 不稳定 | Finding/Limitation 使用 `uuid.uuid4()` | 重复构图后前端选择、Scope、报告引用失效 | P0 |
| 边 ID 不稳定/不规范 | `paper->node` 字符串拼接，缺少 edge_type 和证据哈希 | 多证据合并困难 | P0 |
| 来源追踪弱 | 非 Paper 节点只粗略写 `paper_ids`，且 `source_evidence` 未实际使用 | QA 和报告无法严格回溯 | P0 |
| Gap 生成过宽 | 每个 limitation 都可变成 gap | 创新点会泛化、噪声大 | P0 |
| Dataset 未构建 | `NodeType.DATASET` 和 `USES_DATASET` 存在但构图未使用 | 方法和样本对比缺失 | P0 |
| Task 未构建 | 模型有 Task 但构图未使用 | 研究问题聚合不足 | P1 |
| Future Work 未利用 | EvidenceRecord 有 `future_work` 但未进入 gap 聚合 | 研究空白来源不足 | P0 |
| 存储 collection 不统一 | 使用 `graph_{project_id}` | 后续统一查询、迁移和 API 不方便 | P0 |
| 子图信息不足 | `get_subgraph` 只返回 nodes/edges | RetrievalScope 无法稳定解析 paper/evidence | P0 |
| 路径解释不足 | `find_paths` 只返回 node_id 列表 | 不能解释关系证据 | P1 |
| 实体归一化弱 | 仅 lowercase + replace space | 同义词、缩写、复数无法合并 | P0 |
| 质量校验缺失 | 只有 stats | 无法发现无证据节点、坏边、重复实体 | P0 |
| GraphRAG 缺失 | 无 local/global 图谱检索上下文 | 多跳 QA 和全局综述支撑弱 | P1 |

## 4. 主流系统做法与借鉴

| 系统/产品 | 做法 | 对本项目的借鉴 |
| --- | --- | --- |
| Neo4j Property Graph | 节点和关系都具有类型、方向和属性 | GraphNode/GraphEdge 必须一等建模，边也要有来源和权重 |
| Microsoft GraphRAG | 从文本抽取实体关系，生成社区摘要，查询分 local/global | P1 做局部子图检索和 Topic/Gap 全局摘要 |
| LlamaIndex GraphRAG | Property graph 绑定 source text，图谱检索和文本证据结合 | 每个节点/边都要能回到 source_chunk/source_quote |
| scite | 区分 supporting、contrasting、mentioning 等证据关系 | 后续 evidence relation 可扩展为支持/反对/提及 |
| Connected Papers / ResearchRabbit | 以关系图辅助文献发现和探索 | 前端应支持以节点/子图作为研究范围 |
| Semantic Scholar / OpenAlex | 强调论文、作者、主题、引用元数据 | P1/P2 再补 Author、CITES、外部元数据增强 |

本项目的落地选择：

```text
MVP：
  JSON 轻量 property graph + evidence provenance + graph scope。

P1：
  GraphRAG local/global 上下文 + gap 聚合 + 路径解释。

P2：
  引用网络、作者网络、外部学术 API 增强、可选 Neo4j 迁移。
```

## 7. 稳定 ID 与归一化规则

### 7.1 稳定 ID 规则

必须移除 Finding/Limitation 的随机 UUID。建议 ID 规则：

```text
paper:{paper_id}
topic:{hash(normalized_label)}
method:{hash(normalized_label)}
dataset:{hash(normalized_label)}
task:{hash(normalized_label)}
finding:{paper_id}:{hash(normalized_claim)}
limitation:{paper_id}:{hash(normalized_claim)}
gap:{hash(normalized_gap_statement)}
innovation:{innovation_id}
author:{hash(normalized_author_name)}
```

边 ID：

```text
edge:{edge_type}:{source_id}:{target_id}:{hash(sorted_evidence_ids)}
```

如果同一 source、target、edge_type 后续合并了新 evidence，允许：

```text
1. edge_id 不包含 evidence hash，保持一条边持续合并 evidence_ids。
2. 或 edge_id 包含 source/target/type，properties 中记录 evidence_ids。
```

MVP 推荐第 2 种更简单：

```text
edge:{edge_type}:{hash(source_id)}:{hash(target_id)}
```

### 7.2 文本归一化

`normalize_label(text)`：

```text
1. strip 前后空白。
2. lowercase。
3. 全角转半角。
4. 连续空白压缩为单空格。
5. 去除末尾句号、分号、冒号。
6. hyphen、underscore 统一为空格或 hyphen。
7. 中文标点归一。
8. 常见复数和缩写归一。
9. 命中项目级 alias 表时替换为 canonical_label。
```

示例：

| 输入 | 归一化 |
| --- | --- |
| Large Language Models | large language model |
| LLMs | llm |
| Retrieval-Augmented Generation | retrieval augmented generation |
| RAG-based approach | rag based approach |
| randomized controlled trial | rct |
| quasi-experiment | quasi experimental |


## 8. 构图规则

### 8.1 Paper 节点

来源：

```text
papers collection
evidence_records.paper_id
paper_cards.paper_id
```

规则：

```text
1. 优先从 papers 读取 title、authors、year、doi、venue。
2. 如果没有 Paper 元数据，但 evidence 中出现 paper_id，也创建最小 Paper 节点。
3. Paper 节点可以没有 evidence_ids，因为它是结构性根节点。
4. Paper 节点 properties 必须包含 project_id 和 included 状态。
```

### 8.2 Topic 节点

来源：

```text
EvidenceRecord.topic
PaperCard.topics
```

规则：

```text
1. 支持逗号、分号、中文顿号拆分。
2. 空值、unknown、n/a 不建节点。
3. 同一 normalized_label 合并为一个 Topic。
4. Paper -> Topic 边必须记录 evidence_ids。
```

### 8.3 Method 节点

来源：

```text
EvidenceRecord.method
PaperCard.method
```

规则：

```text
1. unknown 不建节点。
2. 多方法用分隔符拆分。
3. 同义方法通过 alias 合并。
4. Method 节点用于方法对比、Scope 筛选和综述方法段落。
```

### 8.4 Dataset 节点

来源：

```text
EvidenceRecord.data_or_sample
PaperCard.data_or_sample
```

规则：

```text
1. P0 先把 data_or_sample 非空文本建为 Dataset 节点。
2. 能识别具体公开数据集名称时，label 使用数据集名称。
3. 不能识别具体名称时，label 使用样本/场景描述。
4. Paper -> Dataset 使用 USES_DATASET。
```

示例：

```text
data_or_sample = "120 undergraduate students"
  -> dataset/sample node: "undergraduate students sample"

data_or_sample = "MIMIC-III"
  -> dataset node: "MIMIC-III"
```

### 8.5 Finding 节点

来源：

```text
EvidenceRecord.finding
PaperCard.key_findings
```

规则：

```text
1. Finding 以单篇论文内的 claim 为主，不跨论文强行合并。
2. node_id 包含 paper_id，避免不同论文相似句子误合并。
3. label 使用短标签，完整 claim 放入 properties.claim。
4. Paper -> Finding 边必须记录 evidence_id、source_quote。
```

### 8.6 Limitation 节点

来源：

```text
EvidenceRecord.limitation
PaperCard.limitations
```

规则：

```text
1. Limitation 以单篇论文内的 limitation claim 为主。
2. node_id 包含 paper_id。
3. properties 记录 limitation_type，可先用 rule-based 分类。
4. Limitation 是 GapDetector 的主要输入，但不能自动等同于 Gap。
```

初始 limitation_type：

```text
sample_size
single_dataset
short_duration
lack_control_group
generalizability
measurement_bias
method_limitation
domain_limitation
unknown
```

### 8.7 Gap 节点

来源：

```text
EvidenceRecord.future_work
EvidenceRecord.limitation
PaperCard.possible_gaps
PaperCard.future_work
显式 evidence_type=gap 的未来扩展字段
```

规则：

```text
1. Gap 是聚合结果，不是每条 limitation 的直接复刻。
2. 至少满足一个条件才生成 Gap：
   - 显式 possible_gap / future_work 指向；
   - 多篇论文的 limitation 聚合到同一 normalized cluster；
   - 单篇 limitation 但 evidence_strength=high 且包含明显研究空白表述。
3. Gap 节点必须有 supporting_evidence_ids 和 supporting_paper_ids。
4. Gap status 初始为 candidate，经过人工确认或报告采用后可变为 accepted。
```

Gap properties：

```json
{
  "gap_statement": "",
  "source_types": ["limitation", "future_work", "possible_gap"],
  "supporting_evidence_ids": [],
  "supporting_paper_ids": [],
  "supporting_limitation_ids": [],
  "confidence": 0.0,
  "status": "candidate",
  "novelty_score": 0.0,
  "evidence_score": 0.0
}
```

### 8.8 Task 节点

来源：

```text
EvidenceRecord.research_question
PaperCard.research_question
```

优先级：P1。

用途：

```text
研究任务聚合
综述章节组织
方法-任务适配分析
```

边：

```text
Paper -> Task
Task -> Topic
Method -> Task  # P2 可选
```

当前 `EdgeType` 还没有 `STUDIES_TASK`，P1 可选择：

```text
1. 新增 EdgeType.STUDIES_TASK。
2. 或暂时不建 Task 边，只把 research_question 放入 Paper/Finding properties。
```

### 8.9 Author 和 CITES

优先级：P2。

Author：

```text
Paper -> Author
用于作者网络、合作关系和作者筛选。
需要处理姓名归一化和歧义，MVP 暂不做。
```

CITES：

```text
Paper -> Paper
用于引用网络、文献脉络和经典论文发现。
依赖参考文献解析和 DOI/title 匹配，P2 做。
```

## 9. Provenance 来源追踪契约

### 9.1 基本原则

```text
1. Paper 节点是结构性实体，可以没有 evidence_ids。
2. Topic/Method/Dataset/Finding/Limitation/Gap 等非结构性节点必须有 evidence_ids 或明确的 paper_card/source。
3. 非结构性边必须有 evidence_ids。
4. 图谱不能从 LLM 自由生成的文本中直接创造事实，除非该文本已进入 EvidenceRecord 并保留来源。
5. QA、综述、创新点只能引用可追溯的节点和边。
```

### 9.2 EvidenceRecord 到 provenance

每条 evidence 进入图谱时生成 provenance：

```json
{
  "evidence_id": "ev_001",
  "paper_id": "p_001",
  "source_chunk_id": "chunk_001",
  "source_quote": "original quote",
  "evidence_strength": "medium",
  "citation_context": "..."
}
```

节点合并时：

```text
paper_ids 去重合并
evidence_ids 去重合并
source_chunk_ids 去重合并
source_quotes 保留前 N 条，避免 properties 过大
evidence_strengths 记录分布
confidence 根据 evidence_strength 和数量计算
```

### 9.3 Source quote 控制

为避免 JSON 过大：

```text
source_quotes 每个节点最多保留 3 条短 quote。
完整 quote 仍以 evidence_id 回查 EvidenceRecord。
GraphRAG 上下文默认使用 evidence_id 回查，不依赖节点 properties 里的长文本。
```

## 13. GraphRAG 设计

### 13.1 Local Graph Search

适用问题：

```text
这个 gap 的来源是什么？
这个方法被哪些论文使用？
这个主题下有哪些共同局限？
这篇论文和其他论文有什么关系？
```

流程：

```text
question
  -> search_nodes / selected graph_node_ids
  -> get_subgraph(hops=1 or 2)
  -> collect related evidence_ids
  -> load EvidenceRecord + PaperCard compact context
  -> QA answer with citations
```

### 13.2 Global Graph Search

适用问题：

```text
整个项目主要研究脉络是什么？
有哪些高频主题和研究空白？
该领域的方法演进是什么？
```

P1 实现：

```text
按 Topic/Method/Gap 分组统计。
为高频 Topic 和 Gap 生成 graph summary。
QA 全局问题优先使用 summary，再按需回查 evidence。
```

### 13.3 Graph context 格式

GraphRAG 上下文推荐格式：

```text
[Graph Scope]
Selected nodes: ...
Hops: 1
Related papers: p1, p2, p3
Related evidence: ev1, ev2, ev3

[Key relations]
Paper A --USES_METHOD--> Method X (ev1)
Paper B --HAS_LIMITATION--> Limitation Y (ev2)
Limitation Y --SUGGESTS_GAP--> Gap Z (ev2, ev3)

[Evidence]
ev1 | Paper A | method | quote...
ev2 | Paper B | limitation | quote...
```

上下文预算建议：

```text
Graph relations: 500-1000 tokens
Evidence records: 1500-4000 tokens
PaperCard 摘要: 1000-3000 tokens
必要 source chunks: 1000-3000 tokens
```

### 13.4 反幻觉规则

```text
1. 没有 evidence_ids 的图谱关系不能作为强结论。
2. QA 引用必须来自 related_evidence_ids。
3. 图谱路径只能解释关系，不能替代文献证据。
4. 如果 graph scope 证据不足，返回不确定性说明或建议扩大范围。
```

## 14. Gap 检测方案

### 14.1 输入来源

```text
EvidenceRecord.limitation
EvidenceRecord.future_work
PaperCard.limitations
PaperCard.future_work
PaperCard.possible_gaps
未来扩展：EvidenceRecord.evidence_type == "gap"
```

### 14.2 P0 规则型聚合

步骤：

```text
1. 收集 gap candidates。
2. 对 candidate 文本 normalize。
3. 用规则识别 gap source_type：limitation / future_work / possible_gap。
4. 按 normalized 文本、关键词或 limitation_type 聚类。
5. 计算 confidence。
6. 生成 Gap 节点和 SUGGESTS_GAP 边。
```

置信度：

```text
base = 0.3
+ 0.2 if source_type includes future_work
+ 0.2 if source_type includes possible_gap
+ 0.1 if evidence_strength == high
+ 0.1 if supporting_paper_count >= 2
+ 0.1 if source_quote exists
max 1.0
```

生成门槛：

```text
confidence >= 0.5
或 source_type 包含 explicit possible_gap
或 supporting_paper_count >= 2
```

### 14.3 P1 LLM 辅助聚合

P1 可以增加 LLM 聚合，但必须输入候选和证据，输出结构化 JSON：

```json
{
  "gap_statement": "",
  "merged_candidate_ids": [],
  "reason": "",
  "confidence": 0.0,
  "status": "candidate"
}
```

限制：

```text
LLM 不能新增没有 evidence 支撑的 gap。
LLM 输出必须经过 GraphValidator 校验。
```

### 14.4 Gap 与创新点关系

```text
Gap 是研究空白。
InnovationPoint 是基于 Gap、用户目标、可行性和证据生成的研究方案。
```

边：

```text
Gap -> SUPPORTS_INNOVATION -> InnovationPoint
```

创新点模块读取：

```text
accepted/candidate Gap
supporting_paper_ids
supporting_evidence_ids
source limitations
confidence / novelty_score / evidence_score
```

如果只按最小闭环推进，推荐顺序：

```text

2. 补齐 evidence_ids/paper_ids/source_chunk_ids。

4. 改造 get_subgraph 返回 related ids。
5. 增加 validate_graph_traceability。
6. 改造 Gap 聚合。
7. 接入 RetrievalScope。
8. 增加路径解释。
9. 增加 GraphRAG context。
10. 接前端知识图谱页面。
```

不要优先做：

```text
Neo4j
图嵌入
复杂社区检测
完整 citation graph
作者消歧
```

这些会显著增加复杂度，但不能优先解决当前产品的核心风险：来源追踪、Scope 边界和可复现构图。

## 24. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 图谱噪声高 | Topic/Method/Gaps 太碎 | normalize + alias + quality validation |
| Gap 泛化 | 创新点变成空话 | Gap 必须有 supporting evidence 和 confidence |
| Scope 越界 | QA 引用范围外论文 | resolve_graph_scope + scope guard 测试 |
| JSON 过大 | source_quotes 太长 | quote 限长，完整内容通过 evidence_id 回查 |
| 构图不可复现 | UUID 或输入顺序导致变化 | stable hash + 排序构建 |
| 前端难用 | 图太密 | 类型过滤、hops 限制、节点权重 |
| 后续迁移困难 | collection 契约混乱 | 统一 graphs collection，GraphService 保持门面 |

### 下一步深化任务

