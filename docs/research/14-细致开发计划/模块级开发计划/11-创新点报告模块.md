# 创新点报告模块专项开发报告

更新时间：2026-05-28

创新点报告模块负责把 Retrieval Scope 内的证据、研究空白、论文局限、future work、图谱结构缺口和用户研究目标，转化为可追溯、可评分、可筛选、可继续落题的研究创新方向。

这个模块不能做成“让 LLM 发散想几个选题”的功能。它的核心价值是：每一个创新点都必须说明它从哪些证据和 Gap 来，为什么不是泛泛建议，当前证据能支撑到什么程度，有哪些限制和风险，以及是否匹配用户项目的学科、研究目标和能力水平。

## 1. 模块定位

### 1.1 在产品链路中的位置

创新点报告位于 Evidence、KnowledgeGraph、RetrievalScope、ScopeQA、综述生成之后：

```text
Paper Search / PDF Parse
  -> PaperCard
  -> EvidenceRecord
  -> KnowledgeGraph
  -> RetrievalScope
  -> ScopeQA / Review Material
  -> Innovation Report
  -> InnovationPoint graph writeback
  -> Topic proposal / research design
```

它依赖前置模块提供的结构化材料：

| 上游模块 | 提供内容 | 在创新点报告中的用途 |
| --- | --- | --- |
| 05 论文卡片 | 论文元信息、研究问题、方法、结论、局限 | 支撑论文摘要和基础判断 |
| 06 证据表 | finding、limitation、future_work、source_quote | 创新点事实依据 |
| 07 知识图谱 | Topic、Method、Dataset、Gap、路径关系 | 发现结构性空白和方法迁移机会 |
| 08 RetrievalScope | paper_ids、evidence_ids、graph_node_ids | 限定生成范围 |
| 09 ScopeQA/RAG | innovation_seed、gap_analysis 问答材料 | 作为候选信号，但不能绕过证据校验 |
| 10 综述生成 | evidence matrix、主题分组、争议点 | 辅助形成创新点对比和上下文 |
| 15 评估日志 | specificity、gap support、evidence support 指标 | 质量门禁和回归测试 |

### 1.2 模块产物

核心产物是 `ReportType.INNOVATION_REPORT`，并可选生成 `InnovationPoint` 图谱节点。

报告必须包含：

```text
创新点摘要表
每个创新点的证据链
对应研究空白
为什么有新意
已有研究基础
可行性分析
风险和限制
可转化论文题目
评分
来源索引
质量校验结果
```

可选后续产物：

```text
accepted innovation candidates
InnovationPoint graph node
Gap -> SUPPORTS_INNOVATION -> InnovationPoint edge
topic proposal draft
research question draft
initial method design
```

### 1.3 设计原则

```text
1. 证据优先：创新点必须来自 EvidenceRecord、Graph Gap 或已保存 QA material。
2. Scope 优先：不允许引用 scope 外 paper_id/evidence_id。
3. Gap 优先：创新点不是主题推荐，而是围绕明确空白或限制的方案。
4. 可追溯优先：每个候选必须保留 source_signal_ids、supporting_evidence_ids、limiting_evidence_ids。
5. 可执行优先：泛泛方向即使看起来新，也不能通过质量门禁。
6. 用户匹配优先：结合 Project.discipline、education_level、research_goal 判断 fit 和 feasibility。
7. 图谱辅助：GraphRAG 和图谱路径用于解释关系，事实依据仍以 EvidenceRecord 为准。
```

## 2. 本地调研结论落地

### 2.1 产品方案中的要求

本地产品方案对创新点报告的定位是“研究空白到选题机会”的桥接层。可落地要求如下：

| 产品要求 | 开发落点 |
| --- | --- |
| 从研究空白生成创新方向 | 建立 `GapSignal`，统一表示 limitation、future_work、graph gap |
| 说明为什么创新 | `why_innovative` 必须绑定 gap 类型和已有研究不足 |
| 说明研究基础 | 从 finding、method、paper card 中抽取 foundation |
| 说明限制和风险 | 聚合 limitation、contradicting evidence、数据/伦理/技术约束 |
| 输出可转化题目 | `possible_topic` 需要具体到对象、方法、场景、变量或结果 |
| 支持评分筛选 | novelty、evidence、feasibility、risk、fit、specificity |
| 能继续进入图谱和报告链路 | 写入 Report，并可选写回 InnovationPoint 节点 |

### 2.2 证据表模块对本模块的约束

06 证据表模块的核心原则是 EvidenceRecord 成为事实层。本模块必须遵守：

```text
EvidenceRecord.finding      -> 只能作为已有研究基础
EvidenceRecord.limitation   -> 可转为 common_limitation / risk
EvidenceRecord.future_work  -> 可转为 future_work_cluster / explicit_gap
EvidenceRecord.method       -> 可用于 method_transfer / feasibility
EvidenceRecord.data_or_sample -> 可用于 dataset_gap / context_gap
EvidenceRecord.source_quote -> 可用于报告引用和来源索引
EvidenceRecord.evidence_strength -> 影响 evidence score
```

未来证据表增强后，应兼容以下字段：

```text
evidence_type
claim
review_status
evidence_relation
confidence
possible_gap
source_span
```

兼容策略：

| 字段状态 | 处理方式 |
| --- | --- |
| 当前旧模型无 `evidence_type` | 从 finding/limitation/future_work 推断 |
| 当前旧模型无 `review_status` | 默认 pending，中性计分 |
| 当前旧模型无 `evidence_relation` | 先不做支持/反驳分类，只用 limitation/risk |
| 当前旧模型无 `possible_gap` | 从 limitation 和 future_work 构建 gap |
| 当前旧模型无 metadata | 暂存在 Report.scope 的 `innovation_metadata` 中 |

### 2.3 知识图谱模块对本模块的约束

07 知识图谱模块已经定义：

```text
NodeType.GAP
NodeType.INNOVATION
EdgeType.SUGGESTS_GAP
EdgeType.SUPPORTS_INNOVATION
```

创新点模块应使用图谱，但不能被图谱绑死：

| 图谱输入 | 创新点用途 |
| --- | --- |
| Topic -> Method 分布 | 发现 method_gap 和 method_transfer |
| Topic -> Dataset 分布 | 发现 dataset/context gap |
| Paper -> Limitation -> Gap | 聚合显式研究空白 |
| Gap 节点 | 作为创新候选的直接 source_signal |
| Graph path | 解释创新点从哪个主题、方法、证据路径推导而来 |

关键约束：

```text
Graph path 只能解释关系。
候选事实依据必须回落到 supporting_evidence_ids。
没有 evidence_id 的 graph gap 只能生成 low confidence candidate。
写回图谱前必须通过 validation。
```

### 2.4 RetrievalScope 模块对本模块的约束

08 RetrievalScope 模块要求所有报告在解析范围内工作：

```text
1. 先 resolve scope_payload。
2. 再用 ScopeGuard 校验输入材料。
3. 候选生成时只能使用 scope.evidence_ids / scope.paper_ids / scope.graph_node_ids。
4. 生成后再次校验所有引用 ID。
5. scope 为空时不能 fallback 到全项目，必须返回 empty report 或 suggested actions。
```

创新点报告中的 `Report.paper_ids` 和 `Report.evidence_ids` 不能简单复制整个 Scope。更合理的策略是：

```text
report.paper_ids = candidates 实际使用的 supporting_paper_ids + limiting_paper_ids
report.evidence_ids = candidates 实际使用的 supporting_evidence_ids + limiting_evidence_ids
report.scope = 原始 resolved scope + innovation_metadata
```

这样报告的来源列表更精确，也便于后续 traceability 检查。

### 2.5 ScopeQA/RAG 模块对本模块的约束

09 ScopeQA 已规划 `innovation_seed` 和 `innovation_generation` 意图。创新点报告可以复用 QA 材料，但需要二次校验：

```text
QA answer -> innovation_material
  -> extract candidate signal
  -> map to EvidenceRecord
  -> validate inside scope
  -> generate InnovationPoint
```

不允许：

```text
直接把 QA 的自然语言回答复制为创新点。
直接把 graph_paths 当作事实证据。
QA 中出现但 EvidenceRecord 中不存在的 paper_id/evidence_id 不得进入报告。
```

### 2.6 综述生成模块对本模块的复用点

10 综述生成模块已经规划了材料收集、矩阵、结构化输出、渲染、质量校验和 ReportService 集成。创新点报告可以复用同样的工程模式：

```text
collect materials
  -> build matrix/signals
  -> generate structured output
  -> score and validate
  -> render markdown report
  -> save via ReportService
```

差异是：

| 综述生成 | 创新点报告 |
| --- | --- |
| 目标是总结已有研究 | 目标是发现可行研究机会 |
| 以主题/方法/趋势分节 | 以 GapSignal 和 InnovationCandidate 分组 |
| 重点是 coverage 和 citation | 重点是 specificity、gap support、feasibility |
| 低证据时应说明不确定 | 低证据时应降分或标记 evidence_insufficient |

### 2.7 评估日志模块对本模块的要求

15 评估日志监控模块已经提出创新点相关指标：

```text
innovation_specificity_rate
gap_support_rate
evidence_support_rate
feasibility_completeness
generic_filter_pass_rate
scope_violation_count
```

本模块需要在生成过程中输出可计算事件：

```text
innovation.signals.collected
innovation.candidate.generated
innovation.candidate.scored
innovation.candidate.filtered
innovation.validation.completed
innovation.report.saved
```

## 3. 主流产品和研究做法借鉴

### 3.1 文献关系图产品

Connected Papers、ResearchRabbit、Semantic Scholar、OpenAlex 等文献图谱工具的核心启发是：研究机会往往来自论文网络中的相邻主题、关键桥接论文、缺失连接和新近聚集主题。

落地到本项目：

```text
1. 不只统计 limitation 文本，还要看 Topic-Method、Topic-Dataset、Topic-Outcome 的覆盖结构。
2. 对低连接但高相关的组合生成 graph_gap。
3. 对两个相邻主题中方法不对称的情况生成 method_transfer。
4. 用 graph_node_ids 和 graph_edge_ids 解释创新点来源。
```

### 3.2 证据问答产品

Elicit、Consensus 一类工具的核心启发是：结论和建议必须回到论文证据，而不是只给自然语言判断。

落地到本项目：

```text
1. Prompt 输入必须包含 evidence_id。
2. Prompt 输出必须回填 supporting_evidence_ids。
3. LLM 不允许自造 paper_id/evidence_id。
4. 报告中每个创新点必须展示来源证据和限制证据。
5. evidence_insufficient 不等于失败，而是低置信候选。
```

### 3.3 引文语义和争议识别

scite 的支持、反驳、提及关系提醒本项目：创新点不只来自“大家都说有局限”，也来自证据之间的不一致。

落地到本项目：

```text
1. 当前版本先从 limitation 和 finding 文本中发现潜在矛盾。
2. 未来 EvidenceRecord 增强 `evidence_relation` 后，直接识别 supports/contradicts/mixed。
3. contradiction signal 必须同时输出 supporting_evidence_ids 和 limiting_evidence_ids。
4. 争议型创新点的 risk 分数应更高，但 novelty 也可能更高。
```

### 3.4 GRADE 和系统综述方法

GRADE 和系统综述实践的启发是：不能只看证据数量，还要看证据确定性、偏倚、直接性和一致性。

落地到本项目：

```text
1. evidence_strength 不能只按论文数量。
2. review_status、source_quote、方法质量、样本规模、证据一致性都应影响 evidence score。
3. 多篇低质量证据不应自动高分。
4. 风险和限制必须进入报告，而不是藏在评分里。
```

### 3.5 TRIZ 和设计空间分析

创新点还可以来自设计空间的空位：

```text
Topic x Method
Topic x Dataset
Population x Intervention
Context x Outcome
Theory x Application
```

落地到本项目：

```text
1. 建立 design_space matrix。
2. 找到高价值但证据覆盖不足的空格。
3. 从相邻主题迁移方法时检查可行性约束。
4. 输出“组合为什么合理”，而不是只输出“把 A 和 B 结合”。
```

## 5. 目标与边界

### 5.1 一句话目标

基于 Scope 内可追溯证据和图谱 Gap，生成具体、可评分、可校验、可继续落题的创新点报告。

### 5.2 MVP 成功标准

```text
1. 只使用 resolved scope 内的 evidence、paper 和 graph context。
2. 每个候选创新点有 source_signal_ids。
3. 每个候选创新点有 supporting_evidence_ids，或明确 evidence_status=evidence_insufficient。
4. 每个候选创新点必须包含 gap、why_innovative、research_foundation、feasibility、risk、possible_topic。
5. scores 包含 novelty、evidence、feasibility、risk、fit、specificity、total。
6. 空泛创新点会被过滤、降分或标记 validation warning。
7. Project.discipline、education_level、research_goal 参与 fit 和 feasibility。
8. Report 中记录实际使用的 paper_ids、evidence_ids、graph_node_ids。
9. validation result 能说明通过、失败或警告原因。
10. 单测使用 fake LLM，不依赖真实模型。
```

### 5.3 非目标

MVP 不做：

```text
1. 全网自动检索来证明绝对新颖性。
2. 自动生成完整开题报告。
3. 自动给出完整实验方案和数据采集方案。
4. 自动判断顶刊级创新。
5. 自动替用户确认伦理审批、数据可得性和导师认可。
6. 没有证据时硬生成“看起来很新”的题目。
```

P2 后可扩展：

```text
external novelty check
proposal generator
experiment design assistant
topic title optimizer
advisor review workflow
```

## 6. 目标架构

### 6.1 服务拆分

```text
InnovationReportGenerator
  编排整体流程。

InnovationMaterialCollector
  从 Scope 中收集 evidence、paper cards、graph context、project profile、QA materials。

InnovationSignalCollector
  把 limitation、future_work、graph gap、method transfer 等转成 GapSignal。

GapSignalBuilder
  聚合同义 gap，计算 confidence，绑定 evidence/paper/graph IDs。

InnovationCandidateGenerator
  基于 GapSignal 生成候选 InnovationPoint。

InnovationScorer
  对候选计算 novelty/evidence/feasibility/risk/fit/specificity/total。

InnovationValidator
  校验 scope、证据存在性、泛化程度、字段完整性、重复候选。

InnovationRenderer
  渲染 Markdown 报告、摘要表和来源索引。

GraphWritebackService
  可选把 accepted candidate 写回图谱。
```

### 6.2 推荐调用链

```text
generate(project_id, scope_payload, options)
  -> resolve scope
  -> load project profile
  -> guard input scope
  -> collect materials
  -> build gap signals
  -> generate candidates
  -> score candidates
  -> filter / rank candidates
  -> validate candidates
  -> render report
  -> save report
  -> optional graph writeback
```

### 6.3 数据流

```text
scope_payload
  -> RetrievalScope
  -> InnovationMaterials
  -> list[GapSignal]
  -> list[InnovationCandidate]
  -> list[ScoredInnovationCandidate]
  -> InnovationReportValidationResult
  -> Report
```

### 6.4 依赖方向

```text
innovation_generator.py
  -> scope.py
  -> storage.py
  -> models.py
  -> llm_service.py
  -> innovation_signals.py
  -> innovation_scoring.py
```

不要让底层信号和评分模块反向依赖 ReportService 或 API 层。

## 7. 数据模型设计

### 7.1 InnovationMaterials

内部结构：

```python
class InnovationMaterials(BaseModel):
    project_id: str
    scope: RetrievalScope
    project: Project | None = None
    evidence_records: list[EvidenceRecord] = Field(default_factory=list)
    paper_cards: list[dict[str, Any]] = Field(default_factory=list)
    graph_context: dict[str, Any] = Field(default_factory=dict)
    qa_materials: list[dict[str, Any]] = Field(default_factory=list)
```

用途：

```text
统一保存候选生成所需材料。
避免每个函数直接访问 storage。
便于测试构造 fixture。
便于后续记录 source index。
```

### 7.2 GapSignal

推荐新增内部模型：

```python
class GapSignal(BaseModel):
    signal_id: str
    signal_type: str
    description: str
    normalized_key: str = ""
    topic: str = ""
    method: str = ""
    dataset_or_sample: str = ""
    population: str = ""
    outcome: str = ""
    source: str = ""
    supporting_evidence_ids: list[str] = Field(default_factory=list)
```

## 8. 创新信号来源

### 8.1 common_limitation

来源：

```text
EvidenceRecord.limitation
```

触发条件：

```text
1. 相同或相似 limitation 出现在 >= 2 篇论文。
2. 或单篇论文的 limitation 有明确 source_quote，且 evidence_strength != low。
3. 排除 unknown、none、not mentioned、空字符串。
```

需要输出：

```text
description = 归一化后的局限描述
supporting_evidence_ids = 提及该局限的 evidence
supporting_paper_ids = 对应 paper
source_quotes = 有来源句时保留
confidence = min(0.9, 0.4 + 0.1 * paper_count + source_quote_bonus)
```

当前代码只按完全相同字符串计数，需要增强：

```text
lowercase
trim punctuation
中英文常见同义词归一
简单 token overlap
可选 embedding 聚类
```

### 8.2 future_work_cluster

来源：

```text
EvidenceRecord.future_work
```

触发条件：

```text
1. future_work 非空且不是 unknown。
2. 多篇论文 future_work 指向相似方向时提升 confidence。
3. future_work 含有具体对象、方法、数据、场景时提升 specificity。
```

用途：

```text
future_work 是最直接的创新信号。
但不能原样复制为创新点，需要结合 finding/limitation 判断是否有研究基础和风险。
```

### 8.3 explicit_gap

当前旧 EvidenceRecord 没有 `evidence_type=gap`，但可从字段推断：

```text
limitation 中包含 lack/limited/insufficient/缺乏/不足/尚未
future_work 中包含 future work/should/explore/需要/建议/未来
citation_context 中提到 gap/open question
```

未来模型增强后：

```text
evidence_type == "gap"
possible_gap 非空
```

### 8.4 graph_gap

来源：

```text
KnowledgeGraph nodes/edges
NodeType.GAP
SUGGESTS_GAP edges
Topic-Method coverage
Topic-Dataset coverage
```

当前 `detect_graph_gaps()` 只做 topic 下 method 数量判断，P1 应增强为：

```text
1. 读取已有 Gap 节点。
2. 从 Paper -> HAS_LIMITATION -> Limitation -> SUGGESTS_GAP 追溯 evidence。
3. 计算 Topic x Method 覆盖矩阵。
4. 计算 Topic x Dataset 覆盖矩阵。
5. 只对 evidence_count >= 1 或 graph_confidence >= threshold 的 gap 生成候选。
```

### 8.5 method_gap

触发条件：

```text
同一 topic 下 method 分布过于单一。
同一 research_question 在相邻 topic 中有成熟方法，但当前 topic 未使用。
当前 topic 的 limitation 指向方法不足。
```

注意：

```text
不能只因为 method_count < 2 就判断有创新机会。
必须结合 evidence 中的 limitation/future_work 或相邻 topic 的成功方法。
```

### 8.6 method_transfer

示例：

```text
Topic A 中 Method X 有多篇 evidence 支撑。
Topic B 与 Topic A 在对象或研究问题上相似。
Topic B 中未出现 Method X。
Topic B 的 limitation/future_work 指向需要更细粒度、更可解释或更长期的方法。
```

输出候选时必须说明：

```text
从哪个 topic 迁移到哪个 topic。
迁移的前提条件。
为什么不是机械拼接。
潜在数据和方法风险。
```

### 8.7 dataset_gap / context_gap

来源字段：

```text
EvidenceRecord.data_or_sample
PaperCard.sample
PaperCard.context
Graph Dataset nodes
```

常见信号：

```text
样本集中在单一地区。
只覆盖大学生或成人，缺少 K-12 / 老年人 / 特定群体。
数据集规模小。
只使用横截面数据，缺少纵向数据。
只在实验室场景，缺少真实应用场景。
```

注意：

```text
“扩大样本规模”本身是空泛建议。
必须具体到样本类型、场景、变量和可行数据来源。
```

### 8.8 contradiction

当前实现可以先做轻量版：

```text
同一 topic/outcome 下 finding 表述相反。
同一 method 在不同 paper 中结论不一致。
limitation 指向结果不稳定或外部效度不足。
```

未来 EvidenceRecord 增强后：

```text
evidence_relation == contradicts
claim_id 相同但 polarity 不同
```

争议型候选需要：

```text
supporting_evidence_ids
limiting_evidence_ids
risk >= 0.5
why_innovative 说明“解决争议”或“解释异质性”
```

### 8.9 evidence_insufficiency

当 Scope 内证据不足时，不应强行生成高置信创新点。

可输出：

```text
候选类型：补充检索方向 / 证据缺口
evidence_status = evidence_insufficient
total_score 降低
suggested_actions = 扩大 scope / 搜索关键词 / 导入更多论文
```

## 9. 候选生成策略

### 9.1 规则优先的候选骨架

在调用 LLM 前，先从 GapSignal 构建候选骨架：

```text
candidate.name
candidate.gap
candidate.source_signal_ids
candidate.supporting_evidence_ids
candidate.supporting_paper_ids
candidate.limiting_evidence_ids
candidate.graph_node_ids
candidate.innovation_type
```

这样可以避免 LLM 自造来源。

### 9.2 LLM 的职责

LLM 只负责：

```text
把候选骨架改写成自然语言。
补全 why_innovative。
补全 research_foundation。
补全 feasibility。
补全 risk。
生成 possible_topic。
在给定证据内选择最合适的 candidate framing。
```

LLM 不负责：

```text
创建不存在的 evidence_id。
扩大 scope。
判断外部文献绝对没有做过。
凭空添加方法和数据。
```

### 9.3 降级生成

LLM 失败时仍可生成报告，但要透明标记：

```text
generation_mode = fallback
candidate.description = 规则模板
confidence 降低
validation warning 包含 llm_failed
```

降级模板示例：

```text
针对 "{gap_description}"，可考虑在 "{topic}" 场景下，围绕 "{method_or_dataset}" 设计更具体的研究问题。
该方向的依据是 {paper_count} 篇论文共同提到的局限或未来工作。
当前风险是 {risk_summary}。
```

## 11. 评分体系

### 11.1 评分维度

| 维度 | 含义 | 主要依据 |
| --- | --- | --- |
| novelty | 是否来自明确空白、争议、结构缺口或方法迁移 | GapSignal 类型、图谱覆盖、候选表述 |
| evidence | 支撑证据数量和质量 | evidence_count、paper_count、evidence_strength、source_quote |
| feasibility | 用户当前条件下是否可做 | method、data_or_sample、education_level、资源要求 |
| risk | 数据、伦理、方法、证据冲突、外部效度风险 | limitation、contradiction、数据约束 |
| fit | 是否匹配用户项目 | discipline、research_goal、preferred_types |
| specificity | 是否具体到对象、方法、变量、场景、产出 | 文本结构和字段完整度 |

所有维度取值范围：

```text
0.0 - 1.0
```

### 11.2 novelty 规则

加分：

```text
+0.25 来自 future_work_cluster 或 explicit_gap
+0.20 来自 graph_gap 且有 evidence 支撑
+0.20 来自 contradiction
+0.15 来自 method_transfer，且迁移关系解释清楚
+0.10 gap 在多篇论文中出现
```

扣分：

```text
-0.30 描述只是“扩大样本”“优化算法”“结合大模型”等泛化表达
-0.20 没有明确 gap
-0.15 只是重复已有 finding
```

### 11.3 evidence 规则

加分：

```text
+0.20 supporting_evidence_ids >= 2
+0.15 supporting_paper_ids >= 2
+0.15 有 source_quote/source_chunk_id
+0.15 evidence_strength 包含 high
+0.10 review_status == accepted
```

扣分：

```text
-0.30 supporting_evidence_ids 为空且 evidence_status != evidence_insufficient
-0.20 全部 evidence_strength == low
-0.20 review_status == rejected
-0.15 evidence 只来自同一篇 paper
```

### 11.4 feasibility 规则

加分：

```text
+0.20 方法在 Scope 中已有先例
+0.15 数据类型明确
+0.15 可用小规模实验、问卷、访谈、公开数据或二次分析完成
+0.10 与用户 education_level 匹配
```

扣分：

```text
-0.30 本科/硕士项目但候选需要大规模预训练、长期 RCT、多中心临床实验
-0.20 数据不可得或涉及敏感数据
-0.20 方法要求明显超出当前研究目标
-0.15 没有说明可操作路径
```

### 11.5 risk 规则

风险不是坏事，但必须被说明。风险越高，`risk` 分越高，总分中扣除。

加风险：

```text
+0.25 有 contradicting evidence
+0.20 数据获取困难
+0.20 伦理或隐私风险
+0.15 样本代表性不足
+0.15 方法复杂度高
+0.10 证据基础较弱
```

降低风险：

```text
-0.10 Scope 内已有类似方法成功应用
-0.10 候选提供了明确降级方案
```

### 11.6 fit 规则

加分：

```text
+0.25 candidate topic 命中 Project.research_goal
+0.20 discipline 匹配
+0.15 innovation_type 匹配 preferred_types
+0.10 possible_topic 与用户项目描述一致
```

扣分：

```text
-0.20 与 discipline 明显不匹配
-0.20 与 research_goal 无关
-0.15 题目范围明显大于用户项目能力
```

### 11.7 specificity 规则

加分：

```text
+0.15 有具体研究对象
+0.15 有具体方法
+0.15 有具体数据或样本
+0.15 有具体场景
+0.15 有具体 outcome/变量
+0.10 possible_topic 可直接作为论文题目初稿
```

扣分：

```text
-0.40 只有“提高”“优化”“探索”“结合”等动词，无对象和方法
-0.25 没有 possible_topic
-0.20 description 少于 25 个中文字且无结构信息
-0.20 risk/feasibility 空泛
```

### 11.8 总分

推荐公式：

```text
total =
  0.25 * novelty
+ 0.25 * evidence
+ 0.20 * feasibility
+ 0.15 * fit
+ 0.15 * specificity
- 0.15 * risk
```

排序规则：

```text
total desc
evidence desc
specificity desc
risk asc
innovation_id asc
```

默认筛选：

```text
total >= 0.45
specificity >= 0.50
scope_violation_count == 0
```

## 13. Scope 与证据追踪契约

### 13.2 输出侧 ScopeGuard

```python
used_evidence_ids = sorted(unique(

    evidence.paper_id for evidence in used_evidence
    + candidate.supporting_paper_ids

used_graph_node_ids = sorted(unique(
    candidate.graph_node_ids + signal.graph_node_ids

```

## 15. 与 ReportService 集成

### 15.1 当前问题

当前 `generate()` 直接：

```python
self.storage.upsert_item("reports", report.report_id, report.model_dump())
```

问题：

```text
1. 绕过 ReportService 的版本管理。
2. 不便统一导出。
3. 不便记录日志和质量校验。
4. 后续报告更新难以追踪。
```

### 15.2 推荐方案

P1 引入：

```python
ReportService.create_report(...)
ReportService.update_report(...)
ReportService.add_version(...)
```

如果 ReportService 尚未准备好，P0 先保持 storage 写入，但封装成方法：

```python
def save_report(self, report: Report, validation_result: InnovationReportValidationResult) -> Report:
    ...
```

这样后续替换存储方式不会影响生成逻辑。

## 16. 图谱回写设计

### 16.1 回写条件

不是所有候选都写回图谱。默认只写：

```text
status == accepted
validation passed
total_score >= 0.6
supporting_evidence_ids 非空
source_signal_ids 非空
```

用户可以在前端确认后写回：

```text
candidate -> accept -> writeback
candidate -> reject -> do not writeback
candidate -> revise -> update candidate then writeback
```

### 16.2 节点设计

```python
GraphNode(
    node_id="innovation_<stable_hash>",
    node_type=NodeType.INNOVATION,
    label=candidate.name,
    properties={
        "description": candidate.description,
        "possible_topic": candidate.possible_topic,
        "scores": candidate.scores,
        "supporting_evidence_ids": candidate.supporting_evidence_ids,
        "supporting_paper_ids": candidate.supporting_paper_ids,
        "status": "accepted",
    },
)
```

### 16.3 边设计

```text
Gap -> SUPPORTS_INNOVATION -> InnovationPoint
Evidence -> SUPPORTS_INNOVATION -> InnovationPoint
Topic -> RELATED_TO -> InnovationPoint
Method -> RELATED_TO -> InnovationPoint
```

当前 `EdgeType` 只有 `SUPPORTS_INNOVATION` 可直接用。其他关系可先存在 properties：

```json
{
  "relation_role": "evidence_support",
  "source_signal_id": "sig_1"
}
```

### 16.4 稳定 ID

避免随机 ID 影响测试和增量更新：

```text
innovation_id = "ip_" + stable_hash(project_id + normalized_name + sorted(source_signal_ids))
signal_id = "sig_" + stable_hash(project_id + signal_type + normalized_key + sorted(evidence_ids))
```

`uuid` 仍可作为 fallback，但不应用于 golden test 的核心路径。

## 24. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| LLM 生成漂亮但无依据的创新点 | 输出无法追溯 | 规则骨架 + evidence_id 强校验 |
| Scope 越界 | 引用未选论文 | 输入/输出双重 ScopeGuard |
| 空泛建议通过 | “大模型赋能”“提高效果” | specificity score + generic filter |
| 图谱 gap 假阳性 | 低连接不等于真空白 | graph gap 必须结合 evidence 或低置信标记 |
| 多篇低质量证据误判高分 | evidence_count 高但质量低 | evidence_strength/review_status/source_quote 加权 |
| 用户项目不匹配 | 题目太大或跨学科过远 | Project fit 和 feasibility 评分 |
| 测试不稳定 | 真实 LLM 输出随机 | Fake LLM + schema-level assertion |
