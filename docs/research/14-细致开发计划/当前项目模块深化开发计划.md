### 1.3 当前风险最高的不一致

```text
1. storage_backend/postgres/vector_storage 已进入代码，但多数文档仍只按 JSONStorage 规划。
2. ProjectService 对 PostgreSQL 和 JSON 的逻辑不完全一致，update/delete/stats 仍偏 JSON 路径。
3. API 文档中部分端点路径仍是旧 `/api/rw/papers/{id}`，当前 app 使用项目作用域路径居多。
4. SearchOrchestrator 已有完整响应，但 API 搜索响应仍主要返回 session/results/result_count。
5. adapter 仍会在部分异常时返回空列表，source_stats/errors 无法完整传到前端。
6. evaluation/llm 子包已经存在，但旧文档仍写根目录文件名。
7. config.yaml 默认 `storage_backend: postgres`，但测试和本地运行需要明确 JSON fallback。
```

## 2. 下一轮开发主线

下一轮开发建议不要继续横向扩功能，而是先把已有后端闭环收敛成稳定产品骨架。

### Sprint A：存储后端收敛

目标：

```text
让 JSONStorage 和 PostgresStorage 对 service 层表现一致，保证当前配置不会破坏 API 和测试。
```

任务：

```text
A1. 定义 collection/table 契约表：projects、papers、paper_cards、evidence_records、graphs、reports、report_versions、tasks、search_sessions、search_cache、papers_pool。
A2. 让 ProjectService 的 create/list/get/update/delete/stats 在 JSON 和 PostgreSQL 下行为一致。
A3. `get_storage_backend()` 与 `get_storage()` 的职责分清：全局后端选择不应破坏测试注入。
A4. PostgresStorage 增加与 JSONStorage 一致的 project scoped 行为或明确不支持项目目录作用域。
A5. API health 返回 storage_backend、postgres_available、vector_storage、degraded_reason。
A6. 所有默认测试继续使用 tmp_path JSONStorage，不依赖 PostgreSQL。
```

验收：

```text
python -m pytest tests/agents_v3/research_workspace/test_storage.py
python -m pytest tests/agents_v3/research_workspace/test_project_service.py
python -m pytest tests/agents_v3/research_workspace/test_api.py
```

阻塞条件：

```text
storage_backend=postgres 但本地没有数据库时 API 无法启动。
JSON 与 PostgreSQL 下同一 service 返回字段不一致。
测试误写真实 data/research_workspace。
```

### Sprint B：搜索链路产品化

目标：

```text
把搜索从“能跑”推进到“前端可解释、可筛选、可入库、可诊断”。
```

任务：

```text
B1. API `/papers/search` 改为复用 SearchOrchestrator，保留 SearchSession 暂存。
B2. 搜索响应暴露 `source_stats`、`errors`、`cache_hit`、`elapsed_ms`、`duplicate_groups`。
B3. factory 默认源与 config 对齐：OpenAlex、CrossRef、arXiv、Semantic Scholar。
B4. 修正 Semantic Scholar fields，不请求不支持字段；429/400 读取响应体并转 SearchErrorInfo。
B5. CrossRef 进入默认 factory，并用于 DOI 导入元数据补全。
B6. SearchField 贯穿 API DTO、SearchQuery、adapter `_resolve_field()` 和测试。
B7. `require_pdf` 真正参与过滤或标记，不只是模型字段。
B8. papers_pool 与项目 papers 的关系文档化：全局候选池不等于项目论文库。
```

验收：

```text
python -m pytest tests/agents_v3/research_workspace/test_search_models.py
python -m pytest tests/agents_v3/research_workspace/test_search_orchestrator.py
python -m pytest tests/agents_v3/research_workspace/test_search_session.py
python -m pytest tests/agents_v3/research_workspace/test_api.py
```

阻塞条件：

```text
某个 source 失败导致整个搜索失败。
用户看不到 source 失败原因。
commit 同一结果重复创建论文。
```

### Sprint C：解析、卡片、证据质量硬化

目标：

```text
保证进入 QA/综述/创新点的材料都有可追溯来源和质量标签。
```

任务：

```text
C1. ParserService 的 ParseResult、PaperChunk、Paper.status 更新规则固化。
C2. PDF 下载失败、解析失败、空文本、低质量 OCR 分别有 error_message 和 quality_flags。
C3. PaperCardGenerator 的 quality_report 必须持久化或可按 paper_id 重算。
C4. source_spans 校验从“生成时检查”升级为独立 quality gate。
C5. EvidenceRecord 增加或通过 metadata 记录 evidence_type/review_status/confidence/source_quote_status。
C6. EvidenceTableService 不接受 excluded paper 的 evidence。
C7. 证据构建后输出项目级统计：accepted/pending/no_source/weak/generic。
```

验收：

```text
python -m pytest tests/agents_v3/research_workspace/test_parser_service.py
python -m pytest tests/agents_v3/research_workspace/test_paper_card_generator.py
python -m pytest tests/agents_v3/research_workspace/test_evidence_table_service.py
```

阻塞条件：

```text
解析失败被标记为 parsed。
PaperCard 无来源却高置信。
EvidenceRecord 无 paper_id/project_id。
```

### Sprint D：Scope、QA、报告可信度收敛

目标：

```text
让所有生成结果都能说明“基于哪些论文/证据/图谱范围”，证据不足时明确拒答或降级。
```

任务：

```text
D1. RetrievalScopeService 输出 empty_reason、scope_summary、filter_diagnostics。
D2. ScopeGuard 独立化：QA、Review、Innovation、Report 保存前都调用。
D3. ScopeQAResponse 的 supporting_papers/evidence_records 必须存在且在 scope 内。
D4. ReviewGenerator 的 section_sources 覆盖主体章节。
D5. InnovationReportGenerator 的每个候选必须绑定 gap/supporting_papers/limiting_evidence。
D6. ReportService 保存 report 时写入 scope_snapshot、source_snapshot、validation_result。
D7. Markdown 导出包含 scope、paper list、evidence index、warnings。
```

验收：


### Sprint F：评估与可观测性落地

目标：

```text
把 evaluation 子包从测试工具推进为每次 smoke 和报告生成后的质量门禁。
```

任务：

```text
F1. 统一从 `evaluation/` 子包导出 evaluator/gates/golden/logging_utils/metrics。
F2. LLMService 每次调用记录 metric：model、prompt_name、latency、success、error_type、json_repair。
F3. SearchOrchestrator 记录 provider latency、count、cache_hit、error_category。
F4. Parser/Card/Evidence/Graph/Scope/Report 各输出最小 metric。

F6. redaction_check 覆盖 API key、Bearer、完整 prompt、raw_response、PDF 长文本。
```

## 4. 当前优先级建议

按风险和收益排序：

```text
1. 先收敛存储后端一致性，避免 PostgreSQL 配置影响本地运行和测试。
2. 再统一搜索 API 使用 SearchOrchestrator，让搜索结果可解释。
3. 再强化证据和 ScopeGuard，保证生成可信。
4. 最后做前端联调和质量门禁脚本。
```

不建议当前马上做：

```text
1. Neo4j 或重型 GraphRAG。
2. 多用户权限系统。
3. 外部监控 SaaS 强依赖。
4. 自动抓取 Google Scholar。
5. 大规模向量检索重构。
```
