## 1. PostgreSQL + JSONB

### 1.1 核心概念与定义

**PostgreSQL** 是世界上最先进的开源关系型数据库管理系统（据 Stack Overflow 2024 年度调查，超过 48.7% 的开发者正在使用 PostgreSQL，连续第二年成为最受欢迎的数据库）。**JSONB** 是 PostgreSQL 内置的二进制 JSON 数据类型，以二进制格式存储 JSON 数据，支持索引和高效查询，比普通 JSON 类型具有更好的性能表现。

### 1.2 JSONB 存储优势

根据搜索结果，JSONB 的核心优势包括：

- **二进制存储**：数据在存储时已经解析为二进制格式，无需每次查询时重新解析，查询速度更快
- **支持索引**：可以通过 GIN 索引或表达式索引加速查询
- **结构化与非结构化混合存储**：可以将结构化字段和 JSONB 字段放在同一张表中，支持 JOIN 操作
- **继承 ACID 特性**：享有 PostgreSQL 完整的事务支持，而 MongoDB 等文档数据库在默认配置下可能不支持事务

**对比 MongoDB 的优势**（据 AWS 官方对比分析及社区讨论）：

- PostgreSQL 支持 ACID 事务，保证数据一致性
- 可以与现有关系型数据模型混合存储
- 一个数据库同时支持结构化和半结构化数据
- 成熟的生态和丰富的扩展（如 pgvector 向量扩展）

### 1.3 性能优化实践

**JSONB 索引策略**（据 SitePoint 2026 年 2 月发布的性能指南）：

| 索引类型 | 适用场景 | 特点 |
|---------|---------|------|
| GIN 索引（jsonb_ops） | 灵活查询，跨多键搜索 | 支持 @>、?、| 等操作符，索引体积较大 |
| GIN 索引（jsonb_path_ops） | 仅包含查询（@>） | 索引体积更小，不支持 existence 查询 |
| B-tree 表达式索引 | 范围检索、特定字段检索 | 适用于需要数值范围或排序的场景 |

**最佳实践建议**：

- 将频繁更新或过滤的 JSONB 键提升为独立的类型列（Typed Columns），当访问模式稳定后进行此优化
- 使用 `jsonb_path_query_array()` 进行深度路径查询
- 合理使用 `EXPLAIN ANALYZE` 分析查询计划

### 1.4 PostgreSQL 17 新特性（2024 年 9 月发布）

根据 PostgreSQL 官方发布公告及技术博客分析：

| 特性 | 描述 |
|------|------|
| **JSON_TABLE 命令** | SQL/JSON 新函数，将 JSON 数据转换为标准关系表，类似 MySQL 的 JSON_TABLE 功能 |
| **Vacuum 内存优化** | 引入新的 vacuum 内部内存结构，将内存消耗降低 20 倍 |
| **WAL 写入优化** | WAL 写入速度提升 2 倍 |
| **逻辑复制改进** | 支持一键增量备份、更好的故障转移支持 |
| **MERGE 增强** | 为 MERGE 语句添加更多特性，用于条件更新 |

### 1.5 技术难点与解决方案

| 难点 | 解决方案 |
|------|----------|
| JSONB 数据膨胀 | 使用表达式索引精简查询路径，定期进行 VACUUM |
| 深层嵌套查询性能差 | 使用 `jsonb_path_query` 配合表达式索引，或将嵌套数据展平 |
| GIN 索引体积过大 | 使用 `jsonb_path_ops` 替代 `jsonb_ops`，或按访问模式将关键字段提取为独立列 |
| 事务 ID 耗尽 | 配置 `autovacuum_freeze_max_age`，确保自动冷冻机制正常工作 |

### 1.6 实际应用案例

1. **聊天会话存储**：将每条消息存储为 JSONB 数组，支持动态追加消息，索引用户 ID 和时间戳字段实现高效查询
2. **文献数据存储**：将论文元数据（作者、摘要、关键词、引用关系）存储为 JSONB，支持灵活扩展字段
3. **电商订单系统**：订单主体存关系表，商品列表动态字段存 JSONB，兼顾查询效率和扩展灵活性

## 2. Neo4j 图数据库

### 2.1 核心概念与定义

**Neo4j** 是目前最流行的原生图数据库（Native Graph Database），采用 Java 和 Scala 语言开发，专属查询语言为 Cypher。其将结构化数据存储在网络（图）结构上而非表中，具备成熟数据库的所有特性，包括完全的事务支持（ACID）。

Neo4j 的核心概念：

- **节点（Nodes）**：表示实体，可带标签和属性
- **关系（Relationships）**：表示实体之间的连接，始终有方向
- **属性（Properties）**：节点和关系都可以包含键值对属性
- **标签（Labels）**：用于标识节点类型

### 2.2 官方文档和架构

**Neo4j 5.x 架构特性**（据 Neo4j 官方 Wiki 及技术博客）：

- **存储引擎**：使用自定义的图存储格式，节点和关系以数组形式存储，通过 ID 直接寻址实现免索引遍历
- **事务管理**：支持 ACID 事务，write-through 缓存机制
- **查询引擎**：Cypher 查询语言经过优化，支持成本估算器（Cost Estimator）
- **原生内核**：Cypher 执行引擎采用 Volcano/Jorge 风格的成本模型

**Infinigraph 架构**（2025 年 9 月发布，据腾讯新闻）：

- 允许在单一图数据库平台上同时运行操作和分析工作负载
- 处理规模超过 100TB，无需分割图结构
- 统一了实时事务处理与图分析处理

### 2.3 Cypher 查询语言最佳实践

| 实践领域 | 建议 |
|---------|------|
| **模式匹配** | 使用参数化查询而非字符串拼接，避免 Cypher 注入风险 |
| **索引使用** | 为高频查询属性创建索引（`CREATE INDEX FOR (p:Person) ON (p.name)`） |
| **关系遍历深度** | 限制遍历深度（使用 `LIMIT` 或路径长度限制），避免全图扫描 |
| **批量操作** | 使用 `USE IN Transactions` 批处理或 APOC 库的批量过程 |
| **查询优化** | 利用 `EXPLAIN` 和 `PROFILE` 分析查询计划 |
| **OPTIONAL MATCH** | 用于可能不存在的匹配，避免空值问题 |
| **MERGE** | 用于创建或匹配操作，确保幂等性 |

## 3. pgvector — PostgreSQL 向量扩展

### 3.1 核心概念与定义

**pgvector** 是 PostgreSQL 的开源向量相似度搜索扩展，由 Ankane 开发维护（GitHub 仓库：https://github.com/pgvector/pgvector）。它将向量数据类型、运算符和索引方法引入 PostgreSQL，允许用户直接在数据库中进行向量相似性搜索。

### 3.2 官方 GitHub 仓库信息

| 指标 | 数值 |
|------|------|
| GitHub Stars | 17,000+ |
| 最新版本 | 0.8.0（截至 2025 年初） |
| 支持的 PostgreSQL 版本 | 12-18 |
| 编程语言 | C |

### 3.3 技术原理深度解析

**向量数据类型支持**：

- 单精度浮点向量（默认）
- 半精度浮点向量
- 二进制向量（Binary vectors）
- 稀疏向量（Sparse vectors）

**距离度量**（据 pgvector 官方文档）：

| 操作符 | 类型 | 描述 |
|--------|------|------|
| `<->` | L2 距离 | 欧几里得距离 |
| `<#>` | 内积 | Inner Product |
| `<=>` | 余弦距离 | Cosine Distance |
| `<+>` | L1 距离 | Manhattan Distance |
| `<~>` | 汉明距离 | Hamming Distance |
| `<%>` | Jaccard 相似度 | Jaccard Similarity |

**索引算法**：

- **HNSW（Hierarchical Navigable Small World）**：基于图的近似最近邻搜索，构建速度快，查询性能优秀，支持参数 `m` 和 `ef_construction`
- **IVFFlat（Inverted File with Flat）**：基于聚类的索引，需要先有数据，支持参数 `lists`

### 3.4 与 LangChain/LlamaIndex 集成

**LangChain 集成**（据 CSDN 2024-2025 年多篇技术博客）：

```python
from langchain_postgres import PGVector
from langchain_openai import OpenAIEmbeddings

collection_name = "my_docs"
connection = "postgresql+psycopg://user:pass@localhost:6024/langchain"
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

vectorstore = PGVector.from_documents(
    documents=documents,
    embedding=embeddings,
    collection_name=collection_name,
    connection_string=connection,
    pre_delete_collection=False
)
```

**LlamaIndex 集成**：LlamaIndex 提供 `PGVectorStore` 类，支持与 pgvector 的无缝集成。

## 4. Qdrant 向量数据库

### 4.1 核心概念与定义

**Qdrant**（读作 "quadrant"）是由 Rust 语言编写的高性能、大规模向量相似度搜索引擎，提供生产级服务并配有便捷的 API，支持存储、搜索和管理带有额外载荷（payload）的向量点。

### 4.2 官方文档和架构

**架构特点**（据 Qdrant 官方文档及 GitHub 仓库）：

- **Rust 语言编写**：提供极高的性能和可靠性
- **HNSW 图算法**：默认使用分层可导航小世界图算法
- **混合搜索**：支持稠密向量和稀疏向量
- **过滤支持**：在 HNSW 遍历期间直接应用过滤条件，无需预过滤或后过滤
- **多模态支持**：每个对象支持多个向量
- **重新排序**：支持分数提升、Token 级重新排序、MMR 多样性算法

**技术规格**（据 Qdrant 官网 2026 年数据）：

- 25,000+ GitHub Stars
- 60,000+ 社区成员
- SOC2 & HIPAA 合规
- 支持云端部署、本地部署和边缘部署

### 4.3 与 Python/JS 集成

**Python 客户端**（据 CSDN 多篇教程 2024-2025 年）：

```python
from qdrant_client import QdrantClient
from qdrant_client.models import Distance, VectorParams, PointStruct

client = QdrantClient(host="localhost", port=6333)

client.create_collection(
    collection_name="my_collection",
    vectors_config=VectorParams(size=1536, distance=Distance.COSINE)
)

client.upsert(
    collection_name="my_collection",
    points=[PointStruct(id="1", vector=[0.1]*1536, payload={"city": "Berlin"})]
)
```

## 5. PostgreSQL TTL 索引方案 — 用户会话过期

### 5.1 实现方案

**PostgreSQL 本身不提供内置的 TTL 机制**，但可以通过以下方案实现会话过期：

**方案一：定期清理任务（cron/pgAgent）**

```sql
-- 创建会话表
CREATE TABLE user_sessions (
    session_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL,
    data JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_accessed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 创建索引
CREATE INDEX idx_sessions_expire ON user_sessions (created_at);

-- 定期删除过期会话
DELETE FROM user_sessions
WHERE created_at < NOW() - INTERVAL '7 days';
```

**方案二：基于 AutoVacuum 的自动清理**

PostgreSQL 的 AutoVacuum 机制可用于自动清理过期数据：

```sql
-- 设置表级别的 autovacuum 参数（需 PostgreSQL 12+）
ALTER TABLE user_sessions SET (
    autovacuum_vacuum_threshold = 100,
    autovacuum_vacuum_scale_factor = 0.1
);
```

**方案三：分区表策略（推荐生产环境使用）**

```sql
-- 创建按月分区的会话表
CREATE TABLE user_sessions (
    session_id UUID,
    user_id UUID,
    data JSONB,
    created_at TIMESTAMPTZ
) PARTITION BY RANGE (created_at);

-- 创建当月分区
CREATE TABLE user_sessions_2025_05 PARTITION OF user_sessions
    FOR VALUES FROM ('2025-05-01') TO ('2025-06-01');

-- 旧分区直接 DROP 即可
DROP TABLE user_sessions_2025_04;
```

### 5.2 最佳实践

| 实践 | 建议 |
|------|------|
| **TTL 时长设置** | 根据业务需求设置合理的过期时间（如 7 天、30 天） |
| **分区策略** | 按时间分区，简化过期数据清理 |
| **索引设计** | 为 `created_at` 和 `user_id` 创建复合索引 |
| **清理时机** | 在低峰期执行清理任务，使用 `DELETE` 而非 `TRUNCATE`（保留事务日志） |
| **AutoVacuum 配置** | 合理配置 `autovacuum_vacuum_threshold` 和 `autovacuum_vacuum_scale_factor` |
| **监控** | 监控表的膨胀率（bloat）和 dead tuples |
| **批量清理** | 使用分批删除避免锁表：`DELETE WHERE ... LIMIT 1000` |

### 5.3 AutoVacuum 原理与调优

根据搜索结果，AutoVacuum 的核心工作原理：

- **触发条件**：dead tuples 数量 > `pg_class.reltuples * autovacuum_vacuum_scale_factor + autovacuum_vacuum_threshold`
- **事务 ID 冻结**：防止事务 ID 环回（wraparound）
- **性能影响**：通过 `autovacuum_vacuum_cost_limit` 和 `autovacuum_vacuum_cost_delay` 控制清理速度

### 6.2 本项目技术选型建议

基于调研结果，为当前项目推荐以下技术组合：

**推荐的持久化技术组合**：

| 数据类型 | 推荐方案 | 理由 |
|---------|----------|------|
| **聊天会话数据** | PostgreSQL + JSONB | JSONB 支持灵活存储消息结构，ACID 保证一致性，配合分区表实现 TTL 过期 |
| **文献数据** | PostgreSQL + JSONB | 结构化字段（标题、作者）与动态字段（元数据）混合存储，统一数据库运维 |
| **论文数据** | PostgreSQL + JSONB | 支持丰富的论文元数据和复杂查询 |
| **知识图谱数据** | Neo4j | 原生图数据库，Cypher 查询语言高效处理多跳关系，适合构建学术关系图谱 |
| **向量嵌入数据** | pgvector（首选）/ Qdrant（备选） | 若已有 PostgreSQL 环境，pgvector 是最小成本方案；若追求极致向量搜索性能，Qdrant 是更专业选择 |
| **会话过期管理** | PostgreSQL 分区表策略 | 按月分区，月末自动清理历史分区，与 JSONB 存储共用同一数据库 |

**详细选型理由**：

1. **统一 PostgreSQL 栈**：项目已在使用 PostgreSQL，通过 JSONB + pgvector 的组合，可以统一管理结构化数据、半结构化文档和向量数据，大幅降低运维复杂度

2. **知识图谱选择 Neo4j**：知识图谱的核心是实体关系的多跳遍历，Neo4j 的原生图存储和 Cypher 查询语言在复杂关系查询场景下具有无可比拟的优势，配合 LlamaIndex 的 GraphRAG 实现效果更佳

3. **TTL 方案**：使用 PostgreSQL 分区表作为会话存储，每月一个分区，历史数据通过 DROP 分区实现自动过期，零运维成本

4. **pgvector vs Qdrant 的选择逻辑**：
   - 如果向量数据规模在千万级别以内，且希望复用现有 PostgreSQL 环境 → 选择 **pgvector**
   - 如果向量数据规模在亿级以上，且对查询性能有极致要求 → 选择 **Qdrant**
