## 1. 引用立场分类（Citation Stance）

### 1.1 问题定义

判断一条引用的立场是 **Supporting**（支持）、**Contrasting**（对比）还是 **Mentioning**（中性提及）。当前方案计划本地部署 DeBERTa 微调模型。

### 1.2 方案 A：Scite.ai API

**产品概述**：
Scite.ai 是目前最成熟的引用立场分类商业产品，已处理超过 **12 亿条引用声明**，覆盖 **1.85 亿篇** 文章，与 30+ 家出版商合作。

**API 能力**：
- 提供 Smart Citations API，可按 DOI/PMID 查询引用声明及其立场分类
- 返回 Supporting / Contrasting / Mentions 三分类结果
- 包含引用上下文原文（citation statement text）

**访问方式与定价**：

| 层级 | 价格 | API 访问 | 说明 |
|------|------|----------|------|
| Free | $0 | 有限 Web 查询 | 仅浏览器搜索，无 API |
| Individual | ~$10-20/月 | 无标准 API | 个人研究者 Web 使用 |
| Institutional | 联系销售 | 有 API | 高校/机构批量授权 |
| Enterprise/API | 联系销售 | 完整 API | 批量数据、高 QPS |

**限制**：
- **无公开的自助式 API 定价**，必须联系 sales@scite.ai 获取报价
- API 主要面向机构客户，个人开发者获取门槛较高
- 引用立场分类结果依赖 Scite 自己的模型，无法自定义分类体系
- 数据覆盖取决于出版商合作范围，部分论文可能无 Smart Citations

**适用性评估**：
- 优势：数据量大、质量高、无需自己训练模型
- 劣势：成本不透明、依赖第三方服务、无法定制、API 获取门槛高
- **结论：不推荐作为主要方案**。Scite 更适合作为数据源参考，而非实时 API 依赖。

### 1.3 方案 B：LLM 零样本分类（GPT-4 / Claude）

**核心思路**：
用大语言模型（如 GPT-4o、Claude Sonnet）通过精心设计的 Prompt 进行零样本引用立场分类，替代本地 DeBERTa 微调模型。

**Prompt 设计示例**：
```
你是一位学术引用分析专家。请判断以下引用声明对被引论文的立场。

引用声明（citing sentence）："{citation_context}"
被引论文标题："{cited_title}"

请从以下三个类别中选择一个：
- SUPPORTING: 引用为被引论文的观点提供了支持或确认
- CONTRASTING: 引用对被引论文的观点提出了质疑、反驳或对比
- MENTIONING: 中性引用，仅作为背景或一般性参考

只返回类别名称，不需解释。
```

**性能对比（基于学术文献和实践经验）**：

| 模型 | 方法 | 准确率 (F1) | 延迟 | 成本 |
|------|------|------------|------|------|
| DeBERTa-v3-large | 微调（SciCite 数据集） | ~88-92% | <10ms/条 | 本地 GPU |
| SciBERT | 微调（SciCite 数据集） | ~85-88% | <10ms/条 | 本地 GPU |
| GPT-4o | 零样本 | ~78-85% | 500ms-2s/条 | ~$0.002/条 |
| Claude Sonnet | 零样本 | ~76-83% | 500ms-2s/条 | ~$0.001/条 |
| GPT-4o-mini | 零样本 | ~72-80% | 200ms-1s/条 | ~$0.0003/条 |

**关键发现**：
- LLM 零样本分类准确率通常比微调模型 **低 5-12 个百分点**
- LLM 在 Supporting vs Mentioning 的区分上表现尚可，但在 **Contrasting（对比）** 类别上召回率偏低
- LLM 优势在于零样本、无需标注数据、可灵活调整分类体系
- 批量处理时 API 成本可控：1000 条引用约 $0.2-2.0

**优化策略**：
1. **Few-Shot 提示**：提供 3-5 个标注示例，可提升 3-5 个百分点
2. **CoT 推理**：要求模型先分析语言信号再分类，提升对比类召回率
3. **批量处理**：使用 Batch API（GPT-4o batch 价格减半）
4. **混合策略**：LLM 初筛 + 高置信度直接采信 + 低置信度人工复核

**适用性评估**：
- 优势：零部署、零标注、灵活可调、随 LLM 升级自动提升
- 劣势：准确率略低于微调模型、有 API 延迟和成本、存在幻觉风险
- **结论：推荐作为 MVP 阶段方案**。对于论文知识库场景，85% 左右的准确率可接受，后续可按需微调本地模型。

### 1.4 方案 C：本地 DeBERTa 微调（当前方案）

| 维度 | 说明 |
|------|------|
| 准确率 | F1 ~88-92%（最优） |
| 延迟 | <10ms/条（GPU 推理） |
| 成本 | 一次性 GPU 训练 + 推理服务器 |
| 部署复杂度 | 需要 GPU 服务器、模型服务化 |
| 灵活性 | 固定分类体系，修改需重新训练 |

### 1.5 引用立场分类方案对比总结

| 维度 | Scite API | LLM 零样本 | DeBERTa 微调 |
|------|-----------|-----------|-------------|
| 准确率 | ~85-90% | ~78-85% | ~88-92% |
| 部署成本 | 按调用付费 | 按调用付费 | GPU 服务器 |
| 运维复杂度 | 低（托管） | 低（API） | 高（本地） |
| 获取门槛 | 高（需机构） | 低（API Key） | 中（需标注数据） |
| 灵活性 | 低 | 高 | 中 |
| 离线可用 | 否 | 否 | 是 |
| **推荐度** | 不推荐 | **推荐（MVP）** | 推荐（生产） |

## 2. 社区检测（Community Detection）

### 2.1 问题定义

在引用/知识图谱网络中检测社区结构，用于主题聚类、全局搜索、层次化组织。当前方案计划使用 Leiden 算法。

### 2.2 方案 A：Neo4j Aura（云托管图数据库）

**Graph Data Science (GDS) 库支持的社区检测算法**：

| 算法 | GDS 过程 | 说明 |
|------|---------|------|
| Louvain | `gds.louvain.stream()` / `.write()` | 经典模块度优化算法 |
| **Leiden** | `gds.leiden.stream()` / `.write()` | Louvain 改进版，保证社区连通性 |
| Label Propagation | `gds.labelPropagation.stream()` | 快速标签传播 |
| Weakly Connected Components | `gds.wcc.stream()` | 连通分量检测 |
| SLLPA | `gds.sllpa.stream()` | 同步标签传播变体 |

**Neo4j Aura 产品层级**：

| 层级 | 价格（约） | GDS 支持 | 说明 |
|------|-----------|---------|------|
| AuraDB Free | $0 | 否 | 免费层不支持 GDS 插件 |
| AuraDB Professional | ~$0.12/hr 起 | 可选 | 需要额外配置 GDS |
| AuraDB Enterprise | 联系销售 | 是 | 完整 GDS 支持 |
| AuraDS | 联系销售 | 是 | 专用图数据科学实例 |

**限制**：
- **AuraDB Free 和 Professional 层不直接支持 GDS**，需要 Enterprise 或 AuraDS
- GDS 的 Leiden 算法在云实例上运行受实例规格限制
- 对于小规模图（<10 万节点），性价比不如本地方案
- 数据导入/导出有网络延迟

**适用性评估**：
- 优势：托管服务、无需运维、GDS 原生支持 Leiden
- 劣势：成本较高（Enterprise 级别才有完整 GDS）、小规模图性价比低
- **结论：不推荐**。社区检测是纯计算任务，不需要图数据库的持久化和查询能力。

### 2.3 方案 B：AWS Neptune

**Neptune Analytics 内置算法**：

| 算法 | 支持状态 | 说明 |
|------|---------|------|
| PageRank | 已支持 | 节点重要性排序 |
| Shortest Path | 已支持 | 最短路径 |
| Connected Components | 已支持 | 连通分量 |
| **Label Propagation** | 已支持 | 社区检测（近似） |
| **Louvain** | 部分支持 | 通过 Neptune Analytics |
| **Leiden** | **未原生支持** | 需要自行实现或通过 DGL |

**限制**：
- **Neptune 不原生支持 Leiden 算法**，仅支持 Label Propagation 等基础社区检测
- Neptune Analytics 的算法库比 Neo4j GDS 窄
- 需要 AWS 账号和 Neptune 集群配置，运维复杂度高于纯 Python 方案
- 按计算单元计费，小规模图成本不划算

**适用性评估**：
- 劣势：不支持 Leiden、运维复杂、成本高
- **结论：不推荐**。Neptune 的强项是大规模图 OLTP 查询，不是算法计算。

### 2.4 方案 C：leidenalg（本地 Python 库）-- 推荐

**核心特性**：
- **纯 CPU 运行**，不需要 GPU
- 核心算法用 C++ 实现，通过 igraph C 库调用，性能极高
- `pip install leidenalg` 一键安装，依赖 `python-igraph`
- 支持 Modularity、CPM（Constant Potts Model）等多种质量函数
- 支持层次化 Leiden（通过 graspologic 库）

**性能基准**：

| 图规模 | 节点数 | 边数 | Leiden 耗时 | 硬件 |
|--------|--------|------|------------|------|
| 小型 | 1K | 10K | <1s | 普通 CPU |
| 中型 | 10K | 100K | 1-5s | 普通 CPU |
| 大型 | 100K | 1M | 5-30s | 普通 CPU |
| 超大型 | 1M | 10M | 1-5min | 普通 CPU |

**与层次化 Leiden 的配合**：
```python
# leidenalg 方案（标准 Leiden）
import igraph as ig
import leidenalg

g = ig.Graph.TupleList(edges, directed=True)
partition = leidenalg.find_partition(g, leidenalg.ModularityVertexPartition)

# graspologic 方案（层次化 Leiden，GraphRAG 风格）
from graspologic.partition import hierarchical_leiden

community_mapping = hierarchical_leiden(
    edges=edge_list,
    max_cluster_size=10,
    resolution=1.0,
)
```

**适用性评估**：
- 优势：零成本、零部署、纯 CPU、高性能、无外部依赖
- 劣势：需要本地 Python 环境（但这不算真正的劣势）
- **结论：强烈推荐**。社区检测是纯计算任务，leidenalg 完全满足需求，无需任何云服务。

### 2.5 社区检测方案对比总结

| 维度 | Neo4j Aura | AWS Neptune | leidenalg (本地) |
|------|-----------|-------------|-----------------|
| Leiden 支持 | 有（Enterprise） | **无** | **有** |
| 层次化 Leiden | 无 | 无 | 有（graspologic） |
| 成本 | $100+/月 | $50+/月 | **$0** |
| 运维复杂度 | 中 | 高 | **低** |
| 性能 | 受实例限制 | 受实例限制 | **原生 C++ 高性能** |
| GPU 需求 | 否 | 否 | **否** |
| **推荐度** | 不推荐 | 不推荐 | **强烈推荐** |

## 3. 引用网络（Citation Network）

### 3.1 问题定义

构建论文之间的引用关系网络。当前方案计划用 GROBID 从 PDF 解析参考文献列表，再通过 DOI 解析建立引用关系。

**核心问题**：能否完全用 Semantic Scholar API + OpenAlex API 替代 GROBID，跳过 PDF 解析步骤？

### 3.2 Semantic Scholar API

**API 端点**：

| 端点 | 方法 | 说明 |
|------|------|------|
| `/paper/DOI:{doi}` | GET | 通过 DOI 查询论文 |
| `/paper/Title:{title}` | GET | 通过标题查询论文 |
| `/paper/{id}/citations` | GET | 获取引用该论文的论文列表 |
| `/paper/{id}/references` | GET | 获取该论文引用的论文列表 |
| `/paper/search?query=...` | GET | 搜索论文 |
| `/paper/batch` | POST | 批量查询论文 |

**关键字段**（通过 `fields` 参数指定）：
- `title`, `authors`, `year`, `abstract`
- `citations`, `references`（引用/被引论文列表）
- `externalIds`（DOI, ArXiv, PubMed 等）
- `citationCount`, `influentialCitationCount`

**覆盖范围**：
- **2 亿+ 篇论文**元数据
- **引用关系覆盖**：S2ORC 语料库包含 5 亿+ 引用链接
- 通过 DOI 可直接查询引用关系，**无需从 PDF 提取 reference list**

**速率限制**：

| 层级 | 限制 | API Key |
|------|------|---------|
| 无 Key | ~100 req/5min | 不需要 |
| 免费 Key | ~1 req/s (~1,500/day) | 免费申请 |
| 商业 Key | 更高 QPS | 联系 AllenAI |

**查询示例**：
```
# 通过 DOI 查询论文的引用关系
GET https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/3394486.3406901?fields=title,references,citations

# 返回该论文的所有 references（被引论文）和 citations（施引论文）
```

**适用性评估**：
- 优势：免费、覆盖广、直接通过 DOI 查询引用关系、无需 PDF 解析
- 劣势：速率限制较严、部分论文覆盖不全（尤其是非英文、小众期刊）

### 3.3 OpenAlex API

**API 端点**：

| 端点 | 说明 |
|------|------|
| `GET /works/{id}` | 查询单篇论文 |
| `GET /works?filter=doi:{doi}` | 通过 DOI 查询 |
| `GET /works?filter=cites:{id}` | 查询引用某论文的所有论文 |
| `GET /works?filter=cited_by:{id}` | 查询被某论文引用的论文 |

**覆盖范围**：
- **2.5 亿+ 篇学术作品**（works）
- 完全免费，CC0 许可
- 继承自 Microsoft Academic Graph (MAG)，数据质量高

**速率限制**：
- 无 Key：~10 req/s
- Polite Pool（提供 email）：更高限制
- 无每日请求上限

**引用关系获取方式**：
```
# 查询 DOI 为 10.xxxx 的论文被谁引用
GET https://api.openalex.org/works?filter=cites:W1234567890

# 每个 work 对象包含 cited_by_count 和 cited_by_api_url
```

**适用性评估**：
- 优势：完全免费、覆盖最广、无严格速率限制、支持大规模批量查询
- 劣势：引用关系粒度较粗（无引用上下文/立场信息）

### 3.4 OpenCitations COCI

**概述**：
- 专注 DOI-to-DOI 引用链接，**15 亿+ 条引用关系**
- CC0 许可，完全免费
- REST API + SPARQL 端点

**API 端点**：

| 端点 | 说明 |
|------|------|
| `/citations/DOI` | 获取该 DOI 被谁引用 |
| `/references/DOI` | 获取该 DOI 引用了谁 |
| `/citation/DOI/DOI` | 检查两个 DOI 间的引用关系 |
| `/metadata/DOI` | 获取 DOI 元数据 |

**适用性评估**：
- 优势：引用数据最全（15 亿+）、完全免费、专注引用关系
- 劣势：仅有 DOI-to-DOI 关系，无元数据丰富度

### 3.5 引用网络 API 对比

| API | 覆盖范围 | 免费 | 引用关系 | 引用上下文 | 元数据丰富度 | 速率限制 |
|-----|---------|------|---------|-----------|------------|---------|
| **Semantic Scholar** | 2 亿+ papers | 是 | citations + references | 有（部分） | 高 | 1 req/s (free key) |
| **OpenAlex** | 2.5 亿+ works | 是 | cited_by + cites | 无 | 高 | 10 req/s |
| **OpenCitations COCI** | 15 亿+ 引用 | 是 | DOI-to-DOI | 无 | 低 | 无严格限制 |
| **CrossRef** | 1.5 亿+ works | 是 | references | 无 | 中 | 50 req/s |

### 3.6 能否完全替代 GROBID？

**关键问题分析**：

| 场景 | GROBID 必要性 | API 替代可行性 |
|------|-------------|---------------|
| 用户上传的 PDF 论文 | **需要** | API 无法解析用户上传的 PDF 全文 |
| 通过 DOI 查询引用关系 | 不需要 | **Semantic Scholar / OpenAlex 完全替代** |
| 获取参考文献列表 | 不需要 | **Semantic Scholar /references 端点替代** |
| 提取引用上下文文本 | 需要 | Semantic Scholar 部分提供，Scite 完整提供 |
| 论文全文分块和 RAG | **需要** | API 不提供全文文本 |
| PDF 元数据提取 | 可选 | API 通过 DOI 查询替代 |

**结论**：
- **引用关系获取**：可以完全用 API 替代，不需要 GROBID
- **PDF 全文解析**：仍然需要 GROBID（或其他 PDF 解析器），因为 API 不提供用户上传 PDF 的全文内容
- **推荐混合方案**：GROBID 仅用于 PDF 全文解析和分块，引用关系完全通过 API 获取

### 3.7 推荐的引用网络构建流程

```
用户上传 PDF
    ↓
GROBID 解析 → 论文元数据 + 全文文本 + 参考文献列表
    ↓
从参考文献中提取 DOI / 标题
    ↓
Semantic Scholar API → 通过 DOI/标题查询引用关系
    ↓                    → 获取 references（被引论文列表）
    ↓                    → 获取 citations（施引论文列表）
    ↓
OpenAlex API → 补充 Semantic Scholar 缺失的引用关系
    ↓          → 获取作者消歧信息
    ↓
OpenCitations COCI → 补充 DOI-to-DOI 引用链接
    ↓
合并去重 → 构建完整的引用网络
    ↓
写入知识图谱（Neo4j / PostgreSQL）
```

**优势**：
- GROBID 仅负责 PDF 解析（它的强项），不承担引用关系构建
- 引用关系通过多个 API 交叉验证，数据更完整
- 避免了 GROBID reference extraction 的解析错误传播

## 4. 综合推荐方案

### 4.1 三项技术的推荐方案

| 技术 | 推荐方案 | 理由 |
|------|---------|------|
| **引用立场分类** | LLM 零样本分类（MVP） → DeBERTa 微调（生产） | MVP 阶段用 GPT-4o/Claude 零样本分类，准确率 ~80-85% 可接受；数据积累后微调本地模型提升至 ~90% |
| **社区检测** | leidenalg + graspologic（纯本地 Python） | 纯 CPU 运行、零成本、高性能、支持层次化 Leiden，无需任何云服务 |
| **引用网络** | Semantic Scholar API + OpenAlex API + COCI（替代 GROBID 引用提取） | 引用关系完全通过 API 获取，GROBID 仅用于 PDF 全文解析 |

### 4.2 架构调整建议

**调整前（全本地部署）**：
```
PDF → GROBID（全文解析 + 引用提取 + DOI 解析）
    → DeBERTa（引用立场分类）
    → leidenalg（社区检测）
    → 知识图谱
```

**调整后（混合方案）**：
```
PDF → GROBID（仅全文解析 + 元数据提取）
    → LLM API（引用立场分类，MVP 阶段）
    → leidenalg（社区检测，本地 CPU）
    → Semantic Scholar + OpenAlex API（引用关系获取）
    → 知识图谱
```

### 4.3 成本对比

| 组件 | 全本地部署 | 混合方案（推荐） |
|------|-----------|-----------------|
| GROBID | Docker 部署 | Docker 部署（规模更小） |
| 引用立场分类 | GPU 服务器 + DeBERTa | LLM API ~$0.002/条 |
| 社区检测 | Python 环境 | Python 环境（不变） |
| 引用网络 | GROBID 全量解析 | 免费 API（S2 + OpenAlex） |
| 月运维成本 | GPU 服务器 $50-200/月 | LLM API $5-20/月 |

### 4.4 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| LLM 分类准确率不足 | 误判引用立场 | Few-Shot 优化 + 低置信度人工复核 |
| API 速率限制 | 批量处理受限 | 缓存 + 限速队列 + 多 API 互补 |
| API 服务不可用 | 功能中断 | 多 API fallback（S2 → OpenAlex → COCI） |
| 部分论文 API 无覆盖 | 引用关系缺失 | 保留 GROBID 引用提取作为 fallback |
