# 项目规范

更新日期：2026-05-28

本文档是 PaperAgent 的工程规范。它定义项目如何组织、开发、测试、配置、发布和治理。所有新增代码、文档、测试和脚本都应优先遵守本文档；历史代码可以逐步迁移，不要求在一次提交中全部重构。

## 1. 项目定位

PaperAgent 是面向论文调研、知识库分析和学术写作的多 Agent 系统。项目当前包含：

- `agents_v3`：核心业务模块，包含 `research_workspace`（项目管理、论文库、知识提取、图谱、QA、报告）。
- `tests`：自动化测试目录。
- `docs`：文档目录，按 getting-started、api、development、research 等分类。

工程目标：

- 运行路径清晰：本地、测试、Docker 的入口一致。
- 模块边界清晰：Agent、工具、检索、API、存储、写作、工作流各自负责自己的领域。
- 结果可追溯：论文、引用、检索结果、LLM 输出、工具调用保留来源和元数据。
- 默认安全：密钥不入库，工具最小权限，LLM 输出不直接信任。
- 默认可测：核心逻辑能脱离真实 LLM 和网络运行测试。

## 2. 目录规范

推荐结构：

```text
paper-agent/
├── pyproject.toml
├── requirements.txt
├── config.yaml
├── .env.example
├── .pre-commit-config.yaml
├── Dockerfile
├── docker-compose.yml
├── Makefile
├── readme.md
├── docs/
│   ├── README.md
│   ├── api/
│   ├── development/
│   │   ├── 项目规范.md
│   │   └── 代码规范.md
│   ├── getting-started/
│   └── research/
├── src/
│   ├── service.py
│   └── agents_v3/
└── tests/
```

目录职责：

| 目录 | 职责 |
| --- | --- |
| `src/service.py` | 服务入口，启动 FastAPI 应用。 |
| `src/agents_v3/` | 核心业务模块。 |
| `src/agents_v3/research_workspace/` | 研究工作空间：项目管理、论文库、知识提取、图谱、QA、报告。 |
| `src/agents_v3/research_workspace/api/` | FastAPI 路由和依赖注入。 |
| `src/agents_v3/research_workspace/search/` | 多源学术搜索（arXiv/OpenAlex/CrossRef）。 |
| `src/agents_v3/research_workspace/llm/` | LLM 服务层。 |
| `src/agents_v3/research_workspace/evaluation/` | 评估与质量门。 |
| `src/agents_v3/cli.py` | CLI 命令行工具。 |
| `tests/` | 自动化测试。目录结构应尽量映射 `src/`。 |
| `docs/` | 项目文档、开发规范、调研材料和 API 说明。 |

禁止提交：

- `__pycache__`、`.pytest_cache`、`.mypy_cache`、`.ruff_cache`。
- 日志、临时输出、缓存、数据库、模型权重、真实论文数据集。
- `.env`、真实 API Key、Cookie、token、私有 URL。

## 3. 模块边界

### 3.1 模块边界

- `agents_v3` 是唯一的业务模块，包含研究工作空间的所有服务。
- 新增功能应在 `agents_v3/research_workspace/` 下实现。
- 跨模块复用应通过明确的接口和依赖注入。

### 3.2 API 层

- API handler 只负责认证、参数解析、调用服务、返回响应。
- 业务逻辑放在 service、Agent、workflow 或工具层。
- 新增非公开接口必须有认证和输入校验。
- Streaming/SSE 接口必须支持超时、取消、心跳和错误事件。

### 3.3 Agent 与工具

- Agent 决策流程不得直接散落网络请求、文件写入和 SDK 调用。
- 工具必须声明输入 schema、输出结构、权限边界、超时和错误类型。
- 高风险工具，如写文件、联网、执行命令、批量删除、调用外部 API，必须可审计。

### 3.4 搜索、RAG 与学术内容

- 检索结果必须保留来源、时间、查询条件、标题、作者、年份、DOI/URL、分数。
- 生成的学术结论必须能追溯到证据；不能确认时要标记不确定。
- 引用管理和内容生成分离，避免模型凭空编造引用。

## 4. 配置规范

配置优先级：

1. 环境变量。
2. `.env` 本地文件，禁止提交。
3. `config.yaml`。
4. 代码默认值。

常见配置：

```bash
OPENAI_API_KEY=...
ANTHROPIC_API_KEY=...
MINIMAX_API_KEY=...
OPENAI_BASE_URL=...
API_KEY=...
LOG_LEVEL=INFO
HTTP_PROXY=...
HTTPS_PROXY=...
NO_PROXY=...
```

新增配置要求：

- 配置名使用 `snake_case`。
- 有默认值和类型模型。
- 敏感值只从环境变量读取。
- 更新 `.env.example` 或相关运行文档。
- 配置变更不能破坏无密钥的测试环境。

## 5. 依赖规范

`pyproject.toml` 是依赖和工具配置主源。

| 依赖类型 | 放置位置 |
| --- | --- |
| 运行必需依赖 | `[project].dependencies` |
| 可选功能依赖 | `[project.optional-dependencies]` |
| 测试、lint、本地开发依赖 | `[dependency-groups]` |
| Docker/pip 兼容镜像 | `requirements.txt`，需与主依赖同步 |

新增依赖前必须确认：

- 标准库或现有依赖不能解决。
- 许可证可接受。
- 维护状态正常。
- 不显著增加镜像体积或安装复杂度。
- 不引入不必要的网络、遥测或安全风险。

## 6. 工具链规范

项目当前使用：

- Ruff：lint 和 format。
- mypy：类型检查，当前非 strict，但新增公共接口必须类型明确。
- pytest + pytest-asyncio：测试。
- pre-commit：提交前检查。

常用命令：

```bash
pip install -e .
pip install -e ".[api]"

uv sync
uv run ruff check --fix .
uv run ruff format .
uv run mypy src
uv run pytest
uv run pre-commit run --all-files
```

Windows PowerShell 下优先使用 Python、pip、uv、docker 原生命令，不依赖 Unix-only 命令。

## 7. 测试规范

测试目录应映射源码目录：

```text
tests/
├── agents_v3/
└── conftest.py
```

测试分层：

| 类型 | 要求 |
| --- | --- |
| 单元测试 | 不访问真实网络，不调用真实 LLM，不依赖外部密钥。 |
| 集成测试 | 可 mock 外部服务；必须说明依赖和启用方式。 |
| E2E 测试 | 默认跳过，通过环境变量显式启用。 |
| 回归测试 | 修复 bug 时优先补充，覆盖原始失败场景。 |

测试数据要求：

- 小型 fixture 可以提交到 `tests/fixtures/`。
- 大 PDF、真实用户材料、私有论文、模型文件不得提交。
- LLM 响应用固定 fixture 或 mock，不让测试依赖模型随机性。

## 8. 安全规范

PaperAgent 同时面临传统 Web 风险、LLM 风险和 Agent 风险。最低要求：

- API Key、token、Cookie、私有数据不得提交。
- 用户输入、PDF 文本、网页内容、工具输出、LLM 输出都视为不可信。
- 外部 URL 请求必须有 timeout、大小限制和协议限制。
- 文件路径必须规范化，禁止路径穿越。
- LLM 输出进入文件、数据库、API 或工具调用前必须校验。
- Agent 工具采用最小权限，危险操作需要人工确认或白名单。
- 长期记忆、向量库、知识图谱入库前必须记录来源并做清洗。
- 日志脱敏，不输出完整密钥、完整 prompt、隐私数据或系统策略。

重点参考：

- OWASP Top 10 for LLM Applications 2025。
- OWASP Top 10 for Agentic Applications 2026。

## 9. 日志和可观测性

当前项目使用 Loguru 封装。新增代码要求：

- 使用项目日志入口，不直接 `print`。
- 日志带 request_id、task_id、agent_name、tool_name 等上下文。
- 记录耗时、状态、错误类型、上游服务、模型名、重试次数。
- 大文本只记录长度、hash、摘要或安全片段。
- 工具调用、Agent 执行、权限变更、配置变更、文件访问应可审计。

## 10. API 响应规范

JSON 响应建议统一：

```json
{
  "success": true,
  "data": {},
  "metadata": {
    "request_id": "..."
  }
}
```

错误响应建议统一：

```json
{
  "success": false,
  "error": {
    "code": "validation_error",
    "message": "Invalid request"
  },
  "metadata": {
    "request_id": "..."
  }
}
```

状态码约定：

| 状态码 | 场景 |
| --- | --- |
| 400 | JSON 格式错误或基础参数错误 |
| 401 | 缺少或无效认证 |
| 403 | 权限不足 |
| 404 | 资源不存在 |
| 409 | 状态冲突 |
| 422 | 业务校验失败 |
| 429 | 限流或预算耗尽 |
| 500 | 未预期错误 |
| 502/503/504 | 上游服务不可用或超时 |

## 11. Docker 和部署规范

Docker 要求：

- 默认镜像不包含真实 `.env`。
- 使用非 root 用户运行。
- 保留 `/health` 健康检查。
- 运行时写入集中到挂载卷，如 `/app/data`、`/app/output`、`/app/logs`。
- 构建依赖和运行依赖尽量分阶段。
- GPU 或轻量镜像作为独立 target，不影响默认 runtime。

Compose 要求：

- 默认只启动核心服务。
- 监控等可选服务使用 profile。
- 端口、密钥、代理、日志级别通过环境变量注入。

## 12. 文档规范

开发相关文档放在 `docs/development/`：

- `项目规范.md`：工程、流程、配置、测试和发布规范。
- `代码规范.md`：具体编码风格和代码质量要求。

文档要求：

- 新增运行方式必须可复制执行。
- 架构变更必须同步架构或开发文档。
- API 变更必须同步接口说明。
- 调研文档必须标注日期、来源、结论和适用范围。
- 不写个人机器绝对路径，除非是问题复现记录且明确标注。

## 13. Git 规范

提交信息使用 Conventional Commits：

```text
<type>(<scope>): <subject>
```

常用类型：

| type | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修复 |
| `docs` | 文档 |
| `test` | 测试 |
| `refactor` | 重构 |
| `perf` | 性能 |
| `chore` | 工具、杂项 |
| `ci` | CI 配置 |
| `build` | 构建和依赖 |

提交前检查：

- Ruff check/format 已运行或说明原因。
- 测试已运行或说明原因。
- 没有提交密钥、日志、缓存、大文件和生成产物。
- 变更范围聚焦，不混入无关移动、删除或格式化。

## 14. CI/CD 规范

建议 CI 至少包含：

```bash
uv sync
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest
```

CI 原则：

- 默认不调用真实 LLM 或付费 API。
- 需要密钥的测试单独 job，手动触发。
- Docker 构建不注入密钥。
- 发布前必须有版本号、变更说明和可回滚产物。

## 15. 变更准入清单

每个 PR 或重要提交至少确认：

- [ ] 目录和模块位置符合职责边界。
- [ ] 新增配置有默认值、文档和环境变量说明。
- [ ] 新增 API 有认证、校验、错误响应和日志。
- [ ] 新增 Agent/工具有 schema、权限、超时、失败策略和审计信息。
- [ ] 新增 LLM/RAG 输出有来源追踪和结构化校验。
- [ ] 新增功能有测试，或说明无法测试的原因。
- [ ] 没有提交密钥、缓存、日志、生成产物或大文件。
