# 项目规范

调研日期：2026-05-28

本文档定义 PaperAgent 的工程组织、配置、依赖、工作流、安全、测试、部署和可复现性标准。规范以当前仓库为基线，优先解决“多人持续开发时如何不失控”的问题。

## 1. 工程原则

| 原则 | 要求 |
| --- | --- |
| 单一事实源 | 依赖、工具配置和项目元数据优先放在 `pyproject.toml`；运行时配置优先环境变量，其次 `config.yaml`。 |
| 低耦合模块 | Agent、工具、检索、写作、API、监控、状态管理按职责隔离，不跨层直接访问内部实现。 |
| 可替换外部服务 | LLM、搜索源、Embedding、存储和评估服务必须通过适配层封装，不在业务流程中散落 SDK 调用。 |
| 默认可测试 | 核心逻辑不依赖真实网络、真实 LLM 或本地绝对路径；外部依赖可 mock。 |
| 默认安全 | API、Agent 工具、文件访问和外部请求使用最小权限、输入校验、输出校验、审计日志和资源预算。 |
| 默认可追溯 | 学术内容、LLM 输出、工具调用、检索结果、引用和状态变更必须保留可追溯元数据。 |

## 2. 目录结构

当前仓库采用 `src` layout：

```text
paper-agent/
├── pyproject.toml
├── requirements.txt
├── config.yaml
├── Dockerfile
├── docker-compose.yml
├── Makefile
├── readme.md
├── docs/
│   ├── api/
│   ├── architecture/
│   ├── development/
│   ├── getting-started/
│   ├── project-standards/
│   └── research/
└── src/
    ├── main.py
    ├── models/
    └── agents_v2/
        ├── agents/
        ├── api/
        ├── core/
        ├── infra/
        ├── search/
        ├── workflow/
        └── writing/
```

新增目录约定：

| 目录 | 用途 | 约束 |
| --- | --- | --- |
| `src/agents_v2/core/` | 基础抽象、配置、异常、安全、状态基础能力 | 不依赖具体 Agent 或 API 路由。 |
| `src/agents_v2/agents/` | 面向任务的 Agent 实现 | Agent 只通过工具、检索服务、LLM 客户端等接口访问外部能力。 |
| `src/agents_v2/infra/tools/` | 工具注册、工具 schema、外部能力包装 | 工具必须有输入 schema、异常策略和权限边界。 |
| `src/agents_v2/search/` | 学术搜索、RAG、知识图谱、检索排序 | 保存来源、分数、时间和引用元数据。 |
| `src/agents_v2/workflow/` | LangGraph/状态机/编排流程 | 节点保持幂等，状态模型可序列化。 |
| `src/agents_v2/api/` | HTTP API、SSE、中间件、调度接口 | 保持 `aiohttp` 体系和统一响应格式。 |
| `src/agents_v2/writing/` | 写作、引用、修订、质量检查 | 输出必须可追溯到资料来源或上游状态。 |
| `src/models/` | 跨模块共享的数据模型 | 谨慎变更，变更需同步调用方和测试。 |
| `tests/` | 自动化测试 | 新增功能应创建该目录并按单元/集成分层。 |
| `scripts/` | 本地运维、迁移、批处理脚本 | 脚本默认可重复运行，避免写死用户路径。 |
| `data/`、`output/`、`logs/` | 本地数据、生成结果、日志 | 默认不提交到 Git。 |

禁止事项：

- 不新增平行的 `agents_v3`、`new_core`、`utils2` 等临时命名目录，除非有迁移文档。
- 不提交 `__pycache__`、`.pytest_cache`、日志、数据库、模型权重、临时输出。
- 不把大段业务逻辑写进 API handler、Makefile、Dockerfile 或脚本入口。

## 3. Python 项目配置

`pyproject.toml` 是主配置文件，遵循 PyPA `pyproject.toml` 规范和 PEP 621。

必须维护的字段：

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "paper-agent"
version = "0.1.0"
readme = "readme.md"
license = "MIT"
requires-python = ">=3.11"
dependencies = []

[project.optional-dependencies]
api = ["fastapi>=0.110", "uvicorn>=0.27"]

[dependency-groups]
dev = [
    {include-group = "test"},
    {include-group = "lint"},
    "pre-commit>=3.6",
]
test = ["pytest>=8.0", "pytest-cov>=5.0", "pytest-asyncio>=0.24"]
lint = ["ruff>=0.9", "mypy>=1.14"]
```

依赖维护规则：

- 运行时依赖放入 `[project].dependencies`。
- 只在测试、lint、文档或本地开发中使用的依赖放入 `[dependency-groups]`。
- 可由下游选择安装的能力放入 `[project.optional-dependencies]`。
- `requirements.txt` 只作为兼容 Docker/pip 的镜像文件，变更依赖时必须同步。
- 不把标准库、系统包或未使用的实验依赖写入依赖列表。

## 4. 工具链

### 4.1 Ruff

Ruff 同时负责 lint 和格式化。当前项目配置已启用 `E/W/F/I/N/UP/B/SIM/C4/S/A/PIE/PT/RUF/TCH/T20/LOG` 等规则。

本地命令：

```bash
uv run ruff check --fix .
uv run ruff format .
```

CI/提交前检查：

```bash
uv run ruff check .
uv run ruff format --check .
```

规则约定：

- 不新增全局 ignore，除非能说明对全项目都有意义。
- 对遗留代码可用局部 `# noqa: RULE`，必须能从上下文看出原因。
- 测试代码可放宽 `assert` 和少量 `print`，业务代码禁止调试 `print`。

### 4.2 mypy

当前 mypy 不是 strict 模式，目标是逐步增强：

- 新增公共函数、类方法、Pydantic/dataclass 模型必须有类型注解。
- 新增模块避免 `Any` 扩散；无法避免时在边界处转换为明确模型。
- 第三方库缺少类型时可以 `ignore_missing_imports`，但业务模型不能因此失去类型。

```bash
uv run mypy src
```

### 4.3 pre-commit

当前 `.pre-commit-config.yaml` 包含 Ruff、尾随空白、文件末尾换行、YAML 检查和大文件检查。

```bash
uv run pre-commit install
uv run pre-commit run --all-files
```

提交大文件、样本数据、PDF、模型权重或生成结果前必须确认是否应进入 Git。默认不提交。

## 5. 配置管理

配置优先级：

1. 环境变量。
2. `.env` 本地文件，不能提交。
3. `config.yaml`。
4. 代码默认值。

当前 `config.yaml` 包含日志、LLM、缓存、限流、安全、Agent 超时和重试配置。新增配置应遵守：

- 配置名使用 `snake_case`。
- 有默认值、有注释、有类型模型。
- 敏感值只通过环境变量或密钥管理系统传入。
- 不在日志、异常、API 响应或 LLM prompt 中输出密钥。
- 新配置必须写入 `.env.example` 或文档示例，说明含义和默认值。

常见环境变量：

```bash
OPENAI_API_KEY=...
ANTHROPIC_API_KEY=...
MINIMAX_API_KEY=...
OPENAI_BASE_URL=...
API_KEY=...
LOG_LEVEL=INFO
HTTP_PROXY=...
HTTPS_PROXY=...
NO_PROXY=...
```

## 6. API 规范

当前 API 基于 `aiohttp`，入口是 `python -m src.main`，默认端口 `8000`。

API 设计要求：

- 公开端点只允许 `/`、`/health`、`/docs`、`/openapi.json` 和明确的静态资源。
- 非公开端点必须校验 `X-API-Key` 或未来统一认证机制。
- 每个请求必须有 `request_id`，日志带上路径、方法、状态码和耗时。
- JSON 响应统一包含 `success`、`data` 或 `error`、`metadata/request_id`。
- Streaming/SSE 端点必须支持取消、超时、心跳和错误事件。
- Handler 只做参数解析、认证、调用服务、返回响应；业务逻辑放到服务或 Agent 层。
- API 输入输出必须有 schema。当前可使用 Pydantic 模型或明确的 TypedDict/dataclass。

错误码建议：

| 状态码 | 场景 |
| --- | --- |
| 400 | 参数格式错误、字段缺失、非法业务输入 |
| 401 | 缺失或无效 API Key |
| 403 | 已认证但无权限执行 |
| 404 | 资源不存在 |
| 409 | 状态冲突、重复任务、版本冲突 |
| 422 | 输入通过 JSON 解析但业务校验失败 |
| 429 | 限流或资源预算耗尽 |
| 500 | 未预期错误 |
| 502/503/504 | 上游 LLM、搜索源、数据库或外部服务不可用 |

## 7. Agent 和工具规范

### 7.1 Agent 基本契约

Agent 应遵循当前 `BaseAgent` 思路：

- 通过 `AgentInput` 接收任务类型、任务描述、输入数据、上下文、需求和元数据。
- 通过 `AgentOutput` 返回成功状态、结果、推理摘要、后续动作、错误和工具调用。
- 通过 `AgentCapability` 声明可处理任务类型和输入输出 schema。
- 不在 Agent 内直接散落 API Key、路径、网络调用和文件权限逻辑。

新增 Agent 必须说明：

- 处理的任务类型。
- 依赖的工具和外部服务。
- 输入输出数据模型。
- 超时、重试、降级和失败结果。
- 是否需要 HITL 人工确认。
- 产生的审计日志和可追溯元数据。

### 7.2 工具规范

Agent 工具是高风险边界，必须具备：

- 稳定名称，使用 `snake_case`。
- 面向 LLM 的短描述，避免歧义和过度授权。
- JSON Schema 或 Pydantic 输入模型。
- 明确权限：可读/可写、可访问路径、可访问网络域名、最大文件大小、最大 token/请求数。
- 明确错误类型，错误信息可给模型理解，但不能泄露密钥、系统 prompt 或内部堆栈。
- 工具调用日志：工具名、调用方、输入摘要、输出摘要、耗时、失败原因、引用来源。

### 7.3 MCP 对齐

若新增 MCP server/client，按 MCP 官方概念设计：

- `Tools`：可执行动作，必须有输入 schema 和权限限制。
- `Resources`：只读上下文或数据，必须标注来源、MIME、更新策略。
- `Prompts`：可复用提示模板，必须版本化，避免混入密钥或私有系统策略。
- 传输方式优先 `stdio` 用于本地工具，远程服务使用官方支持的 HTTP/SSE 或 Streamable HTTP 方案时必须加认证和限流。

## 8. LLM 和 RAG 规范

LLM 调用必须通过统一客户端或适配层封装，禁止在业务代码中到处直接实例化 SDK。

LLM 请求要求：

- 设置模型、温度、最大 token、超时、重试次数。
- 对结构化输出使用 JSON schema、Pydantic 校验或可靠解析策略。
- 保存调用元数据：模型、provider、prompt 版本、输入摘要、输出摘要、token 用量、耗时、错误。
- 对用户输入、检索内容和系统指令做清晰分隔，降低提示注入风险。
- 不把系统 prompt、API Key、完整隐私数据写入日志或返回给前端。

RAG/学术检索要求：

- 每条检索结果保留 `source`、`title`、`authors`、`year`、`doi/url`、`abstract/snippet`、`score`、`retrieved_at`。
- 去重逻辑优先 DOI，其次 arXiv ID、标题规范化、作者年份。
- 引用和事实性结论必须能追溯到来源；无法确认时标记不确定。
- 不把低可信网页内容直接提升为学术证据。
- 缓存外部搜索结果时记录过期时间和来源许可限制。

## 9. 安全规范

参考 OWASP Top 10 for LLM Applications 2025 和 OWASP Top 10 for Agentic Applications 2026，PaperAgent 重点关注：

| 风险 | 项目要求 |
| --- | --- |
| 提示注入 | 用户文本、论文内容、网页内容、工具输出都视为不可信；系统指令与数据分隔。 |
| 敏感信息泄露 | 密钥、系统 prompt、用户隐私、未公开论文和日志不得进入模型输出或前端响应。 |
| 供应链风险 | 固定依赖范围，审查新增依赖和 Docker 基础镜像。 |
| 不安全输出处理 | LLM 输出进入文件、API、命令、数据库前必须校验。 |
| 过度代理权限 | 工具最小权限，写文件、联网、执行命令、发送外部请求需显式边界。 |
| 向量和知识库风险 | 入库数据保留来源和清洗状态；检索结果不得越权跨用户混用。 |
| 资源消耗 | 设置 token、并发、请求频率、文件大小、PDF 页数和任务时长上限。 |

Agent 专属风险也必须纳入设计评审：

| OWASP Agentic Top 10 项 | 项目控制点 |
| --- | --- |
| ASI01 Agent Goal Hijack | 锁定任务目标和允许动作，高影响或目标变更动作需要确认。 |
| ASI02 Tool Misuse and Exploitation | 工具 schema、权限、参数和输出全链路校验，禁止无约束工具链调用。 |
| ASI03 Identity and Privilege Abuse | Agent 不继承超出任务需要的用户权限，区分用户身份、服务身份和工具身份。 |
| ASI04 Agentic Supply Chain Vulnerabilities | 审查 MCP server、插件、技能、模型和第三方工具来源。 |
| ASI05 Unexpected Code Execution | 默认不开放命令执行；如必须执行，使用白名单、沙箱和人工确认。 |
| ASI06 Memory and Context Poisoning | 记忆、向量库和长期上下文入库前清洗并记录来源。 |
| ASI07 Insecure Inter-Agent Communication | 多 Agent 消息要有来源、目标、schema、权限和审计。 |
| ASI08 Cascading Failures | 工作流节点设置熔断、重试上限、检查点和降级路径。 |
| ASI09 Human-Agent Trust Exploitation | UI/API 不夸大 Agent 确定性，关键建议展示来源和置信度。 |
| ASI10 Rogue Agents | 监控异常目标漂移、异常工具序列和越权行为，支持停止和回滚。 |

工程要求：

- `.env`、密钥、访问 token、私有数据不得提交。
- 日志默认脱敏邮箱、电话、API Key、Bearer token、Cookie。
- 外部 URL 请求必须设置超时、最大响应大小和允许协议。
- 文件路径使用 `pathlib.Path` 规范化，禁止任意路径穿越。
- 危险操作写入安全审计：配置变更、权限变更、工具执行、文件访问、Agent 执行。

## 10. 测试规范

当前 `pyproject.toml` 已配置 `testpaths = ["tests"]`，新增测试目录建议：

```text
tests/
├── conftest.py
├── unit/
├── integration/
├── e2e/
└── fixtures/
```

测试分层：

| 类型 | 范围 | 要求 |
| --- | --- | --- |
| 单元测试 | 纯函数、模型、解析、排序、状态转换、工具 schema | 快速、无网络、无真实 LLM。 |
| 集成测试 | API handler、Agent 与工具组合、检索 pipeline | 外部服务 mock 或使用录制 fixture。 |
| E2E 测试 | 完整论文任务或报告任务 | 默认跳过，需要显式环境变量启用。 |
| 回归测试 | 修复 bug 时新增 | 先复现问题，再验证修复。 |

命令：

```bash
uv run pytest
uv run pytest tests/unit
uv run pytest tests/integration
uv run pytest --cov=src
```

测试数据：

- 小样本放 `tests/fixtures/`。
- 大 PDF、真实论文、私有数据不进入仓库。
- LLM 响应使用固定 fixture，避免测试随机失败。

## 11. Git 工作流

分支命名：

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| 功能 | `feature/<short-name>` | `feature/search-reranker` |
| 修复 | `fix/<short-name>` | `fix/api-timeout` |
| 文档 | `docs/<short-name>` | `docs/project-standards` |
| 重构 | `refactor/<short-name>` | `refactor/tool-registry` |
| 发布 | `release/<version>` | `release/v0.2.0` |

提交信息使用 Conventional Commits：

```text
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

常用 type：`feat`、`fix`、`docs`、`test`、`refactor`、`perf`、`style`、`chore`、`ci`、`build`。

示例：

```text
feat(search): add DOI based deduplication

Normalize DOI and arXiv IDs before merging academic search results.
```

PR 合并前检查：

- 说明变更目的、主要实现、测试结果和风险。
- 通过 Ruff、测试和必要的类型检查。
- 涉及 API、配置、架构、数据模型、部署的变更同步文档。
- 不混入无关格式化、移动文件或删除文档。

## 12. 文档规范

文档文件名：

- 面向中文读者的说明文档可以使用中文文件名。
- 工程入口和跨工具识别文件使用英文惯例：`README.md`、`CHANGELOG.md`、`LICENSE`、`CITATION.cff`。
- 同一目录内命名风格保持一致。

内容要求：

- README 说明目标、架构、快速开始、配置、常用命令、测试和部署。
- API 文档说明认证、请求/响应 schema、错误码、SSE 行为。
- 架构文档说明模块职责、数据流、状态流、关键设计决策。
- 调研文档标注日期、来源、结论、适用范围和不确定性。
- 新增运行方式必须可复制执行，不写只在个人电脑可用的绝对路径。

变更日志建议采用 Keep a Changelog 分类：

- `Added`
- `Changed`
- `Deprecated`
- `Removed`
- `Fixed`
- `Security`

## 13. Docker 和部署

当前 Dockerfile 已采用多阶段构建、非 root 用户和健康检查。后续变更要求：

- 不在镜像中写入真实 `.env`、API Key 或用户数据。
- 优先复制依赖文件再安装依赖，利用构建缓存。
- Runtime 镜像只包含运行必需文件。
- 服务健康检查保持 `/health`。
- 容器内写入路径集中到 `/app/data`、`/app/output`、`/app/logs` 或挂载卷。
- GPU 镜像和轻量镜像作为独立 target 维护，不影响默认 runtime。

Compose 规范：

- 默认只启动核心服务。
- 监控、Grafana、Prometheus 等通过 `profiles` 启用。
- 端口、密钥、代理、日志级别通过环境变量配置。
- 数据卷名称稳定，避免误删用户数据。

## 14. CI/CD

建议新增 GitHub Actions：

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - run: uv sync --all-extras --dev
      - run: uv run ruff check .
      - run: uv run ruff format --check .
      - run: uv run mypy src
      - run: uv run pytest
```

CI 原则：

- 默认不调用真实 LLM、不访问付费 API。
- 需要密钥的 E2E 测试单独 job，手动或定时触发。
- 构建 Docker 镜像时不注入密钥。
- 发布前生成版本、变更日志和可回滚产物。

## 15. 可复现性和学术合规

PaperAgent 面向学术论文场景，必须保留研究可复现性：

- 记录检索日期、数据库、查询词、筛选条件、版本和结果数量。
- 论文引用保留 DOI、URL、作者、年份、标题、来源数据库。
- 生成报告保留模型、参数、prompt 版本和主要输入摘要。
- 对自动生成的事实性结论提供来源；无法验证时标记为假设或建议。
- 对用户上传论文、未发表材料和隐私数据使用最小留存策略。
- 重要实验或评估产物应能通过脚本重跑，输出路径和随机种子可配置。

## 16. 迁移和技术债

当前仓库存在一些需要后续治理的点，新增工作应避免扩大问题：

- `src/` 根包名较泛，短期保持兼容；若未来发布到 PyPI，考虑迁移到 `paper_agent/` 包名并提供兼容层。
- `requirements.txt` 与 `pyproject.toml` 双维护，后续可用 uv lock/export 固化。
- `tests/` 目录缺失，新增功能时优先补齐单元测试框架。
- 部分代码仍有重复导入、宽泛类型、直接 SDK 调用和硬编码模型名，重构时按本规范收敛。
- 仓库中若残留 `__pycache__` 或生成文件，应通过独立清理 PR 处理，避免和功能变更混合。

## 17. 变更检查清单

提交前确认：

- [ ] 变更范围符合模块职责，没有跨层偷懒调用。
- [ ] 新增配置有默认值、环境变量说明和文档。
- [ ] 新增 API 有认证、输入校验、错误响应和日志。
- [ ] 新增 Agent/工具有 schema、权限边界、超时和失败策略。
- [ ] 新增 LLM/RAG 输出有结构化校验和来源追踪。
- [ ] 新增功能有测试；无法测试的外部依赖已 mock 或记录原因。
- [ ] Ruff check/format 通过。
- [ ] 未提交密钥、日志、缓存、生成产物、大文件和私有数据。
