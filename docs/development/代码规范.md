# 代码规范

调研日期：2026-05-28

本文档定义 PaperAgent 的 Python 代码编写规范。目标是让 Agent、工具、API、检索、写作和基础设施代码在长期迭代中保持可读、可测、可追踪、可安全运行。

## 1. 基本规则

- Python 版本按 `pyproject.toml`：`>=3.11`。
- 格式化以 Ruff format 为准，行宽 `88`。
- 新增代码优先使用标准库和项目已有抽象，谨慎引入依赖。
- 公共接口必须有类型注解；复杂数据用 Pydantic、dataclass、TypedDict 或 Protocol 表达。
- 核心逻辑应可单元测试，不依赖真实 LLM、真实网络和本机绝对路径。
- 业务代码禁止调试 `print`，使用项目日志系统。
- 不在异常、日志、prompt、API 响应中泄露密钥、系统 prompt 或隐私数据。

## 2. 命名规范

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| 模块和文件 | `snake_case.py` | `paper_search.py`、`citation_tracker.py` |
| 包目录 | `snake_case` | `knowledge_graph`、`full_paper` |
| 变量/函数 | `snake_case` | `query_text`、`merge_results` |
| 类 | `PascalCase` | `BaseAgent`、`CitationTracker` |
| 异常 | `PascalCase` + `Error` | `ExternalAPIError` |
| 常量 | `UPPER_SNAKE_CASE` | `MAX_RETRY_COUNT` |
| 私有成员 | `_snake_case` | `_build_prompt` |
| 布尔值 | `is_`、`has_`、`can_`、`should_` | `is_public_endpoint` |
| 类型变量 | 简短 PascalCase | `T`、`ResultT` |

命名要求：

- 名称表达业务含义，避免 `data`、`obj`、`tmp`、`handle` 等泛词单独出现。
- 同一概念只使用一个词：不要混用 `paper`、`doc`、`article` 表示同一实体。
- 搜索源、模型、Agent 类型等枚举值使用明确字符串，避免魔法字符串散落。
- 函数名用动词开头：`fetch_papers`、`validate_input`、`build_prompt`、`parse_response`。

## 3. 导入规范

导入顺序由 Ruff/isort 自动处理：

```python
from __future__ import annotations

import asyncio
from pathlib import Path
from typing import TYPE_CHECKING

from pydantic import BaseModel, Field

from src.agents_v2.core.exceptions import ValidationError
from src.agents_v2.logging_config import get_logging_logger

if TYPE_CHECKING:
    from src.models.state import AgentContext
```

规则：

- 新文件如需要前向引用，优先加 `from __future__ import annotations`。
- 不使用通配符导入。
- 避免在函数内部导入，除非为了可选依赖、避免循环依赖或降低启动成本。
- 类型检查专用导入放在 `if TYPE_CHECKING:` 下。
- 不新增从深层模块反向导入上层业务的循环依赖。

## 4. 类型注解

公共函数、类方法和模型字段必须有类型：

```python
def normalize_doi(raw_doi: str | None) -> str | None:
    if not raw_doi:
        return None
    return raw_doi.strip().lower().removeprefix("https://doi.org/")
```

优先级：

- 结构化输入输出：Pydantic `BaseModel`。
- 内部不可变配置：`dataclass(frozen=True)` 或 Pydantic model。
- 字典但字段固定：`TypedDict`。
- 可插拔接口：`Protocol`。
- 受限字符串：`Literal` 或 `StrEnum`。
- 可选值：`X | None`，不要使用隐式可选。

示例：

```python
from enum import StrEnum
from typing import Protocol, TypedDict


class SearchSource(StrEnum):
    ARXIV = "arxiv"
    PUBMED = "pubmed"
    OPENALEX = "openalex"


class PaperMetadata(TypedDict, total=False):
    title: str
    doi: str
    year: int


class PaperSearcher(Protocol):
    async def search(self, query: str, limit: int = 20) -> list[PaperMetadata]:
        ...
```

避免：

- 在公共接口返回裸 `dict[str, Any]`。
- 用 `Any` 穿透多个层级。
- 函数可能返回多种不相关类型。
- 为了通过类型检查而随意 `cast`。

## 5. 数据模型

Pydantic 模型适合 API、Agent 输入输出、工具 schema 和 LLM 结构化输出：

```python
from pydantic import BaseModel, Field, field_validator


class SearchRequest(BaseModel):
    query: str = Field(min_length=1, max_length=1000)
    limit: int = Field(default=20, ge=1, le=100)

    @field_validator("query")
    @classmethod
    def strip_query(cls, value: str) -> str:
        return value.strip()
```

模型规则：

- 字段名用 `snake_case`。
- 字段有默认值或明确必填。
- 对来自用户、LLM、外部 API 的数据必须校验。
- 模型转换集中在边界层，不在业务流程中反复手写字典拼装。
- 序列化输出时注意脱敏和排除内部字段。

## 6. 函数和类设计

函数要求：

- 单一职责，默认不超过 50 行；复杂流程拆成清晰私有函数。
- 参数建议不超过 5 个；更多参数使用配置对象或请求模型。
- 返回类型稳定，失败用异常或明确的结果模型，不混用 `False`、`None`、字符串错误。
- 不修改调用方传入的可变对象，除非函数名和文档明确说明。
- I/O、网络、LLM 调用、业务计算分层处理。

示例：

```python
def merge_unique_papers(papers: list[Paper]) -> list[Paper]:
    seen: set[str] = set()
    merged: list[Paper] = []

    for paper in papers:
        key = paper.doi or paper.normalized_title
        if key in seen:
            continue
        seen.add(key)
        merged.append(paper)

    return merged
```

类设计：

- 类应该围绕状态、协议或明确责任存在，不为“放函数”而创建类。
- 构造函数不做重网络调用、长时间 I/O 或启动后台任务。
- 可变共享状态必须受控；并发场景使用锁、队列或不可变快照。
- Base 类只放稳定抽象，避免为了少量重复提前设计复杂继承层次。

## 7. 异步代码

项目中 API、Agent、检索、LLM 调用大量使用 async。规则：

- I/O 密集操作使用 `async def` 和异步客户端。
- async 函数中禁止 `time.sleep`，使用 `await asyncio.sleep`。
- 外部请求必须设置 timeout。
- 并发调用必须设置上限，避免无界 `gather`。
- 长任务支持取消、检查点或阶段性状态更新。

示例：

```python
import asyncio


async def fetch_all(searchers: list[PaperSearcher], query: str) -> list[Paper]:
    semaphore = asyncio.Semaphore(5)

    async def run_search(searcher: PaperSearcher) -> list[Paper]:
        async with semaphore:
            return await asyncio.wait_for(searcher.search(query), timeout=30)

    results = await asyncio.gather(
        *(run_search(searcher) for searcher in searchers),
        return_exceptions=True,
    )

    papers: list[Paper] = []
    for result in results:
        if isinstance(result, Exception):
            logger.warning("Searcher failed", error=type(result).__name__)
            continue
        papers.extend(result)
    return papers
```

注意：

- `asyncio.gather(..., return_exceptions=True)` 后必须处理异常对象。
- 需要强一致的流程不要静默吞掉子任务失败。
- SSE/流式输出必须处理客户端断开。

## 8. 异常处理

使用项目异常层次，如 `AgentError`、`ConfigurationError`、`ValidationError`、`ExternalAPIError`、`TimeoutError`。

规则：

- 抛出具体异常，不抛裸 `Exception` 表示业务错误。
- 捕获异常时保留上下文，必要时使用 `raise ... from exc`。
- 不写空 `except`，不静默吞掉错误。
- 外部服务错误转换为项目异常，避免 SDK 异常泄露到 API 层。
- API 层把异常映射为统一 JSON 错误。

示例：

```python
try:
    response = await llm_client.invoke_json(prompt)
except TimeoutError as exc:
    raise ExternalAPIError("LLM request timed out") from exc
except ValueError as exc:
    raise ValidationError("LLM returned invalid JSON") from exc
```

重试规则：

- 只重试瞬时错误：超时、429、5xx、临时网络失败。
- 不重试参数错误、权限错误、schema 校验失败。
- 使用指数退避和最大次数。
- 重试日志记录 attempt、delay、错误类型，避免记录敏感输入全文。

## 9. 日志和可观测性

当前项目使用 Loguru 封装。业务代码应通过 `get_logging_logger(__name__)` 获取 logger。

日志要求：

- 使用结构化字段，不拼接大段上下文。
- 每个请求、任务、Agent 执行、工具调用带 request/task/session id。
- 日志包含耗时、状态、错误类型、上游服务、模型名等诊断字段。
- 不记录 API Key、Bearer token、Cookie、完整 prompt、完整论文私密内容。
- 大文本只记录摘要、长度、hash 或前后少量安全片段。

示例：

```python
logger.info(
    "Search completed",
    source=source.value,
    query_hash=query_hash,
    result_count=len(results),
    duration_ms=duration_ms,
)
```

## 10. 安全编码

输入处理：

- 用户输入、上传文件、网页内容、PDF 文本、LLM 输出、工具输出都视为不可信。
- 限制长度、文件大小、页数、MIME、URL scheme、请求耗时。
- HTML/Markdown 渲染前进行转义或安全过滤。
- 路径使用 `Path.resolve()` 后检查是否在允许目录内。

密钥处理：

- 密钥只从环境变量或密钥管理服务读取。
- 不把密钥放入默认配置、测试 fixture、文档示例真实值或日志。
- 对外错误统一返回简短信息，详细堆栈只进内部日志。

LLM/Agent 安全：

- Prompt 中明确区分系统指令、用户输入、检索资料和工具结果。
- 不让检索文本覆盖系统策略。
- 工具执行前校验模型给出的参数。
- 高风险操作需要人工确认或显式白名单。
- Agent 目标、工具序列、长期记忆和跨 Agent 消息必须可审计，防止目标劫持、工具滥用、上下文污染和级联失败。

## 11. LLM 调用规范

LLM 客户端必须集中封装：

```python
class LLMClient(Protocol):
    async def invoke_text(self, prompt: str, *, timeout: int = 120) -> str:
        ...

    async def invoke_model(self, prompt: str, output_type: type[ResultT]) -> ResultT:
        ...
```

调用要求：

- 设置 `model_name`、`temperature`、`max_tokens`、`timeout`。
- 结构化输出先校验再使用。
- prompt 模板应可版本化，核心 prompt 不散落在多个函数中。
- 对响应解析失败、空响应、内容过滤、上游限流分别处理。
- 保留成本和质量评估所需元数据。

禁止：

- 在循环中无上限调用 LLM。
- 把完整用户隐私、密钥或系统 prompt 传给不需要的模型。
- 直接信任 LLM 输出的 JSON、路径、URL、命令、引用和分数。

## 12. Agent 代码规范

新增 Agent 应符合当前 `BaseAgent` 契约：

- `_get_capabilities()` 返回清晰能力描述。
- `execute()` 只负责一次任务执行，输入输出用 `AgentInput`/`AgentOutput` 或其扩展模型。
- `can_handle()` 依赖稳定任务类型，不靠自然语言猜测。
- 工具通过注册表或明确注入获得，不在方法内部临时构造一堆全局对象。
- Agent 输出包含 `success`、`result`、`error`、`metadata`、`tool_calls`。

Agent 内部流程建议：

1. 校验输入。
2. 准备上下文和检索资料。
3. 调用工具或 LLM。
4. 校验输出。
5. 写入审计/追踪元数据。
6. 返回标准结果。

失败输出：

```python
return AgentOutput(
    success=False,
    result=None,
    agent_name=self.name,
    error="Search source unavailable",
    metadata={"source": source_name, "retryable": True},
)
```

## 13. 工具代码规范

工具函数必须把安全边界写在代码里：

- 输入模型定义参数范围。
- 访问外部网络时设置域名/协议策略、timeout、重试和限流。
- 访问文件时限制根目录、扩展名、大小和读写模式。
- 返回结构化结果，不返回难以解析的大段自由文本。
- 对 LLM 可见的错误信息简短、可恢复、无敏感信息。

工具 schema 示例：

```python
class FetchPaperInput(BaseModel):
    doi: str = Field(min_length=1, max_length=200)
    include_pdf: bool = False


class FetchPaperOutput(BaseModel):
    title: str
    abstract: str | None = None
    source_url: str
    retrieved_at: str
```

## 14. RAG 和学术内容

检索和生成代码必须优先保证可追溯：

- Paper、Chunk、Citation、SearchResult 使用明确模型。
- chunk 保存 `source_id`、页码/段落、字符范围、hash、创建时间。
- 排序分数区分来源分、语义分、重排分、最终分。
- 生成答案必须引用来源 ID，不允许凭空生成论文标题、作者或 DOI。
- 对冲突证据标记冲突，不强行合并成单一结论。

论文写作输出：

- 区分“检索事实”“模型推断”“用户提供观点”。
- 引用格式化与引用校验分离。
- 修改/润色保留 diff 或变更摘要。
- 章节生成记录使用的大纲、文献、prompt 版本和模型。

## 15. API 代码规范

Handler 示例结构：

```python
async def handle_search(request: web.Request) -> web.Response:
    request_id = request["request_id"]
    payload = await request.json()
    search_request = SearchRequest.model_validate(payload)

    result = await search_service.search(search_request)

    return web.json_response(
        {
            "success": True,
            "data": result.model_dump(),
            "metadata": {"request_id": request_id},
        }
    )
```

规则：

- Handler 不直接写复杂业务逻辑。
- JSON 解析失败、模型校验失败、业务异常分别处理。
- API 返回不暴露内部异常堆栈。
- 所有长任务接口考虑任务 ID、状态查询和取消。
- SSE 每个事件包含类型、数据、任务 ID 或 request ID。

## 16. 测试代码规范

测试命名：

```text
tests/unit/test_doi_utils.py
tests/integration/test_search_pipeline.py
tests/e2e/test_full_paper_workflow.py
```

测试结构使用 Arrange-Act-Assert：

```python
async def test_merge_results_deduplicates_by_doi() -> None:
    papers = [
        Paper(title="A", doi="10.123/ABC"),
        Paper(title="A copy", doi="https://doi.org/10.123/abc"),
    ]

    result = merge_unique_papers(papers)

    assert len(result) == 1
```

规则：

- 单元测试不访问真实网络、不调用真实 LLM、不依赖执行顺序。
- 随机性设置 seed 或使用固定 fixture。
- 时间相关逻辑注入 clock 或使用可控时间。
- Mock 放在边界，避免把被测逻辑也 mock 掉。
- Bug 修复必须新增能复现原问题的测试。
- E2E 或付费 API 测试默认 `skip`，通过环境变量显式启用。

## 17. 注释和文档字符串

注释说明“为什么”，不是复述“做什么”。

公共模块、复杂类和公共函数建议使用 Google 风格 docstring：

```python
def rerank_papers(query: str, papers: list[Paper]) -> list[Paper]:
    """Rerank papers for a user query.

    Args:
        query: Normalized user query.
        papers: Candidate papers with source metadata.

    Returns:
        Papers sorted by final relevance score.

    Raises:
        ValidationError: If query is empty.
    """
```

TODO 格式：

```python
# TODO(owner): explain what remains and when it can be removed.
# FIXME(owner): explain the known bug and expected behavior.
```

避免：

- 过期注释。
- 大段复制外部文档。
- 在注释里写密钥、内部地址或临时个人路径。

## 18. 性能和资源

性能要求：

- 外部请求、LLM、PDF 解析、Embedding、批量检索必须有超时。
- 批量任务使用分页、流式处理或生成器，避免一次性读入大文件。
- 对重复搜索、解析和 embedding 使用缓存，但缓存 key 必须包含影响结果的参数。
- 并发数、token 数、文件大小、PDF 页数、搜索结果数可配置。
- 热路径避免重复编译正则、重复创建客户端、重复加载模型。

资源默认值建议：

| 项 | 建议 |
| --- | --- |
| LLM 请求超时 | 120 秒以内，长任务分阶段 |
| Agent 任务超时 | 使用 `config.yaml` 的 `agent.timeout` |
| 外部搜索并发 | 默认不超过 5 个源同时请求 |
| 用户输入长度 | 默认不超过 `security.max_input_length` |
| 重试次数 | 默认 3 次以内，指数退避 |

## 19. 常见反模式

| 反模式 | 问题 | 替代 |
| --- | --- | --- |
| API handler 里直接拼 prompt 调 LLM | 难测试、难审计 | 封装 service/Agent/LLM client |
| 到处传 `dict[str, Any]` | 类型和字段不可控 | Pydantic/TypedDict/dataclass |
| 捕获 `Exception` 后返回空结果 | 隐藏错误 | 记录上下文并抛具体异常或返回失败模型 |
| 无上限 `asyncio.gather` | 资源耗尽 | semaphore + timeout |
| 信任 LLM 生成的 JSON | 易崩溃或注入 | schema 校验和错误恢复 |
| 把搜索结果当事实 | 幻觉和引用错误 | 保留来源、置信度和人工可审查证据 |
| 硬编码本地路径 | 无法部署 | 配置项 + `Path` |
| 提交日志/缓存/pycache | 污染仓库 | `.gitignore` + 清理脚本 |

## 20. 代码评审清单

评审时优先看风险：

- [ ] 模块职责是否清楚，没有跨层耦合。
- [ ] 输入、输出、错误路径是否有类型和校验。
- [ ] 异步调用是否有 timeout、并发上限和取消处理。
- [ ] 外部服务、LLM、工具调用是否集中封装。
- [ ] 日志是否可诊断且不泄露敏感信息。
- [ ] Agent/工具是否有权限边界和审计信息。
- [ ] RAG/学术输出是否保留来源和引用。
- [ ] 测试是否覆盖正常路径、失败路径和关键边界。
- [ ] Ruff/format/type/test 是否执行或说明未执行原因。
